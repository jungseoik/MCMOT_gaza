# results/rehearsal_viz_aihub — AI hub 리허설 오프라인 시각화

`tools/rehearsal_viz.py` 로 뽑은 **좌: 카메라 그리드 / 우: 공유 2D 맵** mp4.
CJ 것(`../rehearsal_viz/`)과 같은 도구·같은 화면 구성이고, 패키지만 `aihub-rehearsal` 이다.

```bash
python tools/rehearsal_viz.py --package aihub-rehearsal --scenario scenario_01 \
       --out results/rehearsal_viz_aihub
```

## 화면 보는 법

| 위치 | 내용 |
|---|---|
| 좌 | 카메라 그리드 — ID 박스(ID별 색) · 발끝점 · **대응점 헐/유효 ROI**(청록) · 발끝이 헐 안이면 ● 녹색 / 밖이면 ✕ 빨강(= 라이브에서 버려지는 관측) |
| 우 | 공유 2D 맵 — 사이트 층 `floor4`(AI hub 3층) 도면 + 구역·병목·출구 + 전 카메라 투영점(카메라별 색, 2초 궤적). 헐 밖 관측은 회색 ✕ |
| 좌하 | t · 카메라별 관측 수 · 헐 안/밖 누계 · 살아있는 ID 수 |

라이브(:8900)와 같은 조건이다 — 원본 30fps 를 5fps(analyze_fps)로 서브샘플, 카메라마다 독립
BoostTrack, 검출·ReID 는 ① 설정의 프로파일(`--profile auto` → yolo26_clipreid).
매핑(H·대응점·ROI)은 `media/vsource/aihub/rehearsal/rehearsal.json`, 도면·공간요소는
`data/sites/default` 의 `floor4` 를 그대로 쓴다.

## 전제 — 매핑된 카메라만 들어간다

`rehearsal_viz.py` 는 **매핑이 없는 카메라를 아예 제외**한다(2D 맵에 투영할 H 가 없으므로).
시나리오 전원을 보려면 ② 에서 그 시나리오의 카메라를 전부 매핑해야 한다.
현재 18대 중 16대 매핑 — **cam11·cam17 미매핑**(사용자 판단으로 생략), 해당 시나리오는 그만큼 빠진다.

## 출입구 통과 (2026-09-09 추가)

원래 viz 는 출구 **선만 그리고 세지 않았다.** 라이브와 같은 그림을 내려면 통과 집계가 필요해
엔진이 쓰는 `system.spatial.geometry.DirectionalLine` 을 **그대로 재사용**해 붙였다 —
판정 로직이 조금이라도 다르면 영상과 웹 지표가 안 맞는다.

| 항목 | 라이브와 맞춘 값 |
|---|---|
| 판정 | 엔진과 같은 `DirectionalLine` |
| 데드밴드 | 0.1m → 도면 축척으로 px 환산 |
| 방향 | 출구 `inside`(건물 안쪽) 기준, 안→밖 = `out` |
| 중복 | gid 별 방향당 최초 1회 (왕복해도 out 1) |
| 헐 밖 외삽 | `exit_extrap_m` 2.0m = 103px — ADR 09 §18. 문은 대개 헐 밖이라 이게 없으면 영영 안 세진다 |

화면: 2D 맵 출구 옆 실시간 `OUT n` · 상단 바 총합 · 정보 셀 출구별 표 · 종료 시 통과 이벤트 타임라인.

## 라이브와 어긋나 있던 것 — 수정 (2026-09-09)

렌더 중 `findTransformECC` 수렴 실패로 죽으면서 드러났다. viz 가 `BoostTrack()` 을 맨손으로
만들어 `default_settings.py` 기본값을 물려받고 있었다 — 도구의 존재 이유("라이브와 같은 조건")와
어긋난다.

| 항목 | 라이브 (`system/tracking/analyzer.py`) | viz (수정 전) |
|---|---|---|
| ECC | `use_ecc=False` — 고정 CCTV, `assert tracker.ecc is None` 까지 | **`True`** ← 크래시 원인 |
| ID 공간 | `per_instance_ids=True` (카메라별 독립) | 전역 카운터 |
| `max_age` | 분석 fps × 2s | `GeneralSettings` 기본 |

셋 다 라이브와 같게 맞췄다. 부수 효과로 **영상 ID 와 카메라별 진단 ID 가 같은 체계**가 된다
(전엔 카메라 인터리브 순서에 따라 번호가 섞였다).

레이아웃도 채널 수에 따라 2/3/4 열로 — 12채널을 2열로 쌓으면 7행(세로 1,890px)이라 셀이 우표만 해진다.

## 출구 통과가 2배로 세진다 — 카메라 겹침 + 글로벌 ID off

| 출구 | 집계에 기여한 카메라 |
|---|---|
| exit-0 | **cam05 · cam09** (2대) |
| exit-1 | **cam10 · cam12** (2대) |

시나리오 04·07 의 통과 시각을 보면 0.4~0.6s 간격으로 cam05·cam09 가 **번갈아** 찍힌다 —
한 사람이 나갈 때 두 카메라가 각각 1명으로 센다(실제 ~10명, OUT 20).

원인은 중복 방지 키다. `engine.py` 의 debounce 키는 `gid_eff` 인데 **글로벌 ID 가 off** 면
카메라 로컬 키(`cam05:5`)로 떨어진다 — `cam05:5` 와 `cam09:1` 은 다른 키라 각각 집계된다.
현재 설정 `{'enabled': False, 'cos_th': 0.55, ...}`. **웹 라이브도 같은 규칙이라 지금 똑같이 2배로 센다.**

- SEI 는 두 출구가 같은 배율이면 비율이 유지되지만, **문마다 겹침 정도가 다르면 왜곡**된다
  (03 은 5:5 로 나왔는데 exit-0 만 2대라면 실제는 2.5:5 에 가깝다).
- IDR·EPFI·CBS 는 통과 집계를 안 쓰므로 무관.

선택지: ① 글로벌 ID 켜기(설계된 해법, cos 0.55 는 실측 조정값이라 A/B 필요) ·
② `exits[].count_cam` 으로 출구별 집계 카메라를 1대로 못박기(스키마에 이미 있고 현재 None) ·
③ "OUT 은 겹침만큼 부풀 수 있다"를 전제로 해석.

## 실측 — 관측 폐기율이 높다 (2026-09-09)

시나리오 01 전체 집계. `헐 밖`은 라이브에서도 그대로 버려지는 관측이다.

| 카메라 | 관측 | 헐 안 | 헐 밖(폐기) |
|---|---|---|---|
| cam01 | 568 | 490 | 78 (14%) |
| cam02 | 213 | 0 | **213 (100%)** |
| cam03 | 453 | 393 | 60 (13%) |
| cam04 | 252 | 103 | 149 (59%) |
| cam05 | 307 | 160 | 147 (48%) |
| cam09 | 180 | 50 | **130 (72%)** |

전 카메라가 대응점 4~5개뿐이고 **유효 ROI 미지정**이라, 그 점들의 볼록껍질(헐)이 곧 유효영역이
된다. 헐이 사람이 다니는 바닥을 못 덮으면 그 관측은 통째로 버려진다 — cam02·cam09 는 헐이
너무 작아 **한 점도 안 남는다**. CJ 10F 에서 겪은 것과 같은 문제(ADR 09 §9).

조치는 매핑 쪽이다:
- ② 에서 카메라별 **유효 ROI 를 사람이 다니는 바닥 전체로** 그리거나
- 대응점을 **바닥 가장자리까지** 더 찍어 헐을 넓힌다(4점 → 6~8점)

출입구 통과 판정만은 `Thresholds.exit_extrap_m`(기본 2m)로 헐 밖 외삽을 허용하므로(ADR 09 §18)
SEI 는 영향이 덜하지만, 구역 밀도(IDR)·CBS·표출은 헐 안 관측만 쓴다.

## 실측 — 정지 오탐 ID 108 (2026-09-09)

영상에서 **가장 오래 사는 트랙(102프레임 = 시나리오의 44%)이 사람이 아니다.**
cam01 화면 (1090, 700) 의 **접이식 책상 크롬 다리 + 검은 캐스터** — 은색 기둥 둘 아래 검은
덩어리가 다리·신발 형태로 보인다. 26~46초 구간, 20초를 통째로 살아남는다.

| | 오탐 id 108 | 실제 사람 트랙 74개 |
|---|---|---|
| conf 평균 | **0.608** (최소 0.431) | 최소 0.628 · 하위10% 0.829 · 중앙 0.907 |
| 박스 | **39×47** | 최소 높이 135 · 중앙 381 |
| 종횡비 w/h | **0.83** | 0.30 ~ 0.75 (중앙 0.44) |
| 총 이동 | **3px / 20s** | 수백~1,100px |

- **유지되는 이유는 conf 가 높아서가 아니라 끊길 계기가 없어서다.** 사람은 가려짐·프레임
  이탈로 트랙이 끊기는데, 정지 물체는 매 프레임 같은 자리에서 재검출돼 영원히 산다.
  정지성 트랙 전수 중 이렇게 오래 사는 건 이것 하나뿐(나머지는 3~19프레임 실제 사람).
- conf 로도 갈리지만 실제 트랙 하한(0.628)과 여유가 얇다. **높이·종횡비는 겹치는 구간이 없다.**
- BoostTrack ID 는 **전역 카운터**라 카메라 처리 순서가 바뀌면 번호가 달라진다 —
  카메라별 순차 처리로 진단하면 같은 물체가 cam01 id 1·31 로 나온다. 영상과 번호를 맞추려면
  영상과 같은 인터리브(프레임마다 카메라 순회) 순서로 돌려야 한다.

### 조치

`min_conf` 는 `system/metrics/engine.py:260` 에서 표출·지표 진입을 막는다(스키마 주석: "저신뢰
오탐(예: 의자)"). 현재 사이트값 **0.5** 라 0.608 이 그냥 통과한다.

- ② 카메라 행에서 **cam01 만 `min_conf` 0.65~0.7** 로. 사이트 전역을 올리면 0.628 짜리
  실제 트랙이 위험하다.
- 세션 녹화는 **min_conf 필터 이전 raw** 를 저장하므로(`metrics/recorder.py:8`),
  ④ 리플레이에서 값을 바꿔 재계산하며 안전하게 비교할 수 있다.
- 이 폴더의 시각화 영상은 **min_conf 미적용 원본 트래커 출력**이다 — 라이브 ③ 은 이미 0.5 로
  한 번 걸러지므로 영상에 보이는 오탐 일부는 실제 지표엔 안 들어간다.
- 근본 해결은 **종횡비·최소높이 필터**(현재 `min_box_size=16px` 뿐이라 39px 오탐이 통과).

## 조치 구현 — `min_box_h` (2026-09-09)

박스 높이 하한을 **min_conf 와 같은 상속 규칙**으로 넣었다.

| 위치 | 내용 |
|---|---|
| `system/config/schema.py` | `Thresholds.min_box_h`(사이트 기본, **0 = 끔**) · `CameraConfig.min_box_h`(카메라별 오버라이드, None = 상속) |
| `system/metrics/engine.py` | min_conf 게이트 바로 옆에서 `bbox 높이 < min_box_h` 관측을 버린다 |
| `system/vsource/package.py` | 매니페스트 `cameras[].min_box_h`·`min_conf` 를 가상 카메라에 전달 (rh_* 는 ② 인라인 편집이 409 라 패키지가 정본) |
| `webui/static/main/view_cams.js` | ② 카메라 행에 [최소 박스 높이] 인라인 편집 (conf 와 같은 자리·같은 규칙) |

- **적용값**: `aihub-rehearsal` 의 `cam01` 만 **80px**. 오탐 44~50 · 실제 최소 126 → 양쪽 1.6x 여유.
  나머지 카메라·사이트 전역은 건드리지 않았다(0 = 끔, 기존 동작 유지).
- 녹화는 필터 **이전 raw** 라 ④ 리플레이에서 값을 바꿔 재계산된다 —
  `metrics/replay.py` 가 thresholds 를 `hasattr` 로 훑어서 코드 추가 없이 따라온다.

### 왜 px 인가 (미터가 아니라)

"픽셀은 카메라마다 다르니 맵 미터로 재면 사이트 하나로 끝나지 않나" 를 실측으로 확인했더니
**반대였다** — 같은 시나리오 관측 1,508개(실제 1,373 · 오탐 135):

| 단위 | 오탐 | 실제 최소 | 여유 |
|---|---|---|---|
| 화면 px 높이 | 44~50 | 126 (cam01) · 130 · 189 · 240 | **2.5x** |
| 맵 바닥폭 m | 0.24~0.27 | 0.41 · **0.27** · 0.39 · 0.45 | **겹침** |

맵 미터는 bbox 하단 두 모서리를 발 위치로 가정하는데 실제로는 팔·자세로 폭이 요동친다.
px 높이가 훨씬 깨끗하게 갈린다. 대신 원근을 타므로(4대 최소가 126~240, 2배 차) **카메라별**이 정본.

## 전체 연속 시나리오 시각화 (scenario_10_full, 2026-09-09)

## 4대 지표 측정 가능 여부 (2026-09-09 기준)

| 지표 | 상태 | 근거 |
|---|---|---|
| **IDR** | ❌ **측정 불가** | `IDR_e = D(구역, 경보발생원) / (개시시각 − 경보시각)` 인데 floor4 `alarm_origins = 0`. 엔진이 `origins=[(0,0)]` 으로 폴백해 **도면 좌상단 모서리 기준 거리** — 숫자는 나오지만 의미가 없다. ③ 훈련 시작의 원점 게이트에도 걸린다 |
| **CBS** | ⚠ 계산은 되나 병목이 과소 | b1~b4 가 **문 스윙 아크(26점)** 를 그대로 쓴 것이라 1.35~2.03 m². rho_crit 2.0 이면 임계인원이 2.7~4.1 명 — 한 명만 들어와도 밀도가 0.5~0.7 명/㎡ 로 튄다 |
| **SEI** | ✓ | 출구 2개 · `design_capacity` 8/7 설정됨. 다만 위 출구 집계 오차가 그대로 전파 |
| **EPFI** | ✓ | 경로 5개 |

**IDR 은 구역도 문제다** — z1 하나뿐인데 면적이 **1,479.9 m² = 층 전체**(도면 38.9×39.2m)다.
IDR 은 "구역별 반응 확산" 지표라 구역이 1개면 확산 자체를 볼 수 없다.

### 권장 세팅 (① 맵설정)
1. **경보 발생원 3개** — 배치도의 대피시작점 A·B·C (IDR 의 분자 D 가 여기서 나온다)
2. **구역을 방 단위로** — 배치도의 방 1~12 (지금은 층 전체 1개)
3. **병목을 문 앞 대기공간으로** — 복도 폭 × 2~3m ≈ 6~10 m² (지금은 문짝 스윙 1~2 m²)
