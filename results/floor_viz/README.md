# results/floor_viz — 층 라이브 시각화

`tools/floor_live_viz.py` 로 뽑은 **좌: 도면(줌) / 우: 카메라 그리드 / 하: 4대지표** mp4.

```bash
python tools/floor_live_viz.py --floor default --cams cam01 cam02 cam03 \
       --sec 180 --out results/floor_viz/17F_cam01-03_3min.mp4
```

`--fps` 는 **출력 영상 fps**(기본 24 = 원본), `--state-hz` 는 지표·추적점 갱신
주기(기본 5 = analyze_fps)다. 시각화가 목적이라 **우측 카메라는 원본만큼 부드럽게**
흐르고, 좌측 도면·지표는 분석 주기로 갱신되어 그 사이에는 유지된다.
분석이 5fps 라 지표를 그보다 빨리 받아도 같은 값이므로 낭비다.

## 화면 보는 법

| 위치 | 내용 |
|---|---|
| 좌 | 17F 도면을 **지정 카메라 구역으로 줌**. 구역·병목·경로·출구 + 추적점(카메라별 색) + 2초 궤적 + 객체별 속도(m/s) |
| 우 | cam01·cam02·cam03 RTSP 원본 그리드. 테두리 색 = 도면 추적점 색, 좌상단에 그 카메라의 현재 인원 |
| 하 | **4대 지표**(SEI·EPFI·CBS·IDR) + 실시간(추적 인원·평균 속도·출구 통과·경과) |

## 지표는 직접 계산하지 않는다

서버의 `/api/map/state` 를 그대로 받아 그린다. 따로 계산하면 웹 UI 화면과
영상이 어긋나 근거로 못 쓴다 — **웹에서 보이는 값과 같은 값**이다.

4대 지표는 경보 세션이 있어야 산출되므로, 도구가 녹화 시작과 함께 세션을
시작하고 끝나면 종료한다(`--no-session` 으로 끌 수 있다. 그 경우 SEI·EPFI·CBS 는
빈칸이고 속도·인원만 나온다).

출구 통과는 서버 누적치라 **녹화 시작 시점을 빼서 구간 증분**으로 보여준다.

## 층 도면은 floors[] 에서 뽑는다

`/api/site` 는 **사이트 최상위** map·zones·exits 를 돌려준다(legacy 전역값).
층의 실제 도면·공간요소는 `floors[]` 안에 있다 — 최상위를 쓰면 엉뚱한 층 도면
위에 다른 층 구역을 그리게 된다(실제로 17F 에 AI hub 1층 도면이 깔린 적 있다).

|---|---|---|---|---|
| `17F_cam01-03_3min.mp4` | 17F(default) | cam01·cam02·cam03 | 180s · 1620x852 @**24fps** · H.264 13MB | SEI 97.1 · EPFI 95.0 · CBS 11.32 · IDR 0/3 |

정상이다(피난 개시 조건을 만족하는 구역이 없음).

## 발표용 판 — `tools/floor_demo_viz.py`

같은 소스(라이브 RTSP + `/api/map/state`)를 **demo 영상과 같은 화면 규칙**으로 그린다.
`floor_live_viz.py` 는 진단용이라 구역·경로·라벨을 다 얹는데, 발표에서는 그게 잡음이다.

```bash
python tools/floor_demo_viz.py --floor default --cams cam01 cam02 cam03 \
       --sec 180 --intro 4 --title "17F 실시간 운영 화면" \
       --out results/floor_viz/17F_cam01-03_3min_demo.mp4
```

| | 진단판(`floor_live_viz`) | 발표판(`floor_demo_viz`) |
|---|---|---|
| 우측 | 카메라 수에 맞춘 가변 그리드 | **2×2 고정** — 셋이면 넷째 칸은 요약 카드(층·재실·평균속도) |
| 도면 | 구역·병목·경로·출구 + 라벨 | **병목·출입구만 도형으로** + 우상단 범례 |
| 피난경로 | 항상 그림 | **안 그림** (`--routes` 로 켬) |
| CCTV 커버리지 | — | **안 그림** (`--coverage` 로 켬) |
| 하단 | `SEI 출구효율` 식 약어 | **한글이 먼저**(반응 신속도·경로 준수도·대피 혼잡도·출구 활용도), 넷 다 같은 크기 |
| 시계 | `경과 120s / 180s` | `0:40 분:초` 크게 + 카운팅(재실·출구 통과) 별도 패널 |

17F 는 상시 사무 공간이라 "각자 이 길로 가야 한다" 는 그림이 맞지 않는다 — 그래서
피난경로·커버리지가 기본 꺼짐이다.

### 경과 시계는 **영상 위치**로 그린다

세션의 `elapsed_sec`(벽시계)를 그대로 쓰면, 렌더가 조금만 밀려도 시계만 앞서가
영상이 빨리 감긴 것처럼 보인다. 실제로 그랬다 — 영상 2:30 지점에 시계가 4:12 였다.

원인은 `session_viz.put` 이 **호출마다 이미지를 통째로 PIL 로 왕복**한다는 것이다.
1920×259 하단 바에 25번 부르면 프레임당 136ms 로, 24fps 예산(41ms)의 3.3배다.
`puts()`(왕복 1회)로 바꾸고 바를 1초 단위로만 다시 그려 **지연 +0.0s** 가 됐다.
로그의 `지연 ±Ns` 가 그 실측치다 — 0 에서 벌어지면 화면 시간이 어긋나고 있다는 뜻.

### 2D 맵이 끊겼던 이유 — 보간 없음 + 폴링 어긋남

첫 판은 점이 뚝뚝 끊겼다. 원인 둘이다.

**① 5Hz 상태를 24fps 에 그대로 홀드했다.** 분석이 5fps 라 좌표는 초당 5번만
바뀌는데, 그걸 그대로 들고 있으면 프레임 24개 중 5개만 움직인다. 실측으로도
그랬다 — 맵 영역이 바뀐 프레임이 **23%**(5/24 = 21%) 였다. `demo_viz.interp_objects`
와 웹 UI(`currentInterp`)는 앞뒤 관측을 gid 로 짝지어 사이를 메운다. 그걸 안 했다.

**② 5Hz 폴링이 서버 스냅샷 주기와 어긋났다.** `/api/map/state` 를 0.2초마다
부르면 같은 스냅샷을 두 번 받거나(실측 2/29회) 하나를 건너뛴다. 스냅샷 간격도
0.157~0.415s 로 흔들려(평균 0.215s), 균등 간격으로 홀드하면 튀는 구간이 생긴다.

고친 방법:

- 폴링 대신 **SSE(`/api/map/stream`)** 로 받는다 — 웹 UI 와 같은 경로다.
  스냅샷을 자기 `ts` 와 함께 쌓아 둔다(`StateFeed`).
- 그리는 시각을 **한 주기 뒤로 문다**(`--lag`, 기본 0.30s). 보간하려면 "다음 것"이
  있어야 하는데 라이브에는 미래가 없다. 0.3초 지연은 녹화물에서 문제가 안 된다.
- 매 프레임 앞뒤 스냅샷을 **gid 로 짝지어 선형 보간**한다. 좌표를 지어내는 게
  아니라 표출만 매끄럽게 하는 것이고, **지표는 서버가 낸 값 그대로** 쓴다.
- 자취도 스냅샷이 아니라 **그려진 위치**를 프레임마다 쌓는다(스냅샷을 쌓으면
  자취까지 각진다).

결과: 맵이 움직인 프레임 **23% → 62%**(사람이 안 움직이는 구간 제외하면 전부).

### 그래도 끊겨서 — 원인 세 개를 더 찾았다

보간을 넣고도 여전히 덜컹거렸다. 재 보니 셋이 겹쳐 있었다.

**① 보간이 사실상 안 걸리고 있었다 (결정적).** 스냅샷의 `ts` 는 **벽시계보다
0.168s(최대 0.316s) 뒤**다(추론·집계 지연). 그런데 `--lag` 을 0.3s 로 두면 그리려는
시각이 이미 받은 스냅샷들보다 앞서서, 보간 대신 "마지막 걸 쥐는" 분기로 빠진다.
실측 보간 성립률:

| lag | 0.3s | 0.5s | 0.7s | 0.9s |
|---|---|---|---|---|
| 보간 성립 | **6.7%** | 88.3% | **95.0%** | 93.3% |

기본값을 **0.7s** 로 올렸다. 도구가 끝날 때 `보간 성립 NN%` 를 찍으니, 낮게 나오면
`--lag` 을 키우면 된다. (0.9s 이상은 버퍼 길이에 걸려 되레 떨어진다.)

**② 정수 픽셀 반올림.** 화면 1px = 3.8cm 라, 1.2 m/s 로 걷는 사람이 **프레임당
1.3px** 움직인다. 정수로 반올림하면 그 이동이 계단으로 양자화돼 어떤 프레임은
1px 튀고 어떤 프레임은 그대로다. cv2 의 `shift`(고정소수점)로 **1/16px 단위**로
그린다 — `shift` 는 중심과 반지름에 함께 적용되므로 반지름도 같이 올려야 한다.

**③ 선형 보간의 각진 이음매.** 스냅샷마다(0.2초) 진행 방향이 꺾인다. 앞 1개·뒤
2개로 접선을 잡는 **Catmull-Rom**(비균등 시간 Hermite)으로 바꿨다. 관측점을 정확히
지나므로 **원 관측과의 오차는 0.00px** 이다.

측정(같은 스냅샷 열에 대해, 프레임 간 이동량의 변동계수 — 낮을수록 매끄럽다):

| 방식 | 변동계수 | 원 관측과 벌어짐 |
|---|---|---|
| ① 홀드 | 3.142 (정지 프레임 85%) | 0.00px |
| ② 선형 + 정수픽셀 | 1.103 (22%) | 0.00px |
| ③ **CR + 서브픽셀** | **0.471** (11%) | **0.00px** |
| ④ 2차 회귀 ±0.7s | 0.329 | 중앙 0.88px · **최대 18.9px(0.72m)** |

④ 가 수치는 제일 좋지만 관측을 0.7m 까지 벗어난다 — 급선회를 뭉갠 것이라 안 쓴다.
원 관측(5Hz) 자체의 속도 변동계수가 0.376 이라, ③ 의 0.471 은 **데이터 자체의
흔들림에 거의 닿은 값**이다. 더 매끄럽게 하려면 관측을 왜곡해야 한다.

참고로 **트랙 끊김은 0회**였다(스냅샷 120개·트랙 34개 구간 854개에서 결손 없음).
깜빡임은 트래커 탓이 아니라 전부 렌더링 탓이었다.

### 점이 "점핑" 하는 진짜 이유 — 원본이 15초 루프다

트래커 문제가 아니다. **17F RTSP 소스가 15.04초짜리 클립을 무한 루프**한다.

```bash
# /home/pia/rtsp-stream/stream-1_v1.sh
exec ffmpeg -re -stream_loop -1 -i "/home/pia/rtsp-stream/1_v1.mp4" ...
```

15초마다 영상이 처음으로 되감기면서 화면 속 사람이 전부 순간이동한다. 실측:

| 인원 0 인 구간 | 2.6~4.8s | 17.8~19.8s | 32.8~34.8s | 47.8~50.4s | 62.8~65.2s |
|---|---|---|---|---|---|
| 간격 | — | 15.2s | 15.0s | 15.0s | 15.0s |

평균 **15.05초** — 클립 길이 15.04초와 일치한다. 매 바퀴 **2.0~2.6초 동안 아무도
안 잡히고**, 그 뒤 전원이 클립 시작 위치에 다시 나타난다. 트랙 시작 시각도 15초
주기로 뭉친다(2.0~7.0 → 16.8~22.2 → 31.8~37.8 → 46.8~52.8).

**→ 30초 영상에는 이 되감기가 1회 들어간다.** 1분이면 3회다. 더 긴 17F 원본은
없다(`/home/pia/rtsp-stream/` 에 15초짜리 셋뿐).

`--sync-loop` 는 되감기 순간을 기다렸다 본편을 시작해 **한 바퀴 안에** 담는다
(`--sec 14` 이하). 대기는 **인트로 뒤**에 해야 한다 — 앞에서 기다리면 인트로
길이만큼 바퀴를 까먹어 되감기가 본편 끝자락에 걸린다(첫 시도에서 t≈12s 에 들어왔다).

### ID 는 유지된다

같은 구간에서 카메라별 동시 인원:

| | 기대(영상 속 인원) | 상위10% | 최대 |
|---|---|---|---|
| cam01 | 3 | **3** | 4 |
| cam02 | 6 | **6** | 7 |
| cam03 | 5 | **5** | 6 |

상위10% 가 기대치와 정확히 같다. 최대가 +1 인 건 한 사람의 id 가 바뀌는 찰나
옛 id 와 새 id 가 0.2~0.4초 겹치기 때문이고, 그 뒤 옛 id 는 사라진다. 39초 동안
**결손(트랙이 중간에 끊겼다 이어짐)은 0회**였다(스냅샷 120개·트랙 34개·이음 854개).

남은 자잘한 튐 둘:

- **같은 gid 안에서 3 m/s 초과 이동 22건/39초** — 최대 1.76m / 0.17s. 발끝점
  투영 지터와 간헐 id 스위치다. 사람이 겹쳐 지나갈 때 주로 난다.
- **스냅샷이 10ms 간격으로 중복 발행 3/229건** — 그 순간 속도가 30~48 m/s 로
  계산돼 "평균 속도" 표시가 튄다. 표출만의 문제이고 4대 지표에는 영향이 없다
  (지표는 구간 적분·판정이라 한 샘플로 흔들리지 않는다). 엔진 쪽 별건.

### 점을 "복원 궤적" 으로 그리기 — `tools/demo_loopfold.py`

**루프라서 매 바퀴가 같은 내용**이라는 걸 근거로 쓴다. 여러 바퀴의 관측을
위상(`t mod 15.041667`)으로 포개면 한 사람을 여러 번 본 셈이 되고, 한 바퀴에서
검출이 빠진 구간도 다른 바퀴에는 있으니 구멍이 메워진다.

```bash
python tools/demo_loopfold.py --sec 95 --out results/floor_viz/_loop/default.json
python tools/floor_demo_viz.py ... --loop-track results/floor_viz/_loop/default.json
```

|---|---|---|---|
| 영상 속 실제 인원 | 3 | 6 | 5 |
| 원 gid (95초 = 6.3바퀴) | 24 | 50 | 37 |
| **복원된 사람** | **3** | **6** | **5** |
| 위상 상관 | 0.922 | 0.963 | 0.977 |

거르는 규칙 둘:

- **한 바퀴에만 나온 조각은 버린다** — 진짜 사람은 매 바퀴 나온다(복원된 14명은
  전원 6~7바퀴 지지). 반사·의자 오검출과 id 분절 찌꺼기가 여기서 걸러진다.
- **순이동(시작→끝 직선거리)이 1.5m 미만이면 버린다** — "한자리에 맴도는" 조각이다.
  경로 길이로 거르면 지터가 쌓여 통과한다(실측: 3.3초 동안 경로 3.8m 인데 시작·끝은
  0.26m 차이). `--min-net-m`.

같은 위상 칸(0.1초)에 모인 점들은 평균 내므로 발끝점 지터가 √N 로 줄어든다.

**위상 기준점은 관측과 맞춰 미세 조정한다.** 되감기(빈 구간) 시작만으로 잡으면
0.2~0.5초 어긋나고(빈 구간의 시작 자체가 "마지막 사람이 사라진 시각" 이라 검출
지연이 섞인다), 그대로 두면 등·퇴장 순간에 화면 인원수가 영상과 안 맞는다.
복원 인원수 곡선과 실제 관측 인원수 곡선의 상관이 최대가 되는 쪽으로 민다
— 상관 0.880/0.854/0.960 → **0.922/0.963/0.977**.

결과: 한 바퀴 동안 인원 표시가 바뀌는 건 **26회 / 361프레임** 이고, 그 26회는
14명의 등장 14회 + 퇴장 14회다(같은 프레임에 겹친 둘 제외). **깜빡임이 0 이다.**

`--loop-track` 을 안 주면 예전처럼 원 관측을 그린다(`14s_noloop` 판이 그쪽).

**지표는 건드리지 않는다.** 4대 지표는 서버가 원 관측으로 낸 값 그대로다 —
그림과 수치가 어긋나면 그게 더 나쁜 거짓말이라, 복원한 건 그림에만 쓴다.
`tools/demo_tracks.py`(demo 영상의 이상적 궤적)와 같은 성격이고, 다만 사람이
손으로 그리는 대신 **반복 관측이 근거**다. 루프가 아닌 실제 현장 영상에는 못 쓴다.

### 이어붙이기만으로는 부족했다 — `tools/demo_stitch.py`

복원 궤적에 가기 전에, 끊긴 gid 를 사람 자리(pid)에 꽂는 이어붙이기를 먼저 했다.
흔한 실패가 끊김이 아니라 **겹침**(한 사람에게 옛 id·새 id 가 0.2~0.4초 같이
붙었다 옛 것이 죽는다)이라, 죽은 자리 옆에서 직전에 태어난 자리를 찾아 되붙이는
패스까지 넣었다. 그래도 89초 기준 cam02 47 → 41(이상 35)에 그쳤다. 라이브라
**미래를 못 봐서** 한계가 분명했고, 그래서 루프를 포개는 쪽으로 갔다. 모듈은
루프가 아닌 소스에 쓸 수 있게 남겨 둔다.
