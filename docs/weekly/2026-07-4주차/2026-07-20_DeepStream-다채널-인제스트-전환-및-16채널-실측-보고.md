## 1. 목적

이번 작업의 목적은 다음과 같다. 지난 주 구축한 멀티카메라 2D맵 시스템의 기존 인제스트
경로(카메라별 ffmpeg-NVDEC 디코드 → 풀해상도 BGR CPU 복사 → 호스트 단일 스레드 직렬 TRT
추론)가 **4채널@5fps에서 포화**(총 ~21fps)해 16채널 목표(=80fps) 도달이 구조적으로 불가한
상태를 해소. 배경·전제는 다음과 같다.

- 병목은 GPU 하드웨어가 아니라 프레임당 PCIe 복사·전처리·배치 없는 직렬 추론의 호스트 단가
- 목표: 픽셀을 컨테이너 밖으로 내보내지 않는(비식별·리소스 절감) **zero-copy 디코드 + 배치 추론**
- 기존 경로 무손상 병행 — 스위치를 안 건드리면 100% 기존 동작(안전한 롤백 경로 확보)

## 2. 이번 주 성과

이번 주 핵심 성과는 DeepStream 기반 인제스트로의 전면 전환과 그 정량 검증(P0~P11, 총 24커밋)
이다. 단계별 진행은 다음과 같다.

| 단계 | 내용 |
|------|------|
| P0·P1 | 라이브 RTSP 한계 처리량 스윕 도구 + 기존 ffmpeg 경로 베이스라인 실측(4ch 한계·~21fps 포화) |
| P2~P4 | DeepStream zero-copy 인제스트 + 배치 추론 워커 구현(`ingest_ds/worker.py`) · e2e 출력 유사도 정량 검증 |
| P5~P7 | 멀티 GPU 워커 런처(`DsIngestManager`) · 12~64ch 한계 스윕 · `INGEST_BACKEND` 스위치 통합 + ADR |
| P8·P9 | `WORKERS_PER_GPU` 워커 분할(GPU당 N프로세스) · 트래킹 죽음의 나선 차단 · 5fps 최대 16ch 재확정 |
| P10 | 운영 webui(:8900) DS 모드 E2E 통합검증 7항목 전부 통과 |
| P11 | b32 dynamic 엔진 재스윕 → 이득 없음 확정(b16 유지) · 병목 최종 진단 |

### 2-1. 처리량 실측 — 4ch → 16ch (약 4배)

핵심 성과는 채널당 5fps를 유지하는 최대 채널 수를 4ch에서 16ch로, 총 처리량 포화점을
~21fps에서 ~79fps로 끌어올린 것(1GPU 기준 실측)이다.

| 경로 | 5fps 유지 한계 | 총 처리량 정점 | 비고 |
|------|:---:|:---:|------|
| 기존 ffmpeg | 4ch | ~21fps 포화 | 6ch부터 채널당 fps 미달 |
| **DeepStream** | **16ch**(4.93fps/ch) | **78.7fps** | 12ch 드랍 0, 64ch까지 OOM·에러 0건 |

- 이후 저하 곡선: 24ch ≈ 3.2fps → 32ch ≈ 2.4fps → 48ch ≈ 1.3fps → 64ch ≈ 0.8fps로 완만.
- oldest-drop 큐로 지연 미폭주(lag p95 0.5~0.9s) — 포화 시 "밀린 영상"이 아니라 "듬성한 최신 영상"으로 저하.
- 1GPU 병목의 실체 = 프레임당 직렬 혼합 단가 ~12.6ms(검출 커널 4.9 + 트래킹 CPU·ReID·동기화 ~7.7).

### 2-2. 출력 동등성 검증

전환의 전제 조건인 산출물 동등성은 결정적 입력(sample1, 646프레임 1:1 정렬)으로 정량 확인.

- 검출 bbox 매칭률 **99.44%**(IoU mean 0.976), 트랙 bbox 매칭률 **98.95%**(IoU 0.975)
- 트랙 수 99 vs 96·수명 분포 동등 — **채택 가능 판정**
- ReID cosine 0.956(기준 0.98 미달)은 디코더+색변환 픽셀 차이로 원인 특정, 타인 간 cosine 0.226 대비 판별 마진 충분 → 트랙 산출 영향 없음

### 2-3. UI 개선 — 카메라별 검출 신뢰도·유효 ROI

부수 개선으로 카메라별 검출 신뢰도(`min_conf`) 오버라이드와 유효 ROI 정합 편집을 운영 UI에 추가.

- 카메라별 `min_conf` 오버라이드(전역 상속, 값 지정 시 우선) — 저신뢰 오탐(예: 의자) 억제
- 화면2 목록 인라인 편집 + `valid_roi` 다각형 정합 검증, 잘못된 값 저장 시 422 응답
- 매핑 화면 각 모드가 자기 데이터만 표시 — 커버리지를 실제 탐지영역과 일치(볼록껍질 혼동 제거)

### 2-4. 버그 수정 — TRT 비블로킹 스트림 레이스

운영(DS 모드 라이브)에서 상시 발생하던 "깨진 프레임" 검출 폭풍의 근본 원인 규명·수정.

- 원인: `torch.cuda.Stream()`(non-blocking)이 입력 생성 커널(default 스트림) 완료를 대기하지 않아, GPU가 바쁠 때 TRT가 복사 미완료 메모리를 읽어 프레임당 3,000~7,000개 오검출 발생
- 수정: `execute_async_v3` 직전 `self.stream.wait_stream(torch.cuda.current_stream())` 1줄(검출·ReID 공용) — 정상 프레임 출력 불변(실행 순서만 강제)
- 효과: 깨진 프레임 경고 상시 → **0건**, 실효 분석 fps 4.0~4.8 → **전 채널 5.0 고정**, 맵 순간이동 0건
- 워커 분할 시 트래킹 죽음의 나선(깨진 프레임 → 트랙 폭증 → 연관비용 폭주)도 가드·회로차단기로 차단

## 4. 관찰 및 한계

강점과 현재 한계, 다음 단계는 다음과 같다.

**강점**
- 기존 경로 대비 4배 처리량 + 산출물 동등성 확보 — 안전한 병행·롤백 구조(`INGEST_BACKEND`)
- 64ch까지 OOM·디코드 에러 0건, oldest-drop으로 지연 미폭주 — 과부하에서도 최신성 유지

**현재 한계**
- 1GPU 5fps 한계는 16ch로 확정 — 150채널은 GPU 증설(=워커 증설)이 전제, 전용 GPU 확보(공유 시 추론 붕괴)가 선결
- b32 배치 확대는 이득 없음(기각) — 다음 레버는 트래킹 CPU 절감·검출 해상도 축소·양자화(미착수)
- 24h 연속 운영 안정성 미측정 — 장시간 부하에서 VRAM·워커 생존 검증 필요
- hot add/remove가 워커 컨테이너 재시작(~50초 공백)을 동반 — DS 동적 소스 add/remove는 후속

**다음 단계**
1. 24h 연속 운영 안정성 측정(6.2.4) — 장시간 부하 VRAM·워커 생존·재접속 내성
2. 전용 GPU 2장 확보 시 다GPU 실측(4.7.3) — 24~32ch@5fps 검증, 외삽 검증
3. 성능 튜닝 다음 레버(6.3.2) — 검출 입력 해상도 축소·트래킹 연관 수식 경량화 실측
4. 현장 실증(6.1.x) 선결 스펙(도면·카메라 설치·임계값) 확정 협의

## 5. 부록 — 재현 명령

```bash
# DeepStream 경로로 전환 (운영)
INGEST_BACKEND=deepstream GPU_DEVICES=1 pm2 restart macs-system --update-env

# 롤백 (기본값이 ffmpeg이므로 명시 재기동)
INGEST_BACKEND=ffmpeg pm2 restart macs-system --update-env

# 한계 처리량 스윕 재현
conda run -n boosttrack python docs/reports/bench/bench_ds_limit.py \
    --tag gpu1 --gpu 1 --channels 12,16,24,32,48,64 --secs 60 --warmup 30
```
