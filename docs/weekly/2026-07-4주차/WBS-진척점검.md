## 2. 이번 주 변동 (v7 → v8)

### 2-0. 🔻 목표 재조정 — 최종 채널 스케일 150채널 → 50~60채널

- **무엇**: 이번 주(2026-07-4주차) 프로젝트 **최종 스케일 목표를 150채널 → 50~60채널로 하향**.
- **사유**: 실증 대상 규모 재산정.
- **GPU 산정(현실화)**: DeepStream zero-copy 전환으로 **1GPU 16ch@5fps** 실측 → 50~60ch@5fps는
  **GPU 3~4장**이면 도달 가능(50/16≈3.1, 60/16≈3.75). 구 목표(150ch@5fps, ~8장) 대비 현실적.
- **영향**:
  - 4.7.3(스케일 달성)·4.7.4(스케일 성능 검증)의 목표치가 50~60ch로 재정의 — 다GPU(3~4장) 실측이 남은 핵심.
  - **6.3.2 성능 튜닝의 긴급도 하락**: 3~4 GPU면 경량화 없이도 목표 도달 가능 → 튜닝은 "필수 경로"가
    아니라 **GPU 대수 절감·여유 확보용 선택지**로 격하(아래 §4 참조).
  - 중간 단계 15ch는 유지, 아키텍처(현 경량 스택 Postgres/Redis/DeepStream 단일서버)로 충분 —
    Kafka/Triton/ClickHouse 대규모 백본은 50~60ch 초과 확장 시 옵션(ADR 01 갱신).
- 반영 문서: 요구사항·ADR 01·WBS 02·변경이력 v8·bench README·WBS v8 xlsx(4.7.3 D열).

## 4. 리스크 / 수정 필요

- **다채널 스케일 병목 재진단(3차)**: 진단이 `GIL`(§3) → `GPU 커널`(§7.3) → **프레임당 직렬
  혼합 단가 ~12.6ms**(§9.4, 검출 커널 4.9 + 트래킹 CPU·ReID·동기화 ~7.7)로 최종 정리됨.
  1GPU 16ch@5fps는 확정 상한, 1fps 도달점은 ~54ch. **최종 목표 50~60ch@5fps는 GPU 3~4장(=워커 증설)이 전제**이고
  전용 GPU 확보(공유 시 추론 붕괴)가 선결 조건 — `docs/reports/DeepStream-한계처리량-실측.md §5·§9.4`.
- **6.3.2 성능 튜닝이 여전히 진행중인 이유**(한계처리량 보고서 §9.5 최종 진단 기준): 남은 레버가
  아직 미실측/미착수라 종결 못 함 — ① 트래킹 CPU 단가 절감(프레임당 ~7ms, BoostTrack 연관수식
  벡터화/네이티브화·검출수 상한) **미착수**, ② 검출 입력 해상도 축소(896×1600→736×1280,
  정확도 트레이드오프) **미실측**, ③ appsink 콜백 경량화(전처리·synchronize를 추론스레드로 이동)
  **미실측**, ④ FP8/INT8 양자화 **미실측**. (b32 배치 확대는 실측 기각 — P11.)
- **단, 50~60ch 목표 하향으로 6.3.2 긴급도 하락**: GPU 3~4장이면 경량화 없이도 50~60ch@5fps
  도달 가능하므로, 위 튜닝은 "천장을 올려야만 하는 필수 경로"가 아니라 **GPU 대수 절감·여유
  확보용 선택지**로 격하. 우선순위는 ①>②>③>④(효과/공수 비).
- **운영 안정성 버그 수정 반영**: TRT 비블로킹 스트림 레이스(`9b2ba76`)로 인한 "깨진 프레임"
  검출 폭풍, 워커 분할 시 트래킹 죽음의 나선(`02bdc58`) 각각 수정·재검증 완료. 24h 연속 운영
  안정성(6.2.4)은 여전히 미측정 — 후속 필요.
- **min_conf/valid_roi 카메라 설정 UI**(`925bb38`·`9217348`·`70ca59d`·`d624faf`): 카메라별 검출
  신뢰도 오버라이드·유효 ROI 정합·422 검증 구현. 다만 5.1.4(관리자 UI)의 전 범위(사용자 관리·
  시스템 로그 조회)에는 미달하고 기존 진행중 항목(4.4.x·5.1.x)의 보강 성격이라 **별도 상태 변경
  없이 유지**(과대평가 금지 원칙) — 근거는 남김.
