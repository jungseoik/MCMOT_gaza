# ADR 09 — 리허설 패키지 구조 (폴더 = 진실의 원천)

> 상태: **구현 완료** (2026-08-27) — P1~P5 + §7 층 빙의 모드 전환, 통합 검증 포함

## 0. 배경 — 현 구조의 문제

ADR 08(vsource)은 송출 동기화만 풀었다. 리허설 하나를 구성하는 정보가 세 곳에 흩어진다:

| 정보 | 현재 위치 | 문제 |
|---|---|---|
| 영상 | `media/vsource/…` (또는 `field/encoded/`) | 폴더만 옮겨선 재현 불가 |
| 시나리오 정의 | `data/scenarios/<id>.json` | 영상과 따로 논다 |
| 카메라·매핑·도면 | `data/sites/default/` | **운영 설정과 뒤섞임** — 리허설이 사이트를 오염 |

기존 `drill-16f`는 16F 실훈련 영상을 시간 정렬한 **mock**이었고(등록 카메라 6대를 재사용),
신규 리허설(CJ 리허설 14시나리오, 이후 AI Hub 등)의 기준 구조가 아니다.

## 1. 결정 (2026-08-27 인터뷰로 확정)

1. **패키지 범위 = 전부.** 도면까지 폴더에 포함한 완전 자립 패키지. 폴더만 있으면
   어떤 서버에서도 리허설 재현 가능. 사이트(`data/sites/`)와 완전 분리.
2. **매핑은 UI에서 찍고 폴더로 저장.** 최초 1회 화면↔도면 점 찍기는 지금 UI를 쓰되,
   결과가 사이트가 아니라 패키지 `rehearsal.json`에 저장된다. 이후는 불러오기만.
3. **선택 시 자동 반영 + 종료 시 복원.** 리허설 시작 시 패키지의 층·카메라·매핑을
   런타임에 자동 반영하고(사이트 스냅샷 백업), 리허설 종료 시 원래 상태로 복원.
   ② 탭 수작업 없음.
4. **사전 검증은 준비 CLI + UI는 검사만.** 폴더 배치 전 준비 도구가
   검사(h264·B-frame·길이·시작점 정렬)→부적합 시 재인코딩→리포트를 수행.
   UI는 불러올 때 재검사해 부적합이면 사유 표시 + 송출 차단.

## 2. 패키지 규격

```
media/vsource/<site>/<set>/          예: cj/rehearsal/ · aihub/rehearsal/
  rehearsal.json      ★ 매니페스트 — 진실의 원천 (git 추적)
  README.md           출처·구성 표 (git 추적)
  floorplan/          도면 png (+ 원본 dwg/dxf 명 기록) (git 추적)
  scenario_NN/        송출 대상 camX.mp4 만 (git 제외, HF 보관)
  grid_preview/       몽타주 미리보기 — 송출 금지 (git 제외)
```

git 규칙: 영상만 제외(전역 `*.mp4`), 매니페스트·매핑·도면은 손작업 산출물이므로 **추적**.

### rehearsal.json (schema 1)

```jsonc
{
  "schema": 1,
  "id": "cj-rehearsal",            // <site>-<set>
  "name": "CJ제일제당센터 리허설",
  "rtsp_prefix": "cj",             // path = <prefix>_<cam> → rtsp://…:8554/cj_cam8
  "floors":  [ {"id","name","image","m_per_px","source"} ],
  "cameras": [ {"cam","path","name","floor","analyze_fps","mapping"} ],
                                    // mapping: 사이트 카메라와 동일 스키마
                                    // (cctv_pts·map_pts·H) — UI가 찍어서 여기 저장
  "scenarios":[ {"id","name","cycle_sec","streams":[{"cam","file","duration_sec"}]} ],
  "prep": { /* 준비 CLI가 기록: 검사 시각·항목별 판정 */ }
}
```

- 같은 cam 번호 = 전 시나리오에서 같은 RTSP 경로 → 매핑은 **cam당 1회**.
- `cycle_sec: 0` = 자동(최장 영상 + 2s), ADR 08 그대로.

## 3. 흐름

```
[준비 — 폴더 배치 전]
  tools 준비 CLI: 검사 → (부적합) 재인코딩 → 시작점·길이 리포트 → rehearsal.json prep 기록

[리허설 탭]
  ① 패키지 목록 = media/vsource/*/*/rehearsal.json 스캔 (+경로 직접 입력 허용)
  ② 패키지 선택 → 시나리오 목록·검증상태·매핑 완성도 표시
  ③ 매핑 없는 카메라 → 매핑 도구(기존 UI 재사용) → 결과를 rehearsal.json에 저장
  ④ [시작] → 사이트 스냅샷 백업 → 패키지 층·카메라 자동 반영 → vsource 동기 송출
  ⑤ 세션·4대 지표 (기존과 동일 — 본체 무변경 원칙 유지)
  ⑥ [종료] → 송출 정지 → 사이트 원상 복원
```

## 6. 구현 노트 (2026-08-27)

- **스냅샷/복원 대신 얹기** — overlay.py 와 같은 원칙. `RT.cameras()` 가 활성
  시나리오의 가상 카메라(`rh_cam8`…)를, `reload_engine()` 이 가상 층(`rh_f10`)을
  읽기 전용 뷰로 합친다. 사이트 파일은 한 번도 안 쓰므로 "복원"은 얹기 중단이 전부.
- **시나리오 단위 주입** — 패키지 카메라 전부(14대)가 아니라 활성 시나리오의
  부분집합(4~5대)만 ingest 에 넣는다. 나머지는 송출이 없어 영원히 reconnecting
  으로 DS 슬롯(16ch 한계)만 잠식한다(실측으로 확인 후 수정).
- **벌크 제거 추가** — DS `remove_camera` 는 대당 슬롯 재시작이라 14대 해제에
  ~2분(실측). `remove_cameras()` (ffmpeg/DS 양쪽)로 슬롯당 1회로 묶음 → 7.9s.
- **default 층 오염 차단** — 가상 층은 engines 에 있어 `require_floor` 를 통과
  하는데, 사이트 쓰기 경로의 `get_floor()` 폴백이 **default 층을 조용히 덮는다**.
  `require_floor` 가 `rh_*` 층 쓰기를 409 로 거부.
- **서버 재시작 재부착** — vsource 퍼블리셔는 detach 라 살아남는다. startup 이
  상태파일의 `pkg:` 시나리오를 보고 가상 카메라·층을 다시 얹는다.
  (관찰: pm2 restart 는 detach 퍼블리셔까지 죽이는 경우가 있다 — pm2 의 tree-kill 이
  PPID 기준이라 세션 분리로 못 피함. uvicorn 자체 재시작과 달리 리허설이 끊긴다.)
- **프론트 갱신 버그 수정(같은 날)** — ①리허설 시작/종료 시 `renderList()` 만 다시
  불러 stale 목록이 그려짐(rh 카메라 안 보임) → 상태 변화 때 `/api/cameras`·
  `/api/floors` 재조회 후 렌더. ②층 셀렉터·층 이름이 `site.floors` 만 봐서 가상 층
  미표시 → `App.floors`(백엔드 요약, rh 포함) 우선. ③`selFloorObj()` 가 가상 층을
  못 찾고 **현재 층으로 폴백해 엉뚱한 도면 위에 매핑**하게 되던 것 → App.floors
  폴백 추가(도면 없으면 빈 캔버스). ④rh 카메라의 매핑 층 select 는 패키지 층으로
  잠금 + 서버도 rh_ 접두 아닌 층 id 를 무시(매니페스트 오염 방지). ⑤rh 행의
  삭제·활성·conf 편집 UI 제거(서버 409와 정합).
- **E2E 테스트로 잡은 것(같은 날, Playwright)** — ①standby 채널 행 위치 라벨이 "종료"로
  표시(대기엔 시간 개념 없음) ②⑤→② 이동 시 선택 카메라 행이 스크롤 밖 ③매핑 저장 후 ⑤
  목록의 매핑 수가 낡음(시나리오 캐시) → own_mapped 변화 감지 시 재조회.
- **UX 정리** — ⑤: 사실은 격자 6칸(채널·영상·사이클·층·매핑·사전검증), 경고는 종류별
  한 줄로 집계(채널마다 반복 X), 매핑 배지 단일화(필요/✓/✓상속/낡음), 버튼 주1·보조2.
  ②: [＋ 카메라 추가]를 목록 **맨 위 접이식**으로(17대면 폼이 스크롤 끝에 묻힘),
  카메라 행은 2줄(conf 편집은 선택한 행에만 펼침).
- **한계(다음 과제)** — ① 가상 층은 map 만 있고 출구·구역·경로가 없어 4대 지표가
  제한적(패키지 스키마에 공간요소 추가 필요). ② CJ 10F 도면 미수급 — 수급 전엔
  매핑 자체가 불가. ③ 리허설 층이 낀 세션 녹화의 리플레이는 리허설 종료 후
  층 정보가 사라짐.

## 7. 층은 사이트 것을 빌려 쓴다 — 빙의 모드 (2026-08-27 결정 수정)

결정 ①("도면까지 패키지에")을 실제로 굴려보니 **① 맵설정 플로우를 리허설용으로 또
만들어야** 한다는 뜻이었다 — CAD 편집기 연동, 구역·출구·경로·경보원 지정 전부.
이중 구현·이중 유지보수이고, 가상 층엔 공간요소가 없어 4대 지표가 제한된다(§6 한계 ①).

**수정된 경계**: 도면·구역·출구·경로는 **건물**의 속성 → 사이트(① 맵설정) 정본.
영상·시나리오·카메라·매핑은 **리허설**의 속성 → 패키지 정본.

```
①  맵설정: 층 추가 + 도면(CAD 편집기) + 구역·출구·경로   ← 기존 플로우 그대로, 리허설 무관
⑤  리허설: 패키지 선택 → [붙일 층] = 사이트 층 → 대기 → 매핑(패키지 저장) → 훈련
```

- manifest `cameras[].floor` = **사이트 층 id** (`floor10`). `floors[]` 는 "이 층이
  있어야 한다"는 선언으로 축소 — 없으면 ⑤가 "① 맵설정에서 만들기" 경고.
- 가상 카메라(rh_*)·매핑 패키지 저장·시작/종료 얹기는 그대로. **층만 빌린다.**
- 따라서 ①에서 10F 에 CAD 를 올리고 구역·경로·출입구를 고치면 **리허설 지표에 즉시
  반영**된다 — 카메라가 그 층 엔진으로 라우팅되고 엔진은 사이트 층 공간요소를 쓴다.
- ⑤ [붙일 층] 을 바꾸면 서버가 manifest `floor` 를 되써서 다음부터는 그 층.
  사이트에 없는 층은 404 (오타로 default 층에 조용히 붙는 사고 방지).
- 매핑 저장 시 그 층 도면 크기(`map_wh`)를 스탬프 → 도면이 교체되면 status 가
  `mapping_stale` 로 경고 (사이트 카메라는 자동 해제되지만 패키지 매핑은 못 건드리므로).
- **자립 모드는 남긴다**: `floors[]` 항목에 `image` 가 있으면 예전처럼 가상 층(rh_*).
  두 모드는 `image` 유무 하나로 갈린다. `--floorplan-from-site` 는 자립 모드용.
- 재현성: 층은 사이트 의존이 되지만 사이트는 `tools/seed_version.py` 로 버전·복원된다.
- CJ 리허설: ①에 `floor10`(10F) 층을 만들고 16F 도면(=17F_v2.dwg)을 그대로 올렸다
  (구조 동일). 구역·출구·CAD 는 사용자가 ①에서 이어서 세팅.

## 8. 실측 — "리허설 시작하면 2D 맵에 안 나옴" (2026-08-27)

증상: 대기(정지화면)에선 카메라가 붙는데 [훈련 시작] 후 붙다 안 붙다 하다가 도면에 아무것도
안 찍히고 끝남. 타임라인 실측(2초 간격 fps_in):

```
앞머리(정지화면) 31s : 카메라 떨어짐(12s) → 27s 에 5/5 복귀            ← 정상
본영상 시작(t=41)    : fps_in 4.0 → 2.8 → 1.7 → 0.6 → 0, 트랙 0        ← 여기서 죽음
```

원인: 앞머리는 **baseline** 으로 인코딩되는데 CJ 원본은 **High** 프로파일. concat `-c copy`
로 이어붙이면 SPS/PPS 가 스트림 중간에 바뀌어 DS 디코더가 멈춘다. 현장 영상은 전부
baseline 재인코딩본이라 드러나지 않았고, P1 준비 CLI 가 "B-frame 없으면 High 도 OK" 로
판정한 것이 오판이었다(`check_video.sh` 가 baseline 을 고집한 이유).

조치: 준비 CLI 규칙을 **baseline 필수**로(실패 사유에 근거 명시), 64개 전부 `--encode`
(5개 24s → 전체 약 5분, 파일 크기 50→20MB). 재실측: 본영상 구간 내내 5fps 유지, 10F 도면에
객체 최대 9·5개 카메라 전부 기여. 원본은 `_orig_high_profile/` 에 보관.

부수 교훈: 진단 스크립트가 `MapState.tracks` 를 읽었는데 실제 키는 `objects` — 한동안

## 9. "2D 맵이 끊긴다" — 오프라인 그리드 시각화로 원인 분리 (2026-08-27)

`tools/rehearsal_viz.py` — 영상 파일을 라이브와 같은 조건(5fps 서브샘플·카메라별 BoostTrack·

정합(10F ID 수명 3.5s vs 16F 6.6s). 조치는 매핑 쪽: 각 카메라 **유효 ROI 를 사람이 다니는
바닥 전체로** 그리거나 대응점을 바닥 가장자리까지 추가.

## 10. 오프라인 시각화 vs 웹UI — "웹만 끊기고 싱크가 안 맞는다" (2026-08-27)

같은 시나리오·같은 매핑인데 웹UI 2D 맵만 뚝뚝 끊겨 보였다. 두 경로를 실측으로 갈랐다:

|---|---|---|---|
| 검출·ReID | 기본 `yolox_fastreid` 였음 | `yolo26_clipreid`(① 설정) | **달랐음** → `--profile auto` 로 웹과 동일하게 맞춤 |

## 11. 파일 소스 모드 — 리허설은 RTSP 를 거치지 않는다 (2026-08-28 구현)

§10 뒤에도 웹 2D 맵은 "빨라졌지만 여전히 끊기고, 싱크 맞는 영상인데 점들이 경로를
따라 차례로 나오지 않는다"(사용자). 오프라인 시각화가 원하던 그림을 내는 이유는 남은
차이가 전부 **RTSP 라이브 경로 고유**이기 때문: 카메라별 버퍼·재접속 지연(수백 ms 어긋남),
벽시계 게이트 위상차, 앞머리·재부착이라는 시간축 핵, SSE 지터. 리허설 목적(지표 파이프라인
검증·시연)에 "현장 RTSP 흉내"는 잡음일 뿐이다 → **영상 파일을 직접 읽어 잠금 동기 추론.**

```
rehearsal.json → FileSourceRunner(system/vsource/filesource.py)
   영상 N개를 프레임 k 로 잠금 읽기 → analyze_fps 서브샘플 → FrameItem(ts = t0 + k/fps)
   → AnalyzerThread 큐 (라이브 ffmpeg 백엔드와 같은 스레드; DS 서버엔 파일 모드용 1개 기동)
   → 검출·카메라별 BoostTrack·conf 매칭 → rt._dispatch_tracks → 엔진·세션·지표·SSE  (무변경)
```

- **DS 와 설정 동일**: 프로파일 auto(yolo26+CLIP-ReID), BoostTrack per_instance_ids,
  max_age=fps×2s, ECC off — AnalyzerThread 가 이미 그렇게 돼 있어 재사용으로 보장.
- 패키지 `source` = `file`(기본) | `rtsp`. rtsp 모드는 현장 수집 경로 검증용으로 유지.
- 준비(standby) = 0번 프레임을 정지로 붙잡음(매핑 스냅샷) — 카메라 부착 대기 없음, 즉시.
  시작 = t0 부터 재생, **경보 시각 = t0**(앞머리 0). 끝나면 `done`.
- 가상 카메라(rh_*)는 ingest 에 넣지 않는다(`_rh_ingested` 분리). 상태(fps·스냅샷)는 러너가
  제공 → `rt.cam_states()`/`grab_frame` 이 합친다. ③ 운영뷰는 훈련 시작 시 리허설 층으로 자동 전환.
- 실측(시나리오 02): 준비 3.5s(첫 TRT 로드 포함) · 시작 즉시 · 10F 객체 최대 10 ·
  이동 객체 위치 갱신 3.7회/초 · 27s 후 done · 종료 시 rh 카메라 0.
- 상태 스키마는 controller.status() 와 동형(`source: "file"` 추가) — ⑤ 탭·session.js 무수정 동작.
- 잃는 것: 파일 모드 리허설은 RTSP 수집·DS 디코드를 검증하지 않는다(rtsp 모드로 별도).
- **경보 발생원 사전 검사**(session.js): 이전엔 재생을 시작한 뒤 원점 검사에 걸려 한 사이클을
  허비했다. 이제 ③ [🎬 리허설 훈련 시작] 이 층 자동 전환 → 원점 검사 → 그 다음 재생 시작.
  실측: 10F 에 원점 없이 누르면 재생은 standby 그대로, 층만 10F 로 바뀜.
- 백엔드 세션 E2E(파일 모드): 세션 27s · 트랙 43 · 5카메라 관측 · zone/person/bottleneck/exit
  metrics 산출(SEI 는 출구 통과 0 이라 None). 원점만 ①/③에서 찍으면 4대 지표 전부 나온다.

## 15. 리허설 = 건물 세션 (2026-08-28)

프론트가 "참여 층 1개면 층 세션, 2개 이상이면 건물 훈련"으로 갈라서 단층 리허설이 ④ 리플레이의
**개별 층** 목록으로 흩어졌다. 리허설은 층 수와 무관하게 건물 세션이어야 한다(사용자 지적).

- 리허설 훈련 시작은 항상 `/api/drill/start` — `floors`(시나리오 층 범위)·`label`(🎬 시나리오명)
  ·`rehearsal`(패키지·시나리오·source) 을 함께 보낸다. 범위를 안 주면 파킹된 사이트 카메라 층
  (매핑·활성)이 참여 층으로 섞여 무관한 층에 세션이 열린다.
- 드릴을 **명시 레코드**로: `sessions/_drills/<sid>.json` = {floors, alarm_ts, label, rehearsal}.
  예전엔 "지금 참여 중인 층"으로만 드릴을 추정해 start·stop·롤업·목록·재계산이 전부 그 위에
  있었다 → 리허설 종료로 rh 카메라가 사라지면 그 드릴이 이력에서 **사라지고 재계산도 404**.
  이제 레코드 기준(없으면 예전 방식 폴백).
- ④ 리플레이 기본 모드 = **건물 훈련**(개별 층은 디버그용), 목록에 라벨 배지·층 이름.
- 실측: 시나리오 02 → 건물 세션(floor10) → 종료 → 리허설 종료(rh 0) 후 `/api/drills` 에 라벨과
  함께 남고, `/api/drill/<sid>/replay` 106프레임·EPFI 95.5 재계산.
- SEI 메모: `(1 − ½Σ|E_j/ΣE − C_j/ΣC|)×100`. 출구 1개면 통과가 있을 때 항상 100(정보 없음),
  통과 0 또는 C_j 미설정이면 None. 의미 있는 SEI 는 출구 ≥2.

## 16. 전체 연속 시나리오 (scenario_15_full, 2026-08-28)

카메라 위치 14개는 고정이고 시나리오마다 촬영된 위치가 다르다. 14개를 시간순으로 이어 붙이며
**없는 카메라 구간은 검정 프레임**으로 채우면 14대 전부 같은 길이·같은 시간축의 "전체" 영상이 된다
(사용자 제안). `tools/rehearsal_concat_full.py`:
- 구간 길이 = 시나리오별 최장 프레임 수(1~2프레임 차는 뒤를 검정으로) → 결과 13,574프레임(452.5s) 전 카메라 일치
- 시나리오 사이 검정 4s(`--gap`) — 하드컷이면 사람들이 순간이동해 트래커가 ID 를 잇는다. lost_timeout(3s) 초과로 비워 깨끗하게 끊음
- 검정 구간은 검출 0 → 그 카메라는 그 시간엔 "안 봄"으로 자연 처리
- 인코딩 조건은 준비 CLI 와 동일(baseline). 매니페스트에 `segments`(시나리오별 start/end 초·카메라)·`gap_sec`·`total_sec` 기록
- 카메라당 인코딩 ~3.6분(veryfast) → 4병렬로 전체 ~15분, 카메라당 ~107MB
- 리허설 1회 = 452s 세션. 경보 원점·출입구는 ① 그대로(동·서 2곳 권장 — 그룹 1~4·13~14 동측, 5~12 서측)

## 17. 엣지 — 전체 연속 시나리오의 검정 구간과 매핑 (2026-08-28)

`scenario_15_full` 은 카메라가 없는 구간이 검정이다. [준비]가 0번 프레임을 매핑 스냅샷으로 쓰면
시나리오 01 에 없는 카메라(cam1·2·4·5·6·7·12·13)는 **검정 화면에 대응점을 찍어야** 하는 상황이 된다.

- **준비 스냅샷 = 그 카메라가 실제로 찍힌 첫 구간**: `snapshot_times()` 가 매니페스트 `segments` 에서
  카메라가 등장하는 구간마다 `start+1s` 를 돌려주고, 러너가 차례로 시도해 밝은 프레임(평균 ≥12)을
  고른다. segments 없는 시나리오는 예전처럼 0번 프레임. 실측: 14대 전부 비검정.
- **② [🔄 다른 장면]**: 등장 구간을 순환해 스냅샷 교체(`POST /api/cameras/{id}/test?t=초`). 사람이
  있는 장면을 골라 대응점을 찍는 데도 쓴다. 검정이면 힌트 경고(`black` 플래그).
- 매핑은 카메라 위치별 1회이므로 어느 구간 프레임으로 찍어도 같다 — 동기 재생과 무관.
- 대안으로 "개별 시나리오에서 매핑 후 전체 시나리오 실행" 도 가능하지만, 사용자가 시나리오를 옮겨
  다녀야 해서 기본값으로는 자동 선택 + 수동 순환을 택했다.

## 18. 출입구 통과 판정에 헐 밖 관측 허용 — `exit_extrap_m` (2026-08-28)

문은 대개 매핑 헐 **경계 밖**에 있다. 일반 규칙(헐 밖 관측 폐기)대로면 맵 위에 그린 출입구 선은
영영 안 세지고, 매번 화면 통과선(cam_line)으로 우회해야 했다(사용자: "출입구가 맨날 헐 바깥").
→ **출입구 통과 판정만** 헐 밖 관측(오프라인 시각화의 빨간 ✕)을 쓴다.

- `Thresholds.exit_extrap_m`(사이트 공용, 기본 **2.0m**, 0=끔): 헐 밖 관측을 ROI 무시로 투영
  (`project_raw`)하되 **매핑된 바닥(헐)에서 이 거리 안**일 때만 맵 통과선 관측에 넣는다.
  기준이 "선에서 가깝다"가 아니라 "헐에서 가깝다"인 이유: 외삽 오차는 헐에서 멀어질수록
  커진다(렌즈 왜곡·대응점 잡음 증폭). 문이 헐 바로 밖 1~2m 인 전형적 경우만 허용.
- 표출·구역 밀도·EPFI·CBS 는 그대로 헐 안 관측만 쓴다 — 지표 정의는 변하지 않는다.
- 헐 안→밖 한 걸음 사이에 통과선 부호 기억이 지워지면 crossing 이 안 잡히므로, 외삽이 켜진
  동안은 폐기 시 부호를 유지하고 객체 소실(lost_timeout) 때 지운다.
- 화면 통과선(cam_line/cam_zone)은 그대로 — 문이 화면 가장자리라 "저쪽"이 안 보이는 경우용.
- 단위테스트: 헐 밖 1m 문 crossing 집계 / 헐에서 5m 먼 선은 무시 / 0 이면 예전 동작.

## 19. 영상 끝 = 세션 끝 — 자동 종료·저장 (2026-08-28)

파일 모드 재생이 끝까지 가면(`loop` 아님) 러너가 `on_done` 을 부르고, 서버는 리허설 층에
살아 있는 세션을 `_stop_live_drill()` 로 finalize·저장한다(`VSOURCE_AUTO_END_SESSION`, 기본 1,
`VSOURCE_AUTO_END_GRACE` 2s 여유). 이전엔 영상이 끝나도 세션이 열려 있어 ③에서 종료를 눌러야
리플레이가 저장됐다. 풀 시나리오 실측(452s): e1 out 25 · e2 out 67 · 통과 95 · EPFI 96.7 ·
**SEI 73.2**(출구 2곳) → ④ 건물 훈련 목록·리플레이 1,529프레임.
