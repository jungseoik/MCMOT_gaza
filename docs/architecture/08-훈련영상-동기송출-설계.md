## 0. 무엇을 만드는가 (한 문단)

훈련 영상 파일 묶음을 **시간축이 맞게** RTSP로 내보내는 별도 도구다. 본체(추론·추적·
4대 지표)는 **한 줄도 바꾸지 않는다** — 카메라 입장에서는 여전히 RTSP를 받을 뿐이다.
스위치를 안 켜면 지금과 완전히 동일하게 동작하고, 켜는 동안만 송출 주체가 바뀐다.

---

## 1. 문제 — 파일을 각각 송출하면 시간축이 안 맞는다

4대 지표는 **채널 간 시간 정합**을 전제한다. 건물 훈련(ADR 06)은 전 층이 같은
`t_alarm`을 공유하므로, 16F 카메라의 40초와 1F 카메라의 40초가 같은 순간이 아니면
IDR 반응지연·출구 통과 순서가 전부 무의미해진다.

현재는 `pm2` + `ffmpeg -stream_loop -1` 로 채널마다 독립 송출한다. **실측 근거**:

### ① 영상 길이가 서로 다르다 → 루프마다 벌어진다

| 영상 | 길이 |
|---|---|
| `field_16f_s.mp4` | 181.000 s |
| `field_16f_exit_e.mp4` | 179.900 s |
| `field_1f_exit_w.mp4` | **83.367 s** |

최장−최단 97.6초. 루프 1회마다 그만큼 어긋난다. 159시간 가동분 누적 드리프트
**약 11,000분** — 완전 무작위 위상이다.

### ② 시작 시점을 맞출 수단이 없다

pm2는 프로세스를 순차 기동하고, 개별 재시작(스트림 죽음·재부팅)이 생기면 그 채널만
위상이 튄다.

### ③ 같은 경로에 퍼블리셔 2개는 공존 불가 (실측)

`field_16f_s` 에 두 번째 퍼블리셔를 붙이니 mediamtx가 기존 것을 끊어냈고 pm2가
재시작했다(구독 카메라 fps 5.0→2.7→복구). **경로 소유는 배타적**이다.

## 2. 검증된 메커니즘 — wall-clock 배리어

프로세스를 미리 spawn 해두고 각자 **T0(epoch)까지 정밀 대기 후 `exec ffmpeg`** 한다.

**실측 1 — 시작 편차** (6채널)

```
편차(spread) = 1.7 ms  →  5fps 분석 0.01프레임 · 30fps 영상 0.05프레임
```

**실측 2 — 내용 일치** (3채널, 영상에 경과초를 새겨 동시 캡처)

```
CH1  t=026.0s
CH2  t=026.0s     ← 같은 벽시계 순간에 셋 다 동일 위치
CH3  t=026.0s
```

**실측 3 — 루프 유지** (20초 영상 3채널, 3.5바퀴 후)

```
1회차   : CH1/2/3 모두 t=09.0s
3~4회차 : CH1/2/3 모두 t=11.0s     ← 루프를 돌아도 안 어긋난다
```

단일 ffmpeg 다중출력(tee)보다 단순하고, 한 채널이 죽어도 나머지가 산다.

### 구독(카메라) 타이밍은 맞출 필요가 없다

동기의 기준은 **퍼블리셔**다. 퍼블리셔들이 T0에 함께 시작하면 벽시계 `t` 에서 모든
스트림은 내용상 `(t − T0)` 위치를 송출한다. RTSP 라이브는 처음부터 버퍼링하지 않으므로
**늦게 붙은 구독자도 붙는 순간부터 올바른 위치**를 받는다(앞부분만 유실).
`-c copy` 라 다음 키프레임까지 최대 1초(GOP 30) 대기가 붙는다.

## 3. fps·처리량 — 파이프라인이 이미 처리한다 (새로 설계할 것 없음)

vsource도 결국 RTSP로 내보내므로 카메라 쪽은 아무것도 바뀌지 않는다.

```
① 영상 파일     30fps   (field_16f_s.mp4 = 5430프레임 / 181초)
      ↓ ffmpeg -re     ← 파일을 "실시간 속도"로 읽는다
② RTSP 송출     30fps
      ↓
③ DS 디코드     30fps   (풀레이트 디코드 — GPU 하드웨어라 싸다)
      ↓ _CamGate       ← worker.py:120, 카메라별 analyze_fps 시간 게이트
④ 추론·추적      5fps
```

- **게이트**(`_CamGate.due()`)가 `time.time()` 기준 등간격으로 5fps만 통과시킨다.
  크게 밀리면 `_next_due` 를 현재 시각으로 재동기화해 폭주를 막는다.
- 큐는 `_OldestDropQueue` — 가득 차면 가장 오래된 것을 버려 실시간성을 지킨다.
- 소스가 30fps든 60fps든 **추론은 항상 5fps 고정** → 지표 결과는 동일하다.

**실측 여유**: GPU1 `3,376 MiB / 97,887 MiB · 13%` (9채널). GPU0은 유휴.
경로 인수 방식이라 채널 수가 늘지 않아 **리소스는 지금과 동일**하다.

### vsource가 지켜야 할 것

| | 지킬 것 | 안 지키면 |
|---|---|---|
| **`-re` 필수** | 파일을 실시간 속도로 송출 | 181초를 몇 초에 쏟아붓는다. 시간축·지표 전부 무의미 |
| **`-c:v copy`** | 재인코딩 없이 복사 | 채널당 CPU 인코딩이 붙어 9채널이면 CPU가 먼저 막힌다 |
| 영상 fps 통일(권장) | 전 채널 같은 fps | 지표엔 영향 없으나 디코드 부하가 채널마다 달라진다 |

**주의**: 게이트가 벽시계 기준이라 **배속 재생은 불가능**하다. 리허설 3분이면 실제로
3분이 걸린다. (배속은 시간축 자체를 깨므로 리허설 용도에 애초에 맞지 않는다.)

## 4. 길이가 다른 영상 — 시나리오 단위 사이클

영상들은 **같은 순간부터 시작하되 길이는 제각각**으로 준비된다(확정 1).
그래서 채널별로 각자 루프를 돌리면 두 바퀴째부터 어긋난다. 루프는 **시나리오 단위**로 돈다.

```
사이클 = 190초 (가장 긴 영상 기준, 또는 시나리오에 명시)

 t=0 ─────────────────────────────────────► t=190 ──► 다시 t=0
 CH1 |████████████████████████████|                (170s, 이후 20초 무송출)
 CH2 |██████████████████████████████████|          (185s)
 CH3 |█████████████|                               (80s, 이후 110초 무송출)
       └ 전 채널이 t=190에 동시에 되감긴다
```

짧은 채널은 끝난 뒤 그 카메라만 잠시 신호가 없다. 리허설엔 무해하지만 **현장 시연**엔
보기 안 좋으므로, 준비 도구에서 뒤를 정지화면·검은 화면으로 채워 길이를 맞추는 옵션을 둔다.

## 5. 카메라 연결 — 기존 경로 인수

**"경로"는 폴더가 아니라** `rtsp://127.0.0.1:8554/field_16f_s` 의 맨 뒤 `field_16f_s`,
즉 mediamtx 안의 **채널 칸 이름**이다.

```
지금:  pm2 "field_16f_s" → ffmpeg가 파일 읽음 → mediamtx [field_16f_s] 칸
                                                     ↑ cam05가 여기서 받아감
인수:  pm2 내림 → vsource가 같은 [field_16f_s] 칸에 넣음
                                 ↑ cam05는 주소 그대로, 설정 무변경
```

**이 서버엔 진짜 라이브 RTSP가 없다.** cam04~09가 보는 `field_*` 자체가 이미 pm2의
파일 루프 송출이다. 즉 지금 돌아가는 게 이미 "파일로 하는 리허설"이고 **동기가 안 맞는
조잡한 버전**일 뿐이다. vsource는 새로 얹는 게 아니라 **그 일을 제대로 하게 바꾸는 것**이다.

| | 인수 방식 |
|---|---|
| 카메라 등록·매핑·구역·출입구 | **손 안 댐** (주소 그대로) |
| 리소스 | 지금과 동일 (9채널) |
| 켤 때 | pm2 `field_*` 자동 정지 → vsource 동기 송출 |
| 끌 때 | vsource 정지 → pm2 복구(옵션) |

**버린 대안**

- **별도 사이트**: `SITE_ID` 가 시작 시에만 읽히는 환경변수라(`server.py:60`) 전환에
  :8900 재시작이 필요하다. 시연 중 서버를 내렸다 올리는 건 곤란하다.
- **별도 경로(`sync_*`)**: 카메라 9대를 더 등록하고 매핑을 처음부터 다시 해야 한다.
  리소스는 여유가 있지만 설정 작업이 두 배가 된다.

### 5-1. 훈련 범위는 시나리오의 층으로만

리허설은 **준비한 영상이 전부**여야 한다. 시나리오가 16F인데 17F 카메라가 살아 있으면
그 층까지 건물 훈련 참여 층으로 잡혀 **리허설과 무관한 실영상이 지표에 섞인다.**

**카메라를 끄지 않는다.** 대신 리허설 훈련을 시작할 때 **참여 층을 시나리오의
`floors` 로 좁힌다.** 처음엔 시나리오 밖 카메라를 자동으로 껐다가(파킹) 되돌렸는데,
그 방식은 문제가 더 컸다:

| | 카메라 끄기 (폐기) | 층 범위 제한 (채택) |
|---|---|---|
| 디폴트 세팅(17F+16F) | **깨진다** | 그대로 |
| 대기 송출 소요 | 23초 (워커 재시작) | ~5초 |
| 중간에 죽으면 | **꺼진 채 남는다** | 상태 없음 |
| 훈련 지표 | 16F만 | 16F만 (동일) |

목적은 같이 달성되는데 부작용만 있었다. 자원도 실측 13%라 아낄 이유가 약하다.

**함께 고친 것** — 참여 층 판정이 `mapping` 만 보고 `enabled` 를 안 봤다.
비활성 카메라는 수신 자체를 안 해 추적이 없는데도 참여 층으로 세어, UI 체크박스로
카메라를 끄면 건물 훈련이 오작동했다(리허설과 무관한 **선재 버그**).
`RT.participating_floors()` 와 프론트 양쪽을 **매핑 + 활성**으로 맞췄다.

## 6. 모듈 구조

```
system/vsource/                     신규 — ingest(RTSP 받는 쪽)의 대칭
├── __init__.py
├── scenario.py     시나리오 로드·검증 (영상 존재·길이·코덱·fps)
├── publisher.py    ffmpeg 1개 수명 (detached spawn · 상태 · 종료)
├── controller.py   대기/동시시작 · 사이클 루프 · pm2 인수·복구 · 상태 집계
└── README.md
```

**왜 `system/` 안인가** — :8900이 API를 서비스해야 한다(요구: webui 연동).
`tools/rtsp/` 는 재현용 셸 스크립트 자리라 런타임 상태(어느 시나리오가 도는가, T0가
언제인가)를 가질 수 없다. 별도 포트로 빼면 세션과 타이밍을 묶기 어렵고 포트가 는다.

**프로세스는 detach(`start_new_session=True`) + 상태파일**
`data/vsource_state.json` 에 `{scenario_id, t0, cycle_sec, loop, streams:[{path,pid,file}]}`.
:8900은 재시작이 잦다(현재 37회). uvicorn 자식으로 두면 서버 재시작에 송출이 전부 죽는다.
분리해두고 재기동 후 상태파일로 재부착한다.

### API

| 엔드포인트 | 내용 |
|---|---|
| `GET /api/vsource/scenarios` | 목록 + 영상 검증(존재·길이·코덱·fps) 결과 |
| `POST /api/vsource/standby` | `{scenario_id}` → 정지화면 대기 송출 (매핑용) |
| `POST /api/vsource/start` | `{scenario_id, loop}` → `{t0, cycle_sec, streams[]}` 본영상 t=0 |
| `POST /api/vsource/stop` | 정지 (+ pm2 복구 여부) |
| `GET /api/vsource/status` | `mode`(standby\|play)·`t0`·사이클 위치·채널별 상태 |

## 7. 영상·시나리오 보관 규약

텍스트는 git, 대용량은 HF — 기존 컨벤션 그대로.

```
data/scenarios/<id>.json          시나리오 정의        (git 추적 — 재현 가능)
media/vsource/<id>/*.mp4          송출 준비된 인코딩본  (gitignore + HF 보관)
media/vsource/README.md           규약 설명            (git 추적)
```

`field/`(현장 원본, 개인정보·대용량)와 구분한다 — `media/vsource/` 는 **송출용으로
인코딩·길이 정렬까지 끝낸 준비본**이다.

```json
{
  "id": "drill-16f-1f",
  "name": "화재대피훈련 — 16F 6채널 + 1F 3채널",
  "cycle_sec": 190,
  "streams": [
    {"path": "field_16f_s", "file": "media/vsource/drill-16f-1f/16f_s.mp4"},
    {"path": "field_16f_n", "file": "media/vsource/drill-16f-1f/16f_n.mp4"}
  ]
}
```

`path` 는 **기존 카메라가 보고 있는 경로 그대로** 적는다(경로 인수, §5).

## 8. UI 통합 — 2단계 (대기 → 훈련 시작)

**매핑을 하려면 카메라에 프레임이 들어와야 하는데, 본영상을 틀면 시간이 흘러버린다.**
그래서 대기 상태에서는 **첫 프레임을 정지화면으로** 내보낸다 — 카메라는 붙고 영상은
멈춰 있다. 준비가 끝나면 t=0부터 본영상을 튼다.

| 모드 | 무엇을 내보내나 | 쓸모 |
|---|---|---|
| **대기** (`standby`) | 각 채널 첫 프레임 정지화면 (`-loop 1 -tune stillimage`) | 매핑·ROI·출입구 지정. 시간이 안 간다 |
| **훈련** (`play`) | 본영상, 전 채널 T0에 t=0 동시 시작 | 리허설 본편. 이 순간이 곧 경보 시각 |

새 탭을 만들지 않는다.

| 화면 | 붙는 것 | 왜 여기인가 |
|---|---|---|
| **⑤ 리허설** (전용 탭) | 단계 표시(1 선택 → 2 대기 → 3 매핑 → 4 훈련) · 시나리오 · [⏸ 대기 송출][■ 종료] · 채널별 상태. **채널 클릭 → ②의 그 카메라 매핑 화면** | 리허설은 독립 기능이다. ② 사이드바 맨 아래에 두니 스크롤해야 보였다 |
| **③ 운영 뷰** | 상태 칩 + **[🎬 리허설 훈련 시작]** (대기 중일 때만) | **경보 = 송출 시작**이라 한 번에 걸어야 한다 |
| ①·② | — | 매핑은 ②의 기존 화면을 그대로 쓴다 |

**상태가 여럿이라 헷갈린다**는 지적에 따라 ⑤에 **단계 표시**를 뒀다. 송출·수신·
대기·재생이 따로 놀지 않고 "지금 몇 단계, 무엇을 기다리는 중"으로 한 줄에 모인다.

```
① 시나리오 선택  ▸ ② 대기 송출  ▸ ③ 카메라 매핑  ▸ ④ 훈련 시작
                    └ 대기 송출 준비 중 — 카메라 붙는 중 5/6 (20초쯤 걸립니다)
```

**운용 흐름**

```
1. ⑤ 시나리오 고르고 [⏸ 대기 송출]   → 정지화면, 카메라 20초쯤 뒤 전부 수신
2. ⑤ 채널 클릭 → ② 매핑 화면 → 대응점·ROI·출입구   (영상은 멈춰 있다)
3. ① 도면·구역·병목·임계값                        (순서 자유)
4. ③ 경보 원점 지정 → [🎬 리허설 훈련 시작]
      → 영상이 t=0부터 재생되고 그 순간이 t_alarm 으로 기록된다
5. ③ 세션 진행 → 종료 → 4대 지표
```

**재생 중에 채널을 클릭하면 자동으로 대기로 돌아간다.** 매핑하려는데 화면이 계속
흐르면 대응점을 찍을 수 없다 — "매핑하러 간다"는 행동 자체가 "멈춰라"는 뜻이므로
따로 [대기]를 누르게 하지 않는다. 매핑을 마치면 [▶ 훈련 시작]으로 처음부터 다시 튼다.

### 전환 비용 — 영상 앞 여유가 필요하다 (실측)

대기 → 훈련 전환 시 퍼블리셔가 바뀌므로 **구독자(카메라)도 함께 끊긴다.**
mediamtx가 새 퍼블리셔로 인수는 해주지만 리더 세션은 유지하지 않는다(실측).

```
전 카메라 복귀: T0 + 24~29초 (6채널)
  cam09 T0+ 8.5s · cam08 T0+11.6s · cam07 T0+14.8s
  cam06 T0+17.9s · cam05 T0+21.0s · cam04 T0+23.1s
```

**이 구간에는 채널마다 fps가 다르게 보인다** — 붙는 중이라 그렇다. 실측:

```
   T0+   cam04   cam05   cam06   cam07   cam08   cam09
    10     0.0     0.0     0.0     0.2     1.7     3.3   ← 여기가 "채널마다 fps가 다르다"
    22     1.8     3.3     4.8     5.0     4.9     5.0
    29     4.9     5.1     5.0     5.0     5.0     5.0   ← 이후 120초까지 전부 5.0±0.1
```

붙고 나면 **전 채널이 5.0fps로 균일**하다. fps 자체의 문제가 아니라 램프업 구간이다.

DS 워커가 소스를 **약 3.1초 간격으로 순차 재접속**시켜 채널 수에 비례한다(6채널 ≈ 23초).
단일 채널만 바꾸면 1.2초다.

→ **훈련 영상 맨 앞에 30초 안팎의 여유 구간**을 두고, 실제 훈련 상황은 그 뒤에 오게
준비한다. 경보(t=0)는 영상 시작 시점이므로, 여유 구간 동안 카메라가 다 붙는다.

### IDR 관련 검토 결과 (기록)

"끊고 즉시 시작"은 카메라 재접속(DS 고정 10초) 동안 관측 공백이 생긴다.
알고리즘은 **"관측했는데 안 움직임"과 "관측 못 함"을 구분하지 않는다**
(`session.py:_sample()` — `if not objects: cond_since = None`).

다만 실측 개시 시각이 **z1 = 71.0s · z2 = 81.0s**(엄격 세팅 47.0s)로 공백보다 한참
뒤라 **실사용에서는 무해**하다. 경보 원점 바로 옆 구역이 10초 안에 반응하는 경우에만
그 구역이 늦게 찍힌다. 리허설 도구라는 성격상 감수하고, 필요하면 §10-4의 무중단 모드를 쓴다.
