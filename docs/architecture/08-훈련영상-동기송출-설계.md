## 1. 문제 — 지금 구조로는 시간축 동기가 불가능하다

4대 지표는 **채널 간 시간 정합**을 전제한다. 특히 건물 훈련(ADR 06)은 전 층이
같은 `t_alarm`을 공유하므로, 16F 카메라의 40초와 1F 카메라의 40초가 같은 순간이
아니면 IDR 반응지연·출구 통과 순서가 전부 무의미해진다.

현재는 `pm2` + `ffmpeg -stream_loop -1` 로 채널마다 독립 송출한다. **실측 근거**:

### ① 영상 길이가 서로 다르다 → 루프마다 벌어진다

| 영상 | 길이 |
|---|---|
| `field_16f_s.mp4` | 181.000 s |
| `field_16f_exit_e.mp4` | 179.900 s |
| `field_16f_exit_w.mp4` | 179.800 s |
| `field_1f_exit_e.mp4` | 179.700 s |
| `field_1f_gate_w.mp4` | 179.633 s |
| `field_1f_exit_w.mp4` | **83.367 s** |

최장−최단 = 97.6초. 루프 1회마다 그만큼 어긋난다. 159시간 가동 중인 현재 상태로는
누적 드리프트가 **약 11,000분** — 완전 무작위 위상이다.

### ② 시작 시점을 맞출 수단이 없다

pm2는 프로세스를 순차 기동한다. 게다가 개별 재시작(스트림 죽음·서버 재부팅)이
발생하면 그 채널만 위상이 튄다.

### ③ 같은 경로에 퍼블리셔 2개는 공존 불가 (실측)

`field_16f_s` 에 두 번째 퍼블리셔를 붙여보니 mediamtx가 기존 것을 끊어냈고
pm2가 재시작했다(구독 카메라 fps 5.0→2.7→복구). **경로 소유는 배타적**이다.
→ 신규 모듈은 **기존 pm2 경로와 다른 경로**를 쓴다(결정 3).

## 2. 검증된 메커니즘 — wall-clock 배리어

프로세스를 미리 spawn 해두고, 각자 **T0(epoch)까지 정밀 대기 후 `exec ffmpeg`** 한다.
6채널 실측:

```
프로세스 6개 spawn → T0 대기 → exec
  field_16f_e       T0+0.0104s
  field_16f_exit_e  T0+0.0106s
  field_16f_exit_w  T0+0.0114s
  field_16f_n       T0+0.0113s
  field_16f_s       T0+0.0097s
  field_16f_w       T0+0.0114s

편차(spread) = 1.7 ms  →  5fps 분석 0.01프레임 · 30fps 영상 0.05프레임
```

**충분하다.** 단일 ffmpeg 다중출력(tee) 방식보다 단순하고, 한 채널이 죽어도 나머지가
살아 있다.

### 왜 구독(카메라) 타이밍은 맞출 필요가 없나

동기의 기준은 **퍼블리셔**다. 퍼블리셔들이 T0에 함께 시작하면 벽시계 `t` 에서 모든
스트림은 내용상 `(t − T0)` 위치를 송출한다. RTSP 라이브는 처음부터 버퍼링하지 않으므로,
**늦게 붙은 구독자도 붙는 순간부터 올바른 위치**를 받는다(앞부분만 유실).

→ 구독자 재접속 지연은 "초반 몇 초 유실"일 뿐 **동기를 깨지 않는다**.
단, `-c copy` 라 다음 키프레임까지 최대 1초(GOP 30) 대기가 있다.

## 3. 핵심 설계 — 2단계 모델 (대기 송출 / 동기 시작)

여기가 이 설계의 중심이다. 그냥 "버튼 누르면 동시 시작"만으로는 **닫힌 고리**가 생긴다.

```
② 카메라 매핑은 라이브 프레임이 있어야 대응점을 찍을 수 있다
        ↓  그런데
동기 송출은 훈련 순간에만 t=0부터 흐른다
        ↓  그러면
매핑을 할 시간이 없다 → 매핑 없이는 훈련도 못 한다
```

그래서 같은 스트림을 **두 가지 모드**로 운용한다.

| 모드 | 목적 | 동작 | 시간 정합 |
|---|---|---|---|
| **대기 송출** (standby) | ② 카메라 등록·매핑·ROI·출입구 지정, 미리보기 | 채널별 루프 송출 | 불필요 |
| **동기 시작** (sync) | 훈련 1회 | 전 채널을 죽이고 **T0에 함께 t=0**부터 | **핵심** |

준비는 대기 모드에서 다 끝내고, 훈련 순간에 동기 모드로 전환한다.

### 기존 UI에 녹이는 방법

새 탭을 만들지 않고 **필요한 화면에 필요한 조작만** 붙인다.

| 화면 | 붙는 것 | 이유 |
|---|---|---|
| **② 카메라 등록·매핑** | 시나리오 선택 + **[대기 송출 시작/정지]** · 채널별 송출 상태 | 매핑하려면 스트림이 살아 있어야 한다. 여기가 스트림이 필요한 자리다 |
| **③ 운영 뷰** | **[동기 시작]** (전 채널 t=0 리셋) + 편차 표시 | 훈련 제어와 짝이다. 경보 시작 버튼 옆 |
| ① 맵 설정 | — | 도면·구역·병목은 카메라와 무관 |

**운용 흐름**

```
1. ② 시나리오 고르고 [대기 송출]      → N채널 루프 송출 시작
2. ② 카메라 등록 → 대응점 → ROI → 출입구   (기존 그대로. 스트림 살아있으니 다 됨)
3. ① 도면·구역·병목·출입구·임계값          (카메라 무관, 순서 자유)
4. ③ [동기 시작]  → 전 채널 t=0 동시 송출 → 전 카메라 수신 확인
5. ③ [경보 시작]  → 훈련 세션 (기존 그대로)
```

4와 5를 한 버튼으로 묶는 것은 **하지 않는다**(결정 2). 동기 시작 직후 구독자
재접속에 수 초가 걸리므로, 그 사이 세션이 시작되면 초반 트랙이 빈다. 대신 4가
"전 채널 수신 확인됨"을 UI로 알려 5를 누를 시점을 명확히 한다.

> **영상 준비 요건**: 동기 시작 후 카메라 재접속에 2~5초가 걸린다.
> 훈련 영상은 **앞쪽에 몇 초 여유(lead-in)** 를 두고, 경보 시점을 그 뒤에 오게 준비한다.
> 채널 간 **시작·종료 시각을 맞춘** 영상이면 루프 모드에서도 드리프트가 없다.

## 4. 모듈 위치와 구조

```
system/vsource/                     신규 — ingest(RTSP 받는 쪽)의 대칭
├── __init__.py
├── scenario.py     시나리오 로드·검증 (영상 존재·길이·코덱 적합성)
├── publisher.py    ffmpeg 1개 수명 (detached spawn · 상태 · 종료)
├── controller.py   N개 동시시작 배리어 · 상태 집계 · 정지 · 편차 실측
└── README.md
```

**왜 `system/` 안인가**
- :8900이 API를 서비스해야 한다(요청: "webui에서 별도의 기능 api를 연동").
- `tools/rtsp/` 는 재현용 셸 스크립트 자리 — 런타임 상태(어느 시나리오가 돌고 있나,
  T0가 언제인가)를 가질 수 없다.
- 편집기처럼 별도 포트(:8910)로 빼면 세션 시작과 타이밍을 묶기 어렵고 포트가 하나 더 는다.

**프로세스는 detach 한다 (`start_new_session=True`) + 상태파일**
`data/vsource_state.json` 에 `{scenario_id, t0, loop, streams:[{path,pid,file}]}` 를 남긴다.
:8900은 재시작이 잦다(현재 37회). uvicorn 자식으로 두면 서버 재시작에 송출이 전부 죽는다.
분리해두고 재기동 후 상태파일로 재부착한다.

### API

| 엔드포인트 | 내용 |
|---|---|
| `GET /api/vsource/scenarios` | 시나리오 목록 + 영상 검증(존재·길이·코덱) 결과 |
| `POST /api/vsource/standby` | `{scenario_id}` → 대기 송출 시작(채널별 루프) |
| `POST /api/vsource/sync` | `{scenario_id, lead_sec=2, loop=false}` → `{t0, streams[]}` 동시 시작 |
| `POST /api/vsource/stop` | 전체 정지 |
| `GET /api/vsource/status` | 모드·`t0`·채널별 송출상태·현재 위치·**실측 편차** |

`loop` 플래그로 1회 재생/전체 동시 루프를 고른다(결정 1 — 둘 다).

## 5. 영상·시나리오 보관 규약

텍스트는 git, 대용량은 HF — 기존 컨벤션 그대로 나눈다.

```
data/scenarios/<id>.json          시나리오 정의 (git 추적 — 재현 가능)
media/vsource/<id>/*.mp4          송출 준비된 인코딩본 (gitignore + HF 보관)
media/vsource/README.md           규약 설명 (git 추적)
```

`field/` 와 구분한다 — `field/` 는 **현장 원본**(개인정보·대용량, gitignore),
`media/vsource/` 는 **송출용으로 인코딩·길이 정렬까지 끝낸 준비본**이다.

### 시나리오 정의 예

```json
{
  "id": "drill-16f-1f",
  "name": "화재대피훈련 — 16F 6채널 + 1F 3채널",
  "note": "2026-08 현장 훈련. 전 채널 lead-in 5s, 길이 190s 정렬",
  "streams": [
    {"path": "sync_16f_s", "file": "media/vsource/drill-16f-1f/16f_s.mp4"},
    {"path": "sync_16f_n", "file": "media/vsource/drill-16f-1f/16f_n.mp4"}
  ]
}
```

- `path` = RTSP 경로 = 카메라 등록 주소의 마지막 세그먼트
  (`rtsp://<IP>:8554/sync_16f_s`). **기존 pm2 경로(`field_*`)와 겹치지 않게** `sync_` 접두(결정 3).
- 로드 시 검증: 파일 존재 · 길이(채널 간 편차 경고) · 코덱 적합성(`tools/rtsp/check_video.sh` 규칙)

## 6. 인코딩 — 발판 정리 (선행 과제)

송출이 되려면 영상이 **WebRTC 호환 H.264**(baseline · B-frame 없음 · GOP 30 고정)여야
한다. 이 발판이 지금 레포 밖에 걸쳐 있다.

| 자산 | 위치 | 문제 |
|---|---|---|
| `rtsp-stream` skill | `~/.claude/skills/rtsp-stream/` | **전역** — clone 시 안 따라온다 |
| `add-stream.sh` | `/home/pia/rtsp-stream/` | **레포 밖** — skill이 이걸 호출한다 |
| `check_video.sh`·`encode_video.sh` | `tools/rtsp/` (레포) | ✔ 같은 일을 한다 |

**제안**: skill을 `.claude/skills/rtsp-stream/` 으로 옮기고 내용을 레포 스크립트
(`tools/rtsp/*.sh`) 기준으로 고친다. vsource는 레포 스크립트만 의존하게 한다.
→ 새 서버에서 clone + `fetch_assets.sh` 만으로 동기 송출까지 재현된다.

여기에 **길이 정렬** 단계를 추가한다(동기 송출의 전제) — 채널 간 길이를 맞추고
lead-in을 넣는 도구가 필요하다. `tools/rtsp/align_videos.sh` (신규) 후보.

## 7. 결정된 것 / 남은 것

**결정 (2026-08-24)**

| # | 결정 |
|---|---|
| 1 | 재생 종료: **1회 재생·전체 동시 루프 둘 다** (`loop` 플래그). 영상은 시작·종료 정렬본을 새로 준비 |
| 2 | 세션 연동: **영상 송출만** 담당. 대기 송출(매핑용) → 동기 시작 2단계. 경보는 기존대로 별도 |
| 3 | 기존 pm2 송출: **별도 경로 사용** (`sync_*`). 상시 송출은 그대로 둔다 |
| 4 | 시나리오: **JSON 파일 + UI 선택** (`data/scenarios/*.json`) |

**남은 것**

1. **동기 시작 직후 구독자 재접속을 강제할지** — ingest backoff가 `[5,10,20,40,60]s` 라
   자연 재접속은 최대 60초 걸린다. `_restart_inference` 를 자동 호출할지, 사용자에게
   맡길지. (자동이면 DS 워커 재시작 ~8초 — 영상 lead-in 이 그만큼 필요)
2. **`media/vsource/` 이름** — `field/vsource/` 나 `data/media/` 등 대안.
3. **대기 송출 중 시나리오 전환** — 정지 후 재시작으로 충분한지, 무중단이 필요한지.
4. **경보 시점을 영상 위치에 고정할지** — 시나리오에 `alarm_offset_sec` 을 두면
   "T0+10초 = 경보"로 자동화 가능. 지금은 사용자가 누르는 시점.
