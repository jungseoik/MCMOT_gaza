## 1. 배경 · 목표

경보 세션(경보 시작~종료) 동안 각 사람(track id)의 도면상 위치·속도·방향 등이 프레임마다 흐르지만,
**지금은 최종 집계 지표만 저장되고 프레임별 원본 궤적은 버려진다.** 그래서 다음을 못 한다.

1. **재현(Replay)** — 지난 세션을 다시 돌려보며 사람들이 도면 위에서 어떻게 움직였는지 관찰.
2. **역방향 재파라미터화(Recompute)** — 저장된 원본에 **다른 4대 지표 설정값(속도·밀도·이탈거리 임계 등)을 넣어
   지표를 다시 뽑는다.** "이 임계값이었으면 IDR이 어떻게 나왔을까"를 사후에 시험.

목표: **원본 트랙을 녹화해두고, 결정적(deterministic) 리플레이로 임의 설정값에 대해 지표를 재산출**할 수 있게 한다.

> 왜 가능한가(핵심): 이 엔진은 이미 **"관측된 최신 ts 기준 결정적"** 으로 설계돼 있다
> (`system/metrics/engine.py:10-11, 289-294`, `system/metrics/session.py:24-25`).
> **같은 입력 스트림을 재생하면 반드시 같은 지표가 나온다.** 리플레이의 전제(재현성)가 이미 확보돼 있고,
> 유일하게 빠진 것은 "그 입력 스트림이 저장되지 않는다"는 점뿐이다.

## 2. 현재 구조 진단 (무엇이 저장되고 무엇이 버려지는가)

### 2.1 세션 라이프사이클
- 시작 `POST /api/session/start` (`system/api/server.py:543`), 종료 `POST /api/session/stop`(`:594`).
- 세션 상태 = `EvaluationSession`(`system/metrics/session.py:120`). 층(floor)마다 엔진 1개 → 세션도 엔진별 1개
  (`Runtime.engines: dict[str, MetricsEngine]`, `server.py:81`).
- `session_id = f"sess-{int(round(alarm_ts*1000))}"` — **t_alarm에서 결정적으로 유도**(uuid 아님, `session.py:126-137`).

### 2.2 프레임마다 흐르는 데이터(현재는 휘발)
- `on_tracks()`(`engine.py:171`)가 카메라 px `foot_uv` → 호모그래피 투영 → `_ObjState.hist`에 `(ts, x, y)` 적재.
- **그러나 `hist`는 `window_sec`(기본 1.0초) 슬라이딩 윈도** — 오래된 점을 `popleft()`로 계속 버린다(`engine.py:214`).
- 속도·방향·정렬(align)은 저장이 아니라 **매 스냅샷 시 윈도 양끝점으로 즉석 파생**(`_obj_kinematics`, `engine.py:335-360`).
  가속도는 어디에도 저장 안 됨.
- 이 파생 결과가 매 프레임 `MapObject`(`system/contracts.py:44-`)로 조립되어 SSE로 나간다 —
  즉 **맵 px 좌표(x,y)·vx·vy·speed_mps·align·conf·zone_id는 이미 프레임마다 존재**하지만, 전송 후 보존되지 않는다.

### 2.3 세션 종료 시 저장물 (집계만)
`_save_session()`(`server.py:570`) → `data/sites/<site>/sessions/[<floor>/]<session_id>.json`, top keys 3개:

| 키 | 내용 | 한계 |
|---|---|---|
| `result` | 최종 4대 지표(`EvaluationResult`, `contracts.py:150`) | **특정 임계값으로 이미 확정된 값** |
| `timeline` | 1초 샘플 시계열(`TimelinePoint`, `contracts.py:170`) | 집계치만 |
| `person_series` | gid별 `{route_id, series:[[t, d_m]]}` | **경로 이탈거리 스칼라**뿐, 좌표 아님 |

**결론: 사람들의 실제 도면 좌표(x,y)열은 어디에도 저장되지 않는다.** → 재계산의 입력 원본이 없다.

### 2.4 기존 이력/재계산 흔적
- 세션 이력 저장·조회·내보내기는 **이미 있음**: `GET /api/sessions`(`server.py:651`), `/api/sessions/{id}`(`:666`),
  `/api/session/export`(json/csv, `:674`), 재시작 후 마지막 결과 복원(`:622`).
- 리플레이·재계산(recompute/replay/record/궤적) **실구현 없음** — 결정성 설계 의도 주석(`engine.py:11`)만 존재.

## 3. 설계 원칙

1. **결정성 활용** — 저장할 것은 "지표"가 아니라 **"지표를 만든 입력 스트림"**. 입력만 있으면 결과는 재생성된다.
2. **원본 좌표를 저장** — px `foot_uv`가 아니라 **맵 원본 px (x, y)** 를 저장한다.
   그래야 속도·정렬·구역소속·**출구 통과 카운트(SEI)** 까지 재현된다(px만 저장하면 재투영에 호모그래피 재적용 필요).
3. **파생값은 저장하지 않고 재계산** — speed/align/가속도는 (ts, x, y)에서 파생. 저장하면 window가 고정돼
   역방향 재파라미터화가 막힌다. (뷰잉 편의를 위한 스냅샷 파생값은 §5.3 선택 컬럼으로 별도.)
4. **하위호환·비침투** — 녹화는 `on_tracks()`에 **훅 하나**로 붙이고 env 스위치로 켜고 끈다. 기존 라이브 경로·contracts 무개정.
5. **롤백 가능** — 녹화 off면 기존과 100% 동일. 재계산은 **원본을 절대 덮어쓰지 않고 새 결과로만 산출**.
6. **공간요소 스냅샷 필수** — 재계산의 충실도는 "세션 당시의 zones/routes/exits/graph/alarm_origins"에 달렸다.
   설정이 바뀔 수 있으므로 **세션 시작 시 그 층의 공간요소를 녹화 파일에 스냅샷**한다(§5.2).

## 4. 저장 방식 — SQLite (세션별 단일 .db)

기존 `<session_id>.json`(집계) 컨벤션을 **그대로 두고**, 원본 트랙만 세션별 SQLite로 나란히 둔다.

```
data/sites/<site>/sessions/[<floor>/]<session_id>.json   # (기존) 집계 결과 — 유지
data/sites/<site>/sessions/[<floor>/]<session_id>.db     # (신설) 프레임별 원본 트랙 + 스냅샷
```

선택 이유: 쿼리·필터·집계가 쉽고(사람별 궤적 즉시 조회, KPI 대시보드 확장 용이), 세션별 단일 파일이라
기존 컨벤션과 정합하며 롤백·삭제·이관이 파일 단위로 단순. 대용량 append-only에 적합.

> 대안(JSONL/Parquet)은 단순하나 쿼리를 코드로 짜야 하고, 향후 "회차 비교/KPI 대시보드"에서 재작업 발생.
> 사용자 결정: **SQLite 채택.**

### 4.1 DB 선정 근거 (효율성) — "이 계층에 맞는 선택인가"

이 기능은 **① 세션 중 append 쓰기(단일 writer)** → **② 세션 후 전량 읽기(리플레이/재계산)** 뿐인
**세션 범위(session-scoped) 워크로드**다. 이 성격에 SQLite가 정확히 맞는다.

- **쓰기 처리량 충분**: 부하 상한이 대략 (채널×fps×인원) 행/초 — 50~60ch·5fps·수십 명이라도
  초당 수천 행 수준. SQLite는 WAL + 배치 `executemany`(버퍼 500·주기 commit)로 초당 만 단위
  삽입을 넘긴다. 실측 세션(라이브 8초·150행)·합성 테스트 모두 라이브 5fps에 영향 없음.
- **쓰기 경합 없음**: 층(floor)마다 엔진·세션·`.db`가 **각각 독립 파일** → 층 간 락 경합 0.
  한 세션 내 `on_tracks`는 엔진 락으로 이미 직렬화 → 단일 writer(WAL 이상적).
- **읽기 효율**: `call_seq` 인덱스로 재생은 순차 스캔, 향후 "사람 X 궤적"은 `(gid, ts)` 인덱스로
  즉시. 무엇보다 **SQL 그대로** → 회차 비교·KPI 집계가 코드 재작성 없이 확장된다.
- **운영 단순**: 서버·데몬 없음(임베디드), 세션 = 파일 1개 → 아카이브·삭제·타 서버 이관·백업이
  파일 단위. `data/sites/`는 git 무시라 저장소도 안 부풀린다.

**다른 DB와의 관계(오해 방지)**: ADR 01은 최종 **서빙/집계 계층**을 PostgreSQL(+TimescaleDB)로
본다. 그것과 상충하지 않는다 — SQLite는 **원본 캡처·리플레이 계층**이고, 수백 세션을 가로지르는
플릿 단위 분석/대시보드가 필요해지면 세션 `.db`들을 그 서버 DB(또는 DuckDB-over-parquet)로
**ETL해 올리는 소스**가 된다. 즉 "캡처는 SQLite, 대규모 집계는 서버 DB"로 역할이 갈린다.

**결론**: 캡처+리플레이 계층에서 SQLite는 처리량·운영·확장(SQL) 모두에서 **효율적인 선택**이다.
서버 DB로의 승격은 필요 시점(플릿 KPI)에 ETL로 얹으면 되고, 지금 도입은 과설계다.

## 5. 데이터 모델 (SQLite 스키마 초안)

### 5.1 `tracks` — 프레임별 원본 (핵심)
```sql
CREATE TABLE tracks (
  ts        REAL    NOT NULL,   -- 관측 ts(epoch 초). 프레임 인덱스 가정 금지(채널별 fps 다름)
  gid       TEXT    NOT NULL,   -- cam_id:local_track_id (글로벌 병합 전 키)
  cam_id    TEXT    NOT NULL,
  x         REAL    NOT NULL,   -- 맵 원본 px
  y         REAL    NOT NULL,
  conf      REAL,               -- 최근 검출 신뢰도
  in_bounds INTEGER             -- 0/1 (맵 경계 밖 투영 여부)
);
CREATE INDEX idx_tracks_ts  ON tracks(ts);
CREATE INDEX idx_tracks_gid ON tracks(gid, ts);
```

### 5.2 `meta` — 세션 메타 + 공간요소 스냅샷 (재현 충실도의 핵심)
```sql
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT);  -- value는 JSON 문자열
-- 필수 키:
--   schema_version      녹화 포맷 버전(예: "1")
--   session_id, floor_id, site_id
--   alarm_ts, alarm_origins
--   site_version        세션 시작 시점 사이트 config 버전
--   homography_version  좌표를 만든 캘리브레이션 식별(층별 proj 버전)
--   thresholds_at_start 세션이 고정했던 Thresholds 사본(session.py:141) — 원본 지표 재현 검증용
--   spatial_snapshot    그 층의 zones/routes/exits/graph/alarm_origins/grid 스냅샷(JSON)
--   map_wh              맵 w/h (px)
--   fps_nominal         채널 공칭 fps (참고용)
```
> `spatial_snapshot`이 없으면 재계산이 "현재 설정" 기준이 되어 세션 당시와 어긋난다 → **반드시 저장.**

### 5.3 (선택) `snapshots` — 뷰잉 편의용 파생값
리플레이 화면에서 그대로 그리기 위한 캐시. **재계산은 이 표를 쓰지 않는다**(x,y에서 파생).
```sql
CREATE TABLE snapshots (
  ts REAL, gid TEXT, vx REAL, vy REAL, speed_mps REAL, align REAL, zone_id TEXT, evac_ok INTEGER
);
```
(용량 절감을 원하면 §5.3은 생략하고 리플레이 시 §5.1에서 파생 계산해도 된다.)

### 5.4 용량 산정
16ch × 5fps × 재실자 N × 세션시간. 예) 40명·10분 = 5fps × 600s × 40 ≈ **12만 행**, 행당 ~40B → **세션당 수 MB**.
부담 없음. 대규모(200명·30분)라도 수십 MB.

## 6. 녹화층 설계 (Phase 1 — ✅ 구현 완료)

> 아래는 설계 시점 서술이며, 실제 구현은 `system/metrics/recorder.py`로 반영됨(엔드포인트/API 명칭은 §8 실제값 기준).


### 6.1 탭 지점(tap point)
`MetricsEngine.on_tracks()` 내부, 호모그래피 투영 직후(`engine.py:171-224`). 이미 맵 px `(x, y)`가 계산되는 지점이라
**추가 계산 없이** `(ts, gid, cam_id, x, y, conf, in_bounds)`를 레코더로 흘리기만 하면 된다.

### 6.2 레코더(신설 모듈 제안: `system/metrics/recorder.py`)
- 세션 시작(`start_session`) 시 `<session_id>.db` 생성 + `meta`에 §5.2 스냅샷 기록.
- `on_tracks()`에서 프레임 배치 단위 `executemany` INSERT(버퍼링 후 주기적 commit — I/O 최소화).
- 세션 종료(`stop_session`) 시 flush + `PRAGMA optimize`/close.
- **비침투 원칙**: 레코더 예외가 라이브 경로를 죽이지 않도록 try/except로 격리(녹화 실패 ≠ 서비스 중단).

### 6.3 켜고 끄기 (env)
```
SESSION_RECORD=1      # 기본 0(off) → 켜야 녹화. off면 기존과 100% 동일(롤백)
SESSION_RECORD_SNAPSHOTS=0   # §5.3 파생 캐시 저장 여부
```

## 7. 리플레이 · 재계산 경로 설계 (Phase 2 — ✅ 구현 완료)

> 실제 구현은 §7.1의 "입력원 분리 리팩터링" 없이, 헤드리스 `MetricsEngine`에 녹화 `on_tracks`를
> 재공급하는 방식(`system/metrics/replay.py`)으로 더 단순하게 달성됨(상단 구현 노트 참조).


### 7.1 선행 리팩터링 — `EvaluationSession` 입력원 분리
현재 계산 로직은 라이브 엔진 상태를 **직접 참조**해서 저장 데이터로 되돌리기 어렵다.
- `_obj_rows()`(`session.py:269`)·`_bn_densities()`(`:278`)가 `self._eng._objects`를 직접 읽음.
- SEI/타임라인이 `self._eng._exits`(라이브 카운터)를 읽음(`:346-367`).

**목표 구조**: `EvaluationSession`이 "프레임별 관측 행 리스트"를 입력으로 받는 순수 재생기가 되도록,
엔진 상태 참조를 **입력 포트(추상 소스)** 뒤로 분리한다. 라이브는 엔진에서, 리플레이는 SQLite에서 같은 포트로 공급.
수식(`_sample`, `_person_metric`, `_sei`, `_zone_metric_now`)은 이미 비교적 순수 → 입력원만 갈아끼우면 된다.

### 7.2 재계산 러너(headless)
```
입력: <session_id>.db (tracks + meta.spatial_snapshot) + Thresholds 오버라이드(부분 가능)
절차: ts 오름차순으로 tracks를 프레임(동일 ts·cam 묶음)으로 재구성
      → 공간요소는 meta.spatial_snapshot 사용(세션 당시 기준)
      → EvaluationSession을 새 Thresholds로 재생
      → 출구 통과·구역소속·병목밀도까지 재판정(라이브 카운터 대신 좌표에서 재현)
출력: 새 EvaluationResult + timeline + person_series (원본 .json 미변경, 별도 산출물)
```

### 7.3 재현성 검증(회귀)
`SESSION_RECORD=1`로 녹화한 세션을 **원본과 같은 Thresholds로 재계산 → 저장된 원본 result와 동일**해야 한다.
결정성 설계(§1) 덕에 수치 일치가 기대치. 이 동치 테스트가 리팩터링(§7.1)의 안전망.

## 8. 계약 (v1.10 — ✅ CONTRACT.md 반영 완료)

> 실제 구현에서는 아래 "recompute" 대신 **`POST /api/session/{session_id}/replay`** 하나가
> 재생 프레임 + (thresholds 오버라이드 시) 재계산 결과를 함께 반환한다(재생·재계산 통합).
> 아래 초안 표기는 설계 이력으로 남겨둔다.


- **신설(Phase 2)**: `POST /api/session/{session_id}/recompute?floor=`
  - body: `{thresholds?: {v_th?, a_th?, r_th?, dt_hold?, d_allow?, rho_crit?, weight?, q_design?, design_capacity?...}, save?: bool}`
    (부분 오버라이드; 미지정 필드는 세션 당시 `thresholds_at_start` 사용)
  - resp: `EvaluationResult`(+선택 timeline) — **원본 미변경**, `save:true`면 파생본을 `<session_id>.recompute-<n>.json`로 저장.
- **신설(Phase 3)**: `GET /api/session/{session_id}/replay` — 프레임별 좌표 스트림(리플레이 UI용).
- **스키마**: `EvaluationResult`에 `source: "live"|"recompute"`, `base_session_id`, `thresholds_used` 선택 필드 추가 검토.
- **무개정 유지**: 기존 `TrackedObject`/`MapObject`/`EvaluationResult` 핵심 필드·기존 엔드포인트.

## 9. 재파라미터화 매핑 — 무엇을 바꾸면 무엇이 재계산되나

| 바꿀 설정 (`schema.py`) | 재계산되는 지표 | 재계산 가능? |
|---|---|---|
| `v_th`·`a_th`·`r_th`·`dt_hold` (`Thresholds:112`) | **IDR** (피난 반응) | ✅ (ts,x,y에서 speed·align 재파생) |
| `d_allow` (`Thresholds`) | **EPFI** (경로 충실도) | ✅ (경로 스냅샷 + 좌표로 이탈거리 재적분) |
| `rho_crit`·`weight` (`Bottleneck:68`) | **CBS** (병목 혼잡) | ✅ (병목 폴리곤 스냅샷 + 좌표로 밀도 재적분) |
| `design_capacity` (`ExitLine:83`)·`q_design` | **SEI** (비상구 효율) | ✅ (출구선 스냅샷 + 좌표로 통과 재판정) |
| 속도/가속 계산 **window 자체** | 파생 kinematics 전반 | ✅ (좌표에서 임의 window로 재파생) |
| alarm_origins(경보 발생원 위치) | IDR 거리 기준 | ✅ (스냅샷/오버라이드) |

**재계산 불가·주의:**
- **검출·추적 자체**(놓친 사람, id 뒤바뀜)는 재현 불가 — 녹화는 "추적 결과 좌표"이지 원본 영상이 아니다.
  (원본 영상까지 다시 돌리려면 별개의 "영상 리플레이"가 필요 — 이는 8월 "녹화본 재생"의 상위 범위.)
- **호모그래피(캘리브)를 바꾼 재계산**은 저장 좌표가 옛 캘리브 기준이라 불가. `homography_version`으로 불일치 감지·경고.
- **구역/경로/출구 기하 변경**을 반영한 재계산은 스냅샷과 달라지므로, 기본은 스냅샷 기준. 새 기하 적용은 명시 옵션으로만.

## 12. 검증 계획

1. **동치**: 녹화 세션을 원본 Thresholds로 재계산 → 저장된 원본 `result`와 수치 일치(결정성 확인).
2. **재파라미터화**: `d_allow`↑ → EPFI↑, `rho_crit`↓ → CBS↑ 등 방향성이 수식과 일치.
3. **비침투**: `SESSION_RECORD=0`에서 기존 86종 테스트·라이브 경로 무변화.
4. **부하**: 16ch@5fps 녹화 on/off의 처리량 차이 측정(밀림 없어야).
