# M0 환경 검증 — 디코딩 스택 가용성·16ch 부하 실측 (2026-07-13)

> [멀티카메라 시스템 전환 설계](02-멀티카메라-시스템-전환-설계.md) M0 산출물.
> 결정: **ingest 디코딩 스택 = ffmpeg 서브프로세스 + NVDEC(h264_cuvid)** — 설계서 A-1의 사전 합의 폴백 체인에 따름.

## 1. 가용성 점검 결과

| 항목 | 결과 |
|------|------|
| GStreamer | ❌ 미설치 (`gst-inspect-1.0` 자체 없음) |
| DeepStream (`nvurisrcbin`/`nvstreammux`) | ❌ 미설치 (`/opt/nvidia/deepstream` 없음) |
| gst nvcodec (`nvh264dec`) | ❌ (GStreamer 자체가 없음) |
| **ffmpeg NVDEC** (`-hwaccel cuda`, `h264_cuvid`) | ✅ **즉시 가용** (av1/h264/hevc/mjpeg cuvid 전부) |
| PyAV (`av`) | ❌ conda env `boosttrack`에 미설치 |
| PyGObject (`gi`) | ❌ 미설치 |
| GPU | **RTX PRO 6000 Blackwell Server ×2 (96GB each)**, driver 580.126.09 |
| 테스트 소스 | mediamtx(:8554) 상시 송출 14스트림 (pm2, `rtsp-stream` 스킬 인프라) |

주의: GPU 2장은 점검 시점에 이미 타 워크로드로 사용 중(util 80~90%) — 본 시스템은 공유 사용 전제.

## 2. 실측

### 1ch 스모크 (rtsp://127.0.0.1:8554/sample1, 960×540@25 H.264)
- NVDEC 디코드 정상, 라이브 속도(speed 1.08x = 실시간 제한) 15초 365프레임 수신. 에러 없음.

### 16ch 동시 디코드 (20초, 14스트림+2중복)
| 지표 | 값 | 해석 |
|------|-----|------|
| **NVDEC(dec) 사용률** | **3%** | 960×540@25 16ch는 Blackwell NVDEC에 사실상 무부하. FHD 16ch로 환산해도 ~12% 수준 예상 |
| ffmpeg CPU 합계 | 220% (≈14%/ch, 2.2코어) | RTSP demux+전송 비용. 수용 가능 |
| RAM 합계 | 3.4GB (16프로세스) | 프로세스당 ~210MB |
| GPU0 VRAM 증가 | ~10GB (16 CUDA 컨텍스트, ~0.6GB/ctx) | 96GB 대비 무리 없음. 컨텍스트 공유 최적화 여지 |
| 실패 채널 | 0/16 | (2건 dts 경고는 `-f null` muxer 무해 경고) |

## 3. 결정과 근거

**ffmpeg 서브프로세스(NVDEC) 채택.** 설계서 A-1의 폴백 체인(DeepStream → gst nvh264dec → PyAV/ffmpeg-NVDEC)에서 앞 두 단계가 미설치로 불가, ffmpeg는 무설치로 16ch를 여유 있게 처리함이 실측 확인됨.

- 카메라별 ffmpeg 프로세스: `ffmpeg -hwaccel cuda -rtsp_transport tcp -i <rtsp> -vf fps=<analyze_fps> -f rawvideo -pix_fmt bgr24 pipe:` → 파이프로 프레임 수신 (5fps 기준 채널당 7.8MB/s, 16ch 124MB/s — 파이프 여유)
- 디코드는 원 fps로 NVDEC이 수행, 출력만 analyze_fps로 다운샘플 → 파이프 대역 최소화
- 재접속 워치독(EOS/stall/error + 지수 백오프)은 Edge 레포 `reconnect.py` 패턴을 프로세스 감시로 이식 — **ingest 인터페이스(FrameQueue에 FrameItem 공급)는 스택 무관**이라, 추후 다채널 스케일업(50~60ch 목표) 단계에서 DeepStream 도입 시 ingest 내부만 교체
- GStreamer 설치(apt+PyGObject)는 지금 이득 없음: NVDEC 3% 사용률에서 스택 전환 효과 없고 의존성만 증가

## 4. 후속 확인 사항 (M2에서)
- ffmpeg 파이프 rawvideo 수신 지연·드랍 계측 (FrameQueue 드랍 카운터)
- CUDA 컨텍스트 VRAM(0.6GB/ctx×N) — 채널 수 증가 시 `-hwaccel_device` 분산(2 GPU) 또는 디코드 GPU 고정
- FHD/4K 카메라 혼입 시 채널당 CPU 재실측
