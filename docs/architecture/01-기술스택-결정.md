# 기술 스택 결정 (ADR)

- 작성일: 2026-06-12
- 목적: 요구사항([North Star](../requirements/CCTV-영상분석-엔진-필수추출정보.md)) 충족을 위한 확장 시, 레이어별 기술 선정의 **후보·근거·결정**을 기록.
- 평가 4축: **처리속도/지연 · 메모리 · 운영부담 · 요구적합도**
- 표기: 메모리/속도/운영부담은 상대값(낮음·중간·높음). 절대 수치는 하드웨어 의존이라
  *반드시 자사 GPU에서 PoC 실측*으로 확정할 것(여기 숫자는 자릿수 감각용 추정).

> 🔻 **목표 재조정 (2026-07-4주차): 최종 채널 스케일 150ch → 50~60ch로 하향.** 사유=실증 대상
> 규모 재산정. 이에 따라 "150ch에서 무거운 스택 도입" 트리거가 사실상 오지 않음 → 아래 결정은
> **최종 50~60ch는 현 경량 스택(Postgres/Redis/DeepStream 단일서버)으로 충분, 대규모 백본
> (Kafka/Triton/ClickHouse/deck.gl)은 향후 50~60ch 초과 확장 시 옵션**으로 재조정.

> **모든 결정을 가르는 두 축**
> 1. **채널 스케일**: 단일 → 15ch → **50~60ch**(최종 목표, 2026-07-4주차 하향). 인프라 무게를 결정.
> 2. **요구 2·4·5가 전부 기하 연산**(좌표변환/구역포함/선분교차). DB·연산위치를 결정.

## 결정 요약 (먼저 보기)

| 레이어 | 현재(단일~50~60ch 목표) | 향후 확장 옵션(50~60ch 초과) | 한 줄 사유 |
|--------|-------------------------|------------------------------|-----------|
| L1 RTSP 디코드 | FFmpeg **NVDEC** → **DeepStream**(ADR 04에서 채택) | (동일) | CPU 디코드는 수 채널서 한계, NVDEC/DeepStream으로 GPU 디코드 |
| L2 추론 서빙 | 인프로세스 TRT + 배치 | **Triton** | 카메라↔추론 분리, 배치로 GPU 채움 |
| L3 트래커 | **BoostTrack++** 유지 | PoC로 결정(↓ 참조) | 정확도 차별점 vs 채널수 트레이드오프 |
| L4 메시지 버스 | **Redis**(Streams) | + **Kafka** | Redis로 시작, 내구/다소비자 필요시 Kafka |
| L5 DB | **PostgreSQL+PostGIS+Timescale** | + ClickHouse(선택) | 기하·시계열·관계형 단일화 |
| L6 대시보드 전송 | **WebSocket**(←Redis) | 동일 | 단순·저지연 |
| L7 맵 시각화 | Leaflet 또는 Canvas | **deck.gl** | 점 수 늘면 WebGL 필요 |

핵심: **최종 50~60ch 목표는 현 경량 스택(Postgres 단일화 + Redis + DeepStream 단일서버)으로 충분.**
Kafka/Triton/ClickHouse/deck.gl 등 대규모 백본은 **50~60ch 초과 확장이 실제 요구로 들어올 때** 도입하는 옵션이다.

## L1. RTSP 수신 · 디코드

현재: `webui/server.py`가 OpenCV `VideoCapture` + **단일 공유 모델 + Lock 직렬**. 1~몇 채널용.

| 후보 | 속도/채널밀도 | 메모리 | 운영부담 | 장점 | 단점 |
|------|--------------|--------|---------|------|------|
| OpenCV VideoCapture (CPU) | 낮음(수 채널) | 중간 | 낮음 | 코드 그대로, 단순 | CPU 디코드 병목, 다채널(50~60ch) 불가 |
| **FFmpeg + NVDEC** | 높음(NVDEC 1칩 ≈ 1080p30 20~40ch) | 낮음 | 중간 | GPU 디코드, 기존 파이썬 유지 | NVDEC 개수 한계, 파이프 관리 |
| PyNvVideoCodec / VPF | 높음 | 낮음 | 중간 | 프레임이 GPU에 상주(PCIe 복사↓) | API 성숙도·문서 부족 |
| **DeepStream(GStreamer)** | 최고(GPU당 100s ch) | 중간 | **높음** | 디코드+추론+트랙 일괄 배치 | 학습곡선↑, 커스텀 트래커 이식난이도 |
| GStreamer 단독 | 높음 | 낮음 | 높음 | 유연 | 파이프라인 직접 구성 |

**결정**: 단기 **FFmpeg NVDEC**(또는 PyNvVideoCodec), 장기 **DeepStream(PoC 후)**.
**사유**: 디코드 병목부터 GPU로 옮기는 게 투자 대비 효과 최대. DeepStream은 채널밀도 압도적이나 운영부담·트래커 이식 이슈(L3)가 커서 신중히 접근 — 다채널 스케일 실측 결과 **ADR 04에서 zero-copy 워커로 채택**(1GPU 16ch@5fps). 50~60ch 목표는 이 DeepStream 단일서버 + GPU 3~4장으로 도달 가능.

## L2. 추론 서빙 · 배치

| 후보 | 속도 | 메모리 | 운영부담 | 장점 | 단점 |
|------|------|--------|---------|------|------|
| **인프로세스 TRT**(현재) | 빠름(단일) | 낮음 | 낮음 | 단순, 지연 최소 | 모델 1개 공유→직렬, 다채널 배치 어려움 |
| **Triton Inference Server** | 빠름+**동적배치** | 중간 | 중간 | 다카메라 배치로 GPU 점유↑, 모델 버전관리 | 별도 서버, gRPC 오버헤드 |
| TorchServe | 중간 | 중간 | 중간 | 파이썬 친화 | TRT 대비 처리량↓ |
| 직접 배치 큐 | 빠름 | 낮음 | 중간 | 의존성 없음 | 직접 구현·유지 |

**결정**: 단기 인프로세스 TRT 유지(단, **공유모델+Lock 직렬구조는 제거** → per-camera 워커 + 배치 큐). 장기 **Triton**.
**사유**: 50~60ch 목표는 인프로세스 배치(현 DeepStream 워커의 dynamic batch)로 충분. 그 이상 대규모 확장에서 "카메라 N개 → 탐지 1배치"로 GPU를 더 채워야 할 때 Triton 동적배치가 정석.

## L3. 트래커 — ⚠️ 가장 중요한 트레이드오프

| 후보 | 정확도(ID유지) | 속도 | 메모리 | 비고 |
|------|---------------|------|--------|------|
| **BoostTrack++**(현재) | **최고**(ReID+ECC+MhKF) | 중간 | **높음**(ReID 모델 GPU 상주) | 검출당 ReID 추론 → 채널수에 부담 |
| BoT-SORT | 높음(ReID+카메라보정) | 중간 | 중간 | BoostTrack 대비 가벼움 |
| ByteTrack | 중간 | **매우 빠름** | **낮음** | 모션 only, ReID 없음 → 가림/재등장 약함 |
| DeepStream nvtracker (NvDCF/DeepSORT) | 중간~높음 | 빠름(GPU) | 중간 | 다채널 확장 쉬움, **BoostTrack 아님** |

**결정**: **BoostTrack++ 유지**(현 DeepStream 워커도 카메라별 BoostTrack++ 인스턴스로 구성, ADR 04). 50~60ch 목표는 이 구성으로 도달 가능하므로 nvtracker 교체는 불필요 — 단, 향후 대규모 확장 시 "DeepStream nvtracker로 얻는 채널수 이득" vs "BoostTrack++ ID 정확도 손실"을 자사 영상으로 실측 후 결정.
**사유**: ID 정확도는 멀티캠 병합·고유통과 카운팅의 토대(요구 1·5). 함부로 못 버림. 대안으로 **DeepStream에서 검출 메타데이터만 빼서 Python BoostTrack++ 재연계**도 설계 옵션(채널수는 줄지만 정확도 유지).

## L4. 메시지 / 스트리밍 버스

레이어가 둘로 갈림: **(a) 핫상태·대시보드 fan-out** vs **(b) 내구성 이벤트 백본**.

| 후보 | 지연 | 처리량 | 메모리 | 운영부담 | 내구성 | 적합 |
|------|------|--------|--------|---------|--------|------|
| **Redis Pub/Sub** | **sub-ms** | 높음 | 낮음 | 낮음 | 없음(fire&forget) | 대시보드 푸시 |
| **Redis Streams** | sub-ms | 높음 | 중간(보관량) | 낮음 | 옵션(AOF) | 핫상태+경량 큐, "카프카 라이트" |
| **Kafka** | ms | **최고**(100k+/s) | **높음**(JVM 힙 GB급) | **높음**(파티션/KRaft) | 강함(리플레이) | 대규모 확장 백본(50~60ch 초과) |
| NATS / JetStream | sub-ms~ms | 높음 | **낮음**(Go) | 중간 | JetStream로 옵션 | Kafka 경량 대안 |
| RabbitMQ | ms | 중간 | 중간 | 중간 | 강함 | 복잡 라우팅 |
| MQTT(Mosquitto) | 낮음 | 중간 | **매우 낮음** | 낮음 | 옵션 | 엣지/카메라 다수 발행 |
| ZeroMQ | **최저** | 최고 | 최저 | 높음(직접구성) | 없음 | 브로커리스, 토폴로지 직접 |

**결정**: **Redis**(Streams로 핫상태+fan-out)로 최종 50~60ch까지 운영. 향후 대규모 확장 시 **Kafka 추가**(또는 운영 가볍게 가려면 **NATS JetStream** 검토).
**사유**: 최종 50~60ch 규모에 Kafka는 운영부담·메모리 오버엔지니어링. Redis Streams가 consumer group까지 줘서 충분히 버팀. **50~60ch 초과 확장에서 내구성/리플레이/다중 소비자가 실제 요구로 들어올 때** Kafka 백본 도입.

## L5. 데이터베이스 — ✅ Postgres 단일화가 거의 맞춤형

요구 2·4·5가 전부 기하 연산이라 **PostGIS가 직접 대응**:
`ST_Contains`(구역 포함·요구4) · `ST_Intersects`(가상선 통과·요구5) · `ST_Area`(밀도·요구4) · `geometry`(평면도 좌표·요구2).

| 후보 | 시계열 | 공간 | 관계형 | 벡터 | 메모리/확장 | 비고 |
|------|:------:|:----:|:------:|:----:|------------|------|
| **PostgreSQL+PostGIS+Timescale+pgvector** | ◯(Timescale) | **◎(PostGIS)** | ◎ | ◯(pgvector) | 중간, 수직확장 양호 | **4종을 한 엔진**, 성숙 |
| InfluxDB | ◎ | △ | △ | ✕ | 낮음, 압축 우수 | 메트릭 특화, 공간/관계형 약함 |
| ClickHouse | ◯ | △(geo 일부) | ◯ | ✕ | 낮음(컬럼압축), **분석 초고속** | 대량 이벤트 OLAP, 트랜잭션 약함 |
| MongoDB | ◯(ts컬렉션) | ◯(2dsphere) | △ | ◯(Atlas) | 중간 | 공간 정밀도 PostGIS 미달 |
| Milvus/Qdrant | ✕ | ✕ | ✕ | **◎** | 중간 | ReID 임베딩 전용(대규모시) |

**결정**: **PostgreSQL + PostGIS + TimescaleDB + pgvector** 단일 코어(최종 50~60ch까지 충분). 향후 확장으로 이벤트 분석량 폭증 시 **ClickHouse를 분석 전용으로 추가**(Postgres=운영/공간, ClickHouse=대량 집계).
**사유**: 손으로 짠 `pointPolygonTest`/부호거리(현 `speed.py`·`counter.py`)를 검증된 PostGIS로 대체 + 다구역/다비상구가 그냥 행 N개. 시계열(궤적·밀도·정렬도)·"피난 개시 시점"(시계열 윈도) Timescale로 해결. 멀티캠 ReID 매칭은 pgvector. **DB를 3~4개 따로 둘 이유가 약함.**
**핫 데이터 주의**: 프레임레이트 쓰기는 DB로 직격 금지 → 현재 상태는 Redis, **다운샘플/이벤트만 Postgres에 영속**.

| 후보 | 지연 | 양방향 | 운영부담 | 비고 |

## 미해결 의사결정 (PoC로 확정할 것)

1. **트래커 @대규모**: DeepStream nvtracker vs BoostTrack++ 재연계 — 50~60ch는 BoostTrack++로 도달, 그 이상 확장 시 채널밀도·MOTA/IDF1 실측 후 결정. (L3)
2. **메시지 백본**: 50~60ch 초과 확장 시 실제 이벤트율·소비자 수 측정 후 Kafka vs NATS JetStream. (L4)
3. **분석 DB 분리 시점**: 이벤트/궤적 적재량이 Postgres+Timescale 단일로 버거워지는 임계 측정 → ClickHouse 도입 여부. (L5)
4. **NVDEC 채널 한계**: 자사 GPU(모델/세대)의 1080p30 동시 디코드 채널수 실측 → GPU 대수 산정. (L1)

## 다음 단계 권고

- 단기 스택(NVDEC + per-camera 워커 + Redis + Postgres/PostGIS/Timescale + WebSocket)으로 **단일~15ch를 먼저 안정화**하며 요구 3·4·5의 미구현 산출물(정렬도·피난개시·고유통과)을 PostGIS/Timescale 위에 구현.
- 그 위에서 위 4개 PoC를 돌려 **최종 50~60ch 스택을 데이터로 확정**(현 경량 스택으로 충분한지, 어느 지점에서 대규모 백본이 필요한지).
