## 0. 결론 요약

1. **H.265는 우리 엔진 입장에서 문제가 아니다.** ffmpeg 백엔드(`hevc_cuvid`)도,
   DeepStream 백엔드(`nvurisrcbin`)도 HEVC를 하드웨어 디코드한다. UI 프리뷰는 서버에서
   JPEG로 만들어 내려주므로 브라우저 코덱 호환도 무관하다.
   → "팟플레이어/VLC로 H.265가 안 열렸다"는 것은 **그 NVR의 RTSP/SDP 구현 문제**일 확률이 높다.
   현장에서 **ffmpeg로 직접 검증**하는 것이 첫 액션이고, 그 결과에 따라 대응이 갈린다.
2. **VBR 자체는 큰 문제가 아니지만, "스마트 코덱 + 긴 GOP"는 문제다.** 피난훈련은
   화면 전체가 움직이는 최악의 시나리오라 VBR 비트레이트가 폭증한다.
   → **최대 비트레이트 상한(cap) + GOP 1~2초 고정 + 스마트코덱 OFF**를 요청한다.
3. **로컬 mediamtx 허브를 둔다(권장안 B).** 이유는 트랜스코딩이 아니라 **세션 1:1 고정**이다.
   NVR에는 채널당 딱 1세션만 물리고, 추론·녹화·디버깅 뷰어는 모두 로컬 mediamtx에서 받는다.
   재접속 폭풍이 NVR로 전파되지 않고, 원본 녹화도 공짜로 얻는다.

## 1. 개념 정리

### 1.1 H.264 vs H.265(HEVC)

| | H.264 (AVC) | H.265 (HEVC) |
|---|---|---|
| 나온 해 | 2003 | 2013 |
| 같은 화질 기준 비트레이트 | 기준 | **약 40~50% 절감** |
| 지원 범위 | 사실상 전부 | 대부분 지원하나 **구현 편차 큼** |
| 라이선스 | 단순 | 특허풀 3개로 복잡 → 일부 제품이 회피/부분구현 |

현장 카메라가 H.265로 설정된 이유는 명확하다 — **NVR 저장 용량과 네트워크를 절반으로 줄이려고**.
방재실 입장에서는 H.265가 정상이고, 우리가 맞춰야 하는 쪽이다.

#### "H.265는 RTSP로 유틸리티에서 연결이 불가"의 진짜 원인 후보

VLC·팟플레이어는 둘 다 HEVC를 지원한다. 그러니 "H.265라서 안 된다"는 성립하지 않는다.
실제로는 아래 중 하나일 가능성이 높다.

| # | 원인 | 증상 | 우리 쪽 영향 |
|---|---|---|---|
| ① | **SDP에 `sprop-vps/sps/pps` 누락** — NVR이 DESCRIBE 응답에 HEVC 파라미터셋을 안 실어줌 | 연결은 되는데 화면이 안 나오거나 한참 뒤에 나옴 | ffmpeg는 in-band 파라미터셋을 기다려 대개 **복구 가능**. GOP가 길면 첫 프레임까지 수 초 |
| ② | **RTP 페이로드 타입/`packetization-mode` 오기재** | 플레이어가 코덱을 못 잡음 | ffmpeg가 SDP 무시하고 추정하면 열림. `-analyzeduration`/`-probesize` 상향으로 개선 |
| ③ | **TCP interleaved에서 FU 조각화 버그** | 깨짐·타임아웃 | UDP로 바꾸면 열리는 경우 있음 (단 유실 리스크) |
| ④ | **NVR 트랜스코딩 미지원 채널** — NVR이 H.265 채널은 RTSP 재배포를 안 해줌 | DESCRIBE 자체 실패(404/453) | **회피 불가** → 카메라 직결 또는 코덱 변경 필요 |
| ⑤ | **서브스트림만 H.264** — 메인 H.265 / 서브 H.264 구성 | streamID에 따라 되고 안 되고 | **가장 손쉬운 회피책** (§1.2) |

> 답사에서 "H.264로 바꾸니 됐다"는 것은 ①②③④를 구분하지 못한 상태다.
> **현장 30분 진단(§6)으로 반드시 구분해야** 대응 비용이 결정된다.

#### 우리 엔진의 HEVC 지원 근거 (코드 확인 완료)

- ffmpeg 백엔드: `system/ingest/camera_worker.py:151` — `-hwaccel cuda -rtsp_transport tcp`.
  코덱을 지정하지 않으므로 H.264/H.265 자동 판별. 이 서버에 `hevc_cuvid` 디코더 존재 확인.
- DeepStream 백엔드: `system/ingest_ds/worker.py:283` — `nvurisrcbin`이 내부에서
  `nvv4l2decoder`로 H.264/H.265 모두 NVDEC 디코드.
- GPU: RTX PRO 6000 Blackwell ×2 — NVDEC HEVC 8/10bit 디코드 지원.
- UI 프리뷰: `system/api/server.py:442` — 서버에서 JPEG 인코딩 후 전송이라 **브라우저 무관**.

⚠️ 다만 **처리량은 재측정 대상**이다. 현재 알려진 한계치(DeepStream 16ch@5fps)는 H.264 기준
실측값이며, HEVC는 디코드 특성이 달라 채널 한계가 달라질 수 있다. §5의 사전작업 항목.

### 1.2 메인스트림 / 서브스트림 (`streamID=1,2,3`)

IP 카메라는 보통 같은 영상을 **화질·해상도가 다른 2~3개 스트림으로 동시 인코딩**해서 내보낸다.

| 스트림 | 통상 용도 | 통상 스펙 | 코덱 경향 |
|---|---|---|---|
| streamID=1 (메인) | 녹화·정밀 확인 | 1920×1080 ~ 4K, 4~8Mbps, 30fps | H.265 |
| streamID=2 (서브) | 다분할 라이브 뷰 | 704×480 ~ 1280×720, 0.5~2Mbps, 15fps | **H.264인 경우 많음** |
| streamID=3 (3rd) | 모바일·썸네일 | 320×240급 | H.264/MJPEG |

**우리 추론에는 서브스트림(720p급)으로 충분하다.** 사람 검출·추적은 1280×720이면 되고,
현재 파이프라인도 `nvstreammux`에서 어차피 리사이즈한다. 즉:

> **"H.265 채널은 서브스트림(streamID=2)을 쓴다"** 가 코덱 변경 요청 없이 쓸 수 있는
> 1순위 회피책이자, 대역폭·NVR 부하까지 동시에 낮추는 선택이다. (답사 때 streamID 1~3 모두
> 연결 확인했으므로 가능성 높음 — 다만 서브의 **코덱·해상도·fps를 채널별로 기록**해야 한다.)

### 1.3 비트레이트 — CBR / VBR / 스마트코덱

**비트레이트** = 영상 1초를 표현하는 데이터량(bps). 이게 화질·대역폭·저장용량을 결정한다.

| 방식 | 동작 | 장점 | 단점 |
|---|---|---|---|
| **CBR** (고정) | 장면이 단순하든 복잡하든 초당 데이터량을 일정하게 유지. 단순한 장면에서는 남는 비트를 낭비(혹은 채움) | 대역폭 예측이 정확 → **네트워크 설계가 쉽다** | 움직임 폭증 시 화질이 떨어짐(비트를 못 늘리니까) |
| **VBR** (가변) | 장면 복잡도에 따라 비트레이트를 올렸다 내렸다 함. 빈 복도=낮게, 사람 몰림=높게 | 평균 대역폭·저장용량 절약, 중요한 장면 화질 유지 | **피크가 튄다.** 평균 2Mbps인데 순간 12Mbps가 나올 수 있음 |
| **CVBR / VBR+cap** | VBR인데 **최대치를 못 넘게 상한**을 검 | VBR 이점 + 피크 통제 | 상한에서는 화질 저하 |
| **스마트코덱** (H.264+/H.265+, WiseStream, Zipstream, Smart Codec) | 움직임 없는 영역은 극단적으로 압축하고, **I-프레임 간격(GOP)을 매우 길게**(4~10초) 잡음 | 저장용량 대폭 절감 | **우리에게 가장 위험** — 아래 참조 |

#### "VBR로 잡혀있는데 상관 없나?" 에 대한 답

**보통은 상관없다. 단 조건이 세 개 붙는다.**

1. **최대 비트레이트 상한이 걸려 있어야 한다.**
   피난훈련은 *화면 전체가 동시에 움직이는* 영상 압축 최악의 케이스다. VBR 무제한이면
   40채널이 동시에 피크를 치며 스위치·NVR 업링크를 순간적으로 포화시킨다.
   → 패킷 유실 → 디코더 에러 → 우리 워커의 재접속 → **재접속 폭풍**.
   피난훈련은 재현이 불가능한 1회성 이벤트라 이 리스크는 감당할 수 없다.
2. **GOP(I-프레임 간격)가 1~2초여야 한다.**
   RTSP는 **I-프레임(키프레임)부터** 디코드를 시작할 수 있다. GOP가 8초면 재접속 시
   최대 8초의 공백이 생기고, 이는 곧 **트랙 ID 유실 → 지표(IDR/EPFI) 오염**이다.
   스마트코덱은 GOP를 길게 잡는 것이 핵심 동작이므로 **반드시 OFF**.
3. **fps가 고정이어야 한다.**
   일부 카메라는 비트 절감을 위해 조용할 때 fps를 떨어뜨린다(동적 fps).
   우리 속도·밀도 지표는 프레임 간 시간차 기반이라 fps가 흔들리면 속도 추정이 왜곡된다.

> 정리: **VBR 유지 OK. 단 `최대 비트레이트 cap + GOP 1~2초 + 스마트코덱 OFF + 고정 fps`.**
> 굳이 하나를 고르라면 **CBR이 우리에게 더 안전**하지만, 방재실 저장용량 정책을 건드리는
> 변경이라 협의 비용이 크다. VBR+cap이 현실적 타협점이다.

### 1.4 RTSP 세션 — 유지보수 업체가 경고한 부분

**세션 = RTSP 클라이언트 하나가 스트림 하나를 받는 연결.**
VLC로 1채널을 열면 세션 1개. 우리가 40채널을 물면 **세션 40개**다.

여기서 한계는 세 겹으로 쌓인다.

| 계층 | 통상 한계 | 넘으면 | 현장 조건 |
|---|---|---|---|
| **카메라** | 동시 RTSP 클라이언트 3~10개 | 신규 연결 거부(453 Not Enough Bandwidth), 심하면 카메라 리부팅 | NVR이 이미 1개 점유 |
| **NVR** | 총 출력 세션 수 + 총 출력 대역(예: 128Mbps) | 신규 거부, 기존 세션 끊김, **CMS 화면 끊김** | "여기저기 땡겨 보는 곳 많음" → 이미 여유가 없을 수 있음 |
| **네트워크** | 스위치 포트 속도(100M/1G) | 전 채널 품질 저하 | **미확인 — 반드시 확인** |

업체가 경고한 핵심은 **"방재실 관제 화면이 우리 때문에 끊기면 안 된다"**는 것이다.
피난훈련 당일에 방재 관제가 끊기는 건 안전 사고로 직결된다.

#### 우리가 지켜야 할 3원칙

1. **채널당 RTSP 연결은 정확히 1개.** 추론·녹화·디버깅 뷰가 각각 NVR에 붙으면 세션 3배.
   → **로컬 mediamtx 허브로 1:N 팬아웃** (§3).
2. **재접속은 백오프.** 실패한 채널이 1초마다 재시도하면 NVR에 SYN 폭탄이 된다.
   (`INGEST_BACKEND=deepstream`은 `rtsp-reconnect-interval=10`으로 이미 10초 백오프 — 유지)
3. **단계적 램프업.** 당일에 40채널을 한 번에 붙이지 않는다. 4 → 8 → 16 → 전체로 올리며
   NVR·CMS 상태를 확인한다. (§6 리허설 절차)

## 3. 수집 아키텍처 3안 비교

### A안 — 엔진이 NVR에 직접 접속 (현재 구조)

```
NVR#1~4 ──(RTSP × N채널)──> MACS 엔진 (ffmpeg/DeepStream) ──> 지표
```

- 👍 가장 단순. 추가 컴포넌트 0. 지연 최소.
- 👎 소비자가 늘면 **NVR 세션이 배수로 증가**(추론+녹화+디버깅 = 3배).
- 👎 NVR이 흔들리면 재접속 로직이 NVR로 그대로 전파.
- 👎 원본 녹화가 없어 **사후 재분석이 불가** (현재 리플레이는 트랙 DB 기반이라
  검출 자체가 틀렸을 때 되돌릴 수 없음).
- 판단: **채널 수가 적고(≤8) 단일 소비자면 충분.** PoC 규모에서는 부족.

### B안 — 로컬 mediamtx 허브 (**권장**)

```
NVR#1~4 ──(RTSP 1세션/채널)──> [PoC PC] mediamtx :8554 ──┬──> MACS 엔진 (추론)
                                     (재배포, 재인코딩 X)  ├──> record (원본 fMP4 세그먼트)
                                                          └──> VLC/디버깅 뷰어 (N명)
                                        └ 문제 채널만: runOnDemand ffmpeg (HEVC→H264 변환)
```

- 👍 **NVR 세션이 채널당 1개로 고정.** 우리 쪽 소비자가 몇이든 NVR은 모른다.
- 👍 **NVR 장애 격리** — 재접속·백오프를 mediamtx가 흡수, 엔진은 안정적인 로컬 RTSP만 본다.
  (기존에 겪은 "재접속 죽음의 나선"이 NVR로 나가지 않는다)
- 👍 **원본 녹화 무료 획득** → 훈련 1회성 이벤트를 원본으로 남겨 사후 재분석·파라미터 튜닝 가능.
  기존 세션 리플레이(v1.10)와 결합하면 "검출 단계부터 재계산"이 가능해진다.
- 👍 H.265 문제 채널만 **선별적으로** ffmpeg 트랜스코드 경로를 붙일 수 있다.
- 👍 팀에 이미 mediamtx+pm2 운영 노하우 있음([RTSP 송출서버 구성](RTSP-송출서버-구성.md)).
- 👎 홉 1개 추가 → 지연 +100~300ms 수준(재인코딩은 없으므로 화질 손실 0).
- 👎 관리 포인트 1개 증가, 녹화 시 디스크 필요(§4 용량 계산).
- 판단: **PoC 현장 리스크(세션 제한·NVR 불안정·다중 소비자·원본 확보)를 한 번에 해결.**

> 주의: **mediamtx 자체는 트랜스코딩을 하지 않는다.** 코덱 변환이 필요하면
> `runOnDemand`로 ffmpeg 프로세스를 붙이는 방식이다. B안의 가치는 트랜스코딩이 아니라
> **세션 팬아웃 + 장애 격리 + 녹화**에 있다.
>
> 사용할 바이너리는 **순정 upstream mediamtx** 권장.
> `dev/MACS-Product-dev-mediamtx` 포크는 Minio/OTEL/클립 등 제품 기능이 붙어 있어
> PoC 엣지 노드에는 과하다. (단 원본 클립 업로드가 필요해지면 그때 포크로 교체)

### C안 — 전 채널 H.264 트랜스코드 게이트웨이

```
NVR ──> ffmpeg(NVDEC 디코드 → NVENC H.264 인코딩) ──> mediamtx ──> 엔진
```

- 👍 다운스트림이 코덱을 신경 쓸 필요가 전혀 없음.
- 👎 **채널당 디코드+인코딩 → GPU 예산 두 배.** 우리는 GPU를 추론에 다 써야 한다.
- 👎 재인코딩으로 화질 손실 + 지연 증가.
- 판단: **전면 적용은 낭비.** §6 진단에서 원인 ④(NVR이 H.265 RTSP를 아예 못 내보냄)로
  확정된 채널에 한해 B안 안에서 부분 적용한다.

### 권장: **B안 + 필요 채널만 C안 부분 적용**

| 시나리오 | 채널 | 스트림 | 채널당 | 합계 |

### 진단 커맨드 (P3의 뼈대)

```bash
URL='rtsp://pia:1q2w3e4r!@172.29.0.11:554/trackID=1&streamID=1'

# ① 코덱·해상도·fps — 이게 되면 H.265도 우리 엔진에서 된다는 뜻
ffprobe -v error -rtsp_transport tcp -select_streams v:0 \
  -show_entries stream=codec_name,profile,width,height,avg_frame_rate,bit_rate \
  -of default=nw=1 "$URL"

# ② SDP 원문 덤프 — sprop-vps/sps/pps 유무로 원인 ① 판별
ffmpeg -v trace -rtsp_transport tcp -i "$URL" -t 1 -f null - 2>&1 | grep -iE 'sdp|sprop|a=fmtp|a=rtpmap'

# ③ GOP(키프레임 간격) 측정 — 2초 넘으면 스마트코덱 의심
ffprobe -v error -rtsp_transport tcp -select_streams v:0 \
  -show_entries frame=key_frame,pkt_pts_time -of csv -read_intervals '%+30' "$URL" | grep ',1$\|1,'

# ④ 실제 비트레이트 변동(VBR 피크) 관찰 — 30초 동안 bitrate= 값 추이
ffmpeg -rtsp_transport tcp -i "$URL" -t 30 -f null - 2>&1 | grep -o 'bitrate=[^ ]*'

# ⑤ TCP가 안 되면 UDP로 (원인 ③ 판별)
ffprobe -v error -rtsp_transport udp -show_entries stream=codec_name "$URL"

# ⑥ 30초 원본 저장 (재인코딩 없이) — 사무실에서 정밀 분석용
ffmpeg -rtsp_transport tcp -i "$URL" -t 30 -c copy -y ch01_sample.mkv
```

### 트랜스코드 프리셋 (P4 — 예외 채널 전용)

```bash
ffmpeg -rtsp_transport tcp -hwaccel cuda -hwaccel_output_format cuda \
  -i "$URL" \
  -c:v h264_nvenc -preset p4 -tune ll -profile:v high \
  -b:v 3M -maxrate 3M -bufsize 6M -g 50 -an \
  -f rtsp -rtsp_transport tcp rtsp://127.0.0.1:8554/ch01_h264
```
`-g 50` = 2초 GOP(25fps 기준). `-tune ll`(low latency)로 지연 최소화.
GPU: RTX PRO 계열은 GeForce의 NVENC 8세션 제한이 없으나, **동시 트랜스코드 수는 추론
예산과 경쟁하므로 최소화**한다.

### mediamtx 엣지 설정 예 (P2)

```yaml
# mediamtx.yml (엣지 허브)
rtspTransports: [tcp]          # 방재실 네트워크에서는 TCP 고정 (유실 방지)
writeQueueSize: 4096
logLevel: info

pathDefaults:
  rtspTransport: tcp           # NVR에서 당길 때도 TCP
  sourceOnDemand: no           # 훈련 중 끊김 방지 — 상시 유지
  # record: yes                # 원본 녹화 필요 시
  # recordPath: /data/rec/%path/%Y-%m-%d_%H-%M-%S-%f
  # recordSegmentDuration: 1m

paths:
  ch01:
    source: "rtsp://pia:1q2w3e4r!@172.29.0.11:554/trackID=1&streamID=2"
  ch02:
    source: "rtsp://pia:1q2w3e4r!@172.29.0.11:554/trackID=2&streamID=2"
  # ── H.265 재배포가 안 되는 예외 채널만 트랜스코드 경로 ──
  ch09_h264:
    runOnDemand: >
      ffmpeg -rtsp_transport tcp -hwaccel cuda -hwaccel_output_format cuda
      -i "rtsp://pia:1q2w3e4r!@172.29.0.12:555/trackID=9&streamID=1"
      -c:v h264_nvenc -preset p4 -tune ll -b:v 3M -maxrate 3M -bufsize 6M -g 50 -an
      -f rtsp rtsp://127.0.0.1:8554/$MTX_PATH
    runOnDemandRestart: yes
```
> URL에 `&`가 있으므로 **반드시 따옴표**. 비밀번호의 `!`는 셸에서 히스토리 확장에 걸리니
> 스크립트에서는 작은따옴표를 쓴다. 비밀번호는 **커밋 금지** — `.env`/환경변수로 주입.

엔진 등록 주소는 `rtsp://127.0.0.1:8554/ch01` 형태가 되어, 시스템 쪽 코드는 **무개정**이다.

## 5b. 처리 용량 실측 — 채널 수 × fps (2026-08-17)

측정 환경: a6000 / RTX PRO 6000 Blackwell **1장 전유**(`GPU_DEVICES=1`) /
`INGEST_BACKEND=deepstream` / b16 엔진 / mediamtx 송출 H.264 소스 /
설정마다 서버 1회 기동 → 25초 워밍업 → 40초 구간 중앙값.

| 채널 | 목표fps | 요구합 | 달성합 | 달성/ch | 달성률 | GPU% | VRAM |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 12 | 5.0 | 60 | **60.0** | 5.00 | **100%** | 38 | 5.9GB |
| 16 | 5.0 | 80 | 75.5 | 4.72 | 94% | 46 | 7.6GB |
| 24 | 5.0 | 120 | 78.4 | 3.27 | 65% | 46 | 8.1GB |
| 12 | 15.0 | 180 | 74.4 | 6.20 | 41% | 65 | 7.1GB |
| 32 | 3.0 | 96 | 69.8 | 2.18 | 73% | 36 | 8.6GB |
| 40 | 2.0 | 80 | 64.5 | 1.61 | 81% | 36 | 9.0GB |

**한계는 채널 수가 아니라 총 fps다 — GPU 1장당 약 75~78fps에서 포화.**
요구합을 60 → 180으로 3배 올려도 달성합은 60 → 78 → 74로 눌린다. 24ch@5fps든
12ch@15fps든 결과는 같은 ~75fps. 실용 설계선은 **채널수 × fps ≤ 70**(여유 10%).
기존 문서의 "16ch@5fps = 78.7fps"와 일치한다.

### 현장 40채널 시나리오

| 구성 | 요구합 | GPU 1장 | GPU 2장 (`GPU_DEVICES=0,1`) |
|---|---:|---|---|
| 40ch @ 2fps | 80 | 81% (1.61fps/ch) | 여유 |
| 40ch @ 3fps | 120 | 58% — 붕괴 | **~100% 예상 (슬롯당 60)** ← 목표선 |
| 40ch @ 5fps | 200 | 불가 | 슬롯당 100 → 부족 |

보행속도 1.2m/s 기준 3fps면 프레임당 40cm라 추적·속도 산출에는 충분하다.

**두 가지 관찰**

- GPU 사용률이 36~65%인데 처리량이 막힌다 → 병목이 연산이 아니라 배치 구성·트래킹
  연관 쪽. b16 엔진이라 32/40채널에서도 배치가 16으로 잘리는 것이 유력.
  `yolox_mot20_fp16_dyn_b32.engine`이 이미 있으므로
  `DS_ENGINE_MAX_BATCH=32 DS_DET_ENGINE=…b32.engine`으로 재측정할 여지가 있다.
- VRAM은 40채널에서도 9GB — **제약이 아니다.**

## 5c. 채널 등록 — 벌크 경로 (구현 완료)

웹 UI에서 카메라를 **한 대씩** 추가하면 DS 백엔드는 매번 워커 컨테이너를
재시작하고, 그때마다 **같은 GPU 슬롯의 기존 채널이 전부 끊긴다**(실측 공백
7.9~8.4초). 40채널이면 9.5분 + 40회 단절. 활성화도 같은 경로라 비용이 두 배가 된다.

실측 (a6000 / GPU1 / `analyze_fps=5.0`, 채널 4→12에서 일정):

| 방식 | 채널당 | 기존 채널 공백 | 9채널 | 40채널 |
|---|---|---|---|---|
| `POST /api/cameras` 순차 | API 6.1s · 복귀 14.3s | 매번 ~8s | 129s | ~9.5분 + 40회 단절 |
| `POST /api/cameras/bulk` | — | **~8.7s 1회** | **15.4s** | 채널 수에 거의 무관 |

**현장 절차 (워커 재시작 1회로 완결)**

| 단계 | 동작 | 재시작 | GPU 부하 |
|---|---|---|---|
| ① | UI 모달에서 벌크 등록 — **비활성으로 등록** 체크 | 0회 | 0 |
| ② | **연결 테스트**(`POST /api/cameras/probe`, 동시 4개) — 안 붙는 주소를 등록 전에 색출 | 0회 | 0 |
| ③ | 채널별 매핑(대응점) — `PUT …/mapping`은 워커를 건드리지 않음 | 0회 | 0 |
| ④ | **"매핑 완료 N대 전부 활성화"**(`PUT /api/cameras/bulk`) | **1회** | 정상 |

②가 현장에서 특히 중요하다 — NVR 40채널 URL 중 어떤 것이 안 붙는지(코덱 원인 ④,
채널번호 오기 등) **등록 전에** 알 수 있고, 해상도까지 같이 확인돼 서브스트림
선택(§1.2)의 근거가 된다. 동시 4개로 제한해 NVR 세션 부담을 억제한다.

③이 무료라는 점도 중요하다. 40채널 매핑은 수 시간이 걸리는데(자동화 불가),
그동안 이미 가동 중인 채널은 **한 번도 끊기지 않는다.**

> **비활성 등록을 쓰는 이유**: mapping이 없는 카메라도 디코드·추론·트래킹 자원은
> 그대로 쓰고 결과만 버려진다(`system/metrics/engine.py:190`). 매핑 전 40채널을
> 활성으로 두면 요구 fps가 §5b의 천장을 넘겨 **이미 매핑된 채널의 fps까지 떨어진다.**

CSV 경로(`tools/bulk_register_cams.py`)는 NVR 채널표를 그대로 쓸 때 — `rtsp` 컬럼을
직접 주거나 `nvr,port,track,stream`으로 URL을 조립한다. 계정은 CSV가 아니라
`NVR_USER`/`NVR_PASS` 환경변수로 주입한다(비밀번호 커밋 금지).
상세는 [system/README](../system/README.md#카메라-일괄-등록-벌크).

## 6. 현장 방문 체크리스트

### 6-1. 네트워크·인프라 (10분)

- [ ] 스위치 포트 속도: `ethtool <iface> | grep Speed` → **1000Mb/s 확인**
- [ ] NVR 4대 ping RTT·유실: `ping -c 100 172.29.0.11`
- [ ] 포트 도달성: `nc -zv 172.29.0.11 554` (4대 전부)
- [ ] NVR↔우리 PC가 같은 L2인지, 상단 라우터 경유인지 (포트가 554/555/556/557로 다른 이유)

### 6-2. 코덱 진단 — **H.265 채널에서 반드시** (20분)

채널 2~3개를 샘플로 위 ①~⑥ 커맨드를 돌리고 아래 판정표로 분기한다.

| ffprobe(①) 결과 | 판정 | 대응 |
|---|---|---|
| `codec_name=hevc` + 정상 fps | **우리 엔진 OK** | 코덱 변경 요청 **불필요**. 그대로 수집 |
| 연결되나 첫 프레임까지 5초+ | 원인 ①/GOP 과다 | GOP 단축 요청 + `-probesize`/`-analyzeduration` 상향 |
| TCP 실패 / UDP 성공 | 원인 ③ | mediamtx path만 `rtspTransport: udp` |
| DESCRIBE 자체 실패(404/453) | 원인 ④ | **서브스트림 시도 → 그래도 실패 시 H.264 변경 요청** |
| 서브(streamID=2)만 성공 | 원인 ⑤ | **서브스트림 채택 (가장 좋은 결과)** |

- [ ] 채널별 `streamID=1/2/3` 각각의 **코덱·해상도·fps·비트레이트 기록** → 매핑표 작성
- [ ] GOP 측정(③), VBR 피크 관찰(④)
- [ ] 대표 채널 30초 원본 저장(⑥) → 사무실에서 추론 정확도 사전 검증

### 6-3. 세션·부하 램프업 (20분) — **업체·과장님 입회 하에**

- [ ] 4채널 동시 접속 → 5분 유지. NVR 상태·CMS 화면 이상 없는지 **육안 확인**
- [ ] 8 → 16 → 목표 채널 수로 단계 상승, 각 단계마다 CMS 확인 및 대역 측정
  (`nload`/`iftop`으로 우리 PC 인터페이스 수신량 기록)
- [ ] 세션 상한 탐색: 연결 거부가 나오는 지점 기록 (**나오면 즉시 중단**하고 그 수를 상한으로)
- [ ] 우리 접속을 전부 끊고 CMS가 정상 복귀하는지 확인

### 6-4. 확보할 정보

- [ ] **채널번호 ↔ 실제 카메라 위치 매핑표** (평면도 좌표 매핑에 필수 — 없으면 PoC 진행 불가)
- [ ] NVR 모델명·펌웨어 버전 (4대) → 세션/대역 스펙 시트 확인용
- [ ] 카메라 모델명(대상 채널) → 스마트코덱 설정 항목 파악용
- [ ] NVR admin 비밀번호 or 설정 변경 시 업체 입회 절차·연락망

## 7. 유지보수 업체 요청서 (그대로 전달용)

> PoC 대상으로 선정된 카메라에 한해 아래 설정을 요청드립니다.
> **저장용량에 영향이 있는 항목은 PoC 기간(YYYY-MM-DD ~ )에만 적용하고 이후 원복 가능합니다.**

| 항목 | 요청값 | 이유 |
|---|---|---|
| 코덱 | **H.265 유지 가능** (변경 불필요) | 분석 엔진이 H.265를 하드웨어 디코드함. 단 사전 검증에서 RTSP 재배포 실패가 확인된 채널만 H.264 변경 요청 |
| 해상도 | 메인 1080p / **서브 1280×720 이상** | 서브스트림으로 수집 예정 — 서브가 D1(704×480) 이하면 인식률 저하 |
| fps | **고정 15fps 이상** (동적 fps OFF) | 이동속도·밀도 지표가 프레임 간격 기반 |
| 비트레이트 | VBR 유지 + **최대 비트레이트 상한 설정** (1080p 4Mbps / 720p 2Mbps) | 훈련 중 전 채널 동시 피크로 네트워크 포화 방지 |
| **GOP / I-프레임 간격** | **1~2초 (fps의 1~2배)** | 재접속 시 복구 지연 = 추적 ID 유실 = 지표 오염 |
| **스마트코덱** (H.265+/WiseStream/Zipstream 등) | **OFF** | 긴 GOP + 배경 열화로 검출·추적 정확도 하락 |
| RTSP 계정 | `pia` 계정 유지 (NVR 4대) | 이미 생성 완료 |
| 동시 접속 | PoC PC에서 **채널당 1세션**, 총 N세션 사용 예정 | 관제 영향 최소화를 위해 허브 방식으로 세션 고정 |

## 8. 리스크 & 오픈 이슈

| # | 리스크 | 영향 | 완화 |
|---|---|---|---|
| R1 | 스위치가 100Mbps | 채널 수 반토막 | 서브스트림 채택 / 전용 1GbE 스위치 반입 / NVR별 분산 |
| R2 | NVR 세션 상한이 낮음 | 목표 채널 미달 | 램프업으로 사전 확정 → **채널 수를 그 상한에 맞춰 PoC 범위 재조정** |
| R3 | H.265 채널이 RTSP 재배포 불가(원인 ④) | 채널별 트랜스코드 필요 | GPU 예산 확보 + 해당 채널만 C안 부분 적용 |
| R4 | HEVC 디코드 부하로 채널 한계 하락 | 동시 처리 채널 감소 | H.264 기준 용량 곡선 확보(§5b — GPU 1장 ~75fps 천장). **HEVC 소스 재측정 필요** |
| R5 | 훈련 당일 NVR 과부하로 관제 영향 | **안전 사고 · 신뢰 상실** | 리허설 필수 · 램프업 · 즉시 차단 절차 · 업체 상주 |
| R6 | 채널↔카메라 매핑표 미확보 | 평면도 좌표 변환 불가 = PoC 불가 | 6-4에서 반드시 확보 |
| R7 | 훈련 1회성 — 실패 시 재현 불가 | 전체 PoC 실패 | **원본 녹화(B안)로 사후 재분석 경로 확보** |

### 열린 결정사항

1. **PoC 총 채널 수** — 미정. R2 램프업 결과와 §5b 용량 곡선으로 상한이 정해진다.
   현재 근거로는 **GPU 2장 + 40ch @ 3fps**가 기본선(요구합 120 = 슬롯당 60).
2. **원본 녹화 여부** — 디스크 100~150GB 필요. R7 대비로는 강력 권장.
3. **메인 vs 서브 스트림** — 6-2 진단 결과로 결정. 현재는 **서브 우선** 방침.
