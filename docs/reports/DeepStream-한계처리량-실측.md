## 1. 방법

- **환경**: GPU1(RTX PRO 6000 Blackwell 96GB) 단독. **vLLM이 동일 GPU 메모리
  약 84GB를 상주 점유**(측정 중 추론 유휴) — 여유 ~14GB 안에서 진행.
  GPU0은 타 프로젝트 사용 중이라 제외.
- **부하 생성**: mediamtx 라이브 RTSP 12본을 채널이 중복 구독
  (`urls[i % 12]`, `bench_e2e_limit.py`와 동일 방식). 채널 전부 목표 5fps.
- **측정**: 스텝당 전 채널 첫 트랙 수신 대기(10~20초) → 워밍업 30초 →
  60초 측정. 채널당 실효 fps는 호스트 bridge 수신 간격 기준.
  batch 상한은 `min(16, N)` (YOLOX dynamic 엔진 max 16 — 16 초과 채널은
  배치 여러 번으로 자연 처리).
- **지표 정의 주의**: 지연(lag)은 *컨테이너 appsink 수신 ts → 호스트 트랙
  수신*(추론+트래킹+ZMQ 포함). ffmpeg 베이스라인의 `avg_queue_lag_s`는
  *수신 ts → 분석 시작*(큐 대기만)이라 직접 비교엔 약간 보수적으로 볼 것.
  infer(ms)는 배치 1회의 검출+트래킹 합산 시간.

- 전 스텝에서 **64채널까지 전 채널 연결 성공, 워커 생존, OOM·GST·디코드
  에러 0건, zmq 드랍 0건**. GPU mem은 vLLM 상주분(~84GB) 포함 — 워커
  자체 사용량은 12ch ~5.9GB → 64ch ~10.9GB.
- **한계 지점: 16ch** — 채널당 4.93fps로 목표 5fps에 사실상 도달하는 마지막
  스텝(큐 드랍이 나타나기 시작하는 경계). 12ch는 여유(드랍 0).
- 이후 저하 곡선: **24ch ≈ 3.2fps → 32ch ≈ 2.4fps → 48ch ≈ 1.3fps →
  64ch ≈ 0.8fps**. 총 처리량은 16ch에서 78.7fps로 정점, 24~32ch에서
  ~75fps 평탄, **48ch부터는 오히려 감소**(59.7 → 50.4fps).
- **지연은 폭주하지 않는다**: oldest-drop 큐가 오래된 프레임을 버려
  최신성을 유지 — lag p95는 전 구간 0.5~0.9초. 포화 시 "밀린 영상"이 아니라
  "듬성한 최신 영상"으로 저하된다 (운영 관점에서 의도된 동작).

## 3. 병목 분석

| 후보 | 판정 | 근거 |
|------|------|------|
| NVDEC(디코드) | **아님** | 64ch(=풀레이트 디코드 ~1,600fps)에도 NVDEC util 최대 9%. 세션 64개 정상 동작 — Blackwell 세션 한도 미달 |
| GPU 메모리 | **아님(현 조건)** | 최대 94.8GB/96GB (vLLM 84GB 포함). 워커 단독 ~11GB — vLLM 없다면 64ch도 크게 여유 |
| GPU SM(추론) | **주요 병목 아님** | SM 평균 39~54%, 최대 85%. 포화 없이 오히려 64ch에서 평균이 내려감(39%) — GPU가 놀고 있다 |
| **호스트 단일 프로세스 직렬화** | **주병목** | 프레임당 처리시간이 12.6ms(12ch)→20.0ms(64ch)로 증가하며 총 처리량이 역감소. 추론 스레드(검출+트래킹 CPU)와 appsink 콜백(배치 메타 순회·게이트·GPU 전처리·`cuda synchronize`)이 한 파이썬 프로세스(GIL) 안에서 경합 — 채널이 늘수록 콜백 측 부하(초당 메타 순회 수 ∝ N×원본fps)가 커져 추론 스레드를 침식 |
| 큐(oldest-drop) | 병목 아님(설계대로) | 드랍은 원인이 아니라 결과 — 처리 능력 초과분을 버려 지연 폭주를 막는 역할 수행 |

정리하면 **현 구조의 1GPU 한계는 "워커 프로세스 1개의 처리 능력"이지 GPU
하드웨어가 아니다**. 프레임당 ~12.7ms(검출 배치 지분 + 카메라별 BoostTrack
CPU 지분)가 기본 단가이고, 이 단가로 초당 ~79프레임이 상한이다.

## 5. GPU 2장 외삽·운영 권고

- 워커는 GPU별 독립 컨테이너/프로세스(P5 launcher)라 병목(프로세스 단가)도
  GPU 수만큼 복제된다 → **산술 외삽: 2GPU ≈ 24~32ch에서 5fps**
  (GPU당 12ch 확실 + 16ch 경계). 4대 지표 PoC 목표(≤16ch)는 **1GPU로 충족**,
  2GPU면 12ch씩 나눠 여유 운영이 가능.
- 단 실측상 **GPU0을 타 프로젝트(deepstream-app 2개 등, SM ~54~75%)와
  공유하면 TRT 추론이 배치당 2.8~10초로 붕괴**(채널당 ~0.1fps, P5 2GPU
  검증에서 실측) — 멀티 GPU 운영은 전용 GPU 확보가 전제다.
- 1GPU에서 16ch를 넘겨야 한다면 다음 순서로 여지가 있다(미실측, 후속 과제):
  ① 워커를 GPU당 2개로 쪼개 채널 분할(프로세스 병목 우회 — launcher 구조
  재사용 가능), ② appsink 콜백의 전처리·synchronize를 추론 스레드로 이동해
  GIL 경합 축소, ③ b32 엔진(현 데이터로는 배치 크기가 아니라 호스트 직렬화가
  병목이라 우선순위 낮음).

## 6. 발견 제약 (기록)

- vLLM 점유(84GB)로 여유 ~14GB 조건에서도 64ch까지 OOM 없음(워커 ~11GB).
  vLLM이 활성 추론을 시작하면 SM 경합으로 수치가 달라질 수 있음 — 본 측정은
  vLLM 유휴 시점.
- NVDEC 세션 64개까지 에러 없음 — 이 서버에서 디코드 세션 한도는 64ch
  이내에서 미발현.
- 스트림 12본을 중복 구독하는 방식이라 콘텐츠 다양성은 12종 — 트래킹 CPU
  부하(객체 수)는 실제 현장 분포와 다를 수 있다.

### 7.2 판정 — 5fps 유지 최대 채널 수

**16ch로 확정 — 워커 분할과 무관하게 동일하다** (w1 4.93 / w2 4.96,
w3는 20ch에서 이미 4.20으로 미달). 분할의 총량 이득은 5fps가 이미 깨진
과부하 영역에서만 나타난다(24ch +9~36%, 64ch +25%).

### 7.3 왜 분할이 한계를 못 늘리는가 — 병목 재진단

§3은 "SM 39~54%로 GPU가 놀고 있으니 병목은 워커 프로세스(GIL)"라고
진단했지만, 분할 실험이 이를 기각한다:

- 분할하면 SM이 91~96%로 포화되는데 총량은 79~102fps에 머문다. GIL이
  병목이었다면 분할로 총량이 ~2배 나와야 한다.
- 배치 벽시계 시간: 단일 16ch = 204ms/16장(12.7ms/장) vs 2분할 = 189ms/8장
  ×2워커(23.6ms/장). 두 컨텍스트가 GPU를 시분할하므로 각 워커의 배치가
  서로를 기다린다 — 단독 실행 시 같은 8장 배치는 ~79ms(§7 스팟체크·8ch
  단독 실측)로, 동시 실행에서 ~2.4배로 늘어난 것.
- 즉 **상한은 GPU 커널 시간이다**: 이 엔진(YOLOX 896×1600 fp16 b16)의 검출
  커널 처리량이 초당 ~80장 수준이고, 단일 워커는 이미 그 근처(75~79fps)에서
  포화돼 있었다. §3의 SM 평균 39~54%는 nvidia-smi 폴링 표본의 과소집계로
  본다(분할 후 91%+로 급등한 것이 방증 — 커널 점유가 이미 높았다).
- 다만 분할이 순수 손해는 아니다: 3분할 24ch 총량 102.5fps(+36%)는 다중
  컨텍스트가 커널 사이 틈(호스트 준비 시간)을 서로 메꾼 효과다. 그러나
  5fps 유지선은 못 넘긴다.

### 7.4 운영 권고·남은 병목

- **`WORKERS_PER_GPU` 기본 1 유지 권장.** 분할은 5fps 한계를 늘리지 못하고
  메모리(워커당 ~5~7GB)와 시동 복잡도만 늘린다. 목표가 "채널당 fps 유지"가
  아니라 "많은 채널의 총 처리량"(저하 허용)이라면 2~3분할이 +25~36% 유효.
- 1GPU에서 16ch를 넘기는 다음 레버 (우선순위 갱신):
  ① **b32 dynamic 엔진**(최우선 — b8≈b16≈190~200ms로 배치 고정비가 지배하는
  구간이므로, b32가 같은 고정비면 프레임 단가가 절반: ~13→~7ms/장,
  이론상 ~29ch@5fps. §5에서 "우선순위 낮음"으로 본 것은 §3의 오진에 따른
  것 — 정정), ② 검출 입력 해상도 축소(896×1600 → 736×1280 등, 정확도
  트레이드오프 실측 필요), ③ MPS(멀티 프로세스를 쓸 경우의 컨텍스트 스위칭
  낭비 제거 — 과거 실측 +27%, `bench/results_mps_*.json`), ④ FP8/INT8 양자화.

## 8. 부록 — 워커 분할이 드러낸 트래킹 죽음의 나선 (발견·수정)

재스윕 첫 시도에서 스텝마다 워커 한쪽이 배치당 3~7초로 붕괴해 수 분간
지속되는 현상이 재현됐다(어느 워커가 걸릴지는 무작위). py-spy 스택 표본
100%가 BoostTrack 연관 수식(`soft_biou_batch`·`get_mh_dist_matrix`)의 CPU
구간이었고, STATS 계측(trk=/detmax= 추가)으로 인과를 실증했다:

1. RTSP 힉업/재접속 구간의 깨진 디코드 프레임이 저신뢰 오검출을 **프레임당
   5,800~7,600개**(정상 47~65개) 생성
2. BoostTrack 신뢰도 부스트(dlo/duo)가 이를 트랙 후보로 승격 → 트래커
   **14,394개**까지 폭증 (max_age는 "처리 프레임" 기준이라 드랍 중엔 wall-clock
   으로 오래 잔존)
3. 연관 비용 O(det×trk)이 배치당 수 초 → 큐 드랍 가속 → 프레임 간격 확대 →
   매칭 실패 → 트래커 재폭증 … **자기유지 나선**

수정(worker.py — 정상 경로 출력 불변, 커밋 02bdc58):

- **깨진 프레임 가드**: 프레임당 검출 >1,000이면 트래킹 생략(상태 오염 방지)
- **회로차단기**: 캠 트래커 >500이면 해당 캠만 리셋(나선 진입 시 탈출)
- **엔진 워밍업**: 파이프라인 기동 전 더미 배치로 콜드 스타트 소진
- **BLAS 스레드 1 고정**: 컨테이너 nproc(128) 스핀 풀의 프로세스 간 CPU 경합 제거

수정 후 검증: 타 작업이 SM 55%를 점유하는 최악 조건에서도 16ch 2분할이
채널당 4.91fps·qdrop 0으로 안정. 이 나선은 단일 워커·기존 ffmpeg 경로에도
잠재하는 리스크였다(트리거만 안 밟았던 것) — 가드는 모든 DS 워커 구성에
기본 적용된다.

### 9.3 대조 실험 — 열세가 엔진 탓인가 배치 크기 탓인가

같은 32ch·같은 b32 엔진에 배치 상한만 16으로 걸었다
(`--max-batch 16`, [`gpu1_b32cap16`](bench/results_ds_limit_gpu1_b32cap16.json)):

| 32ch 구성 | 채널 fps mean | 총 처리량 | infer/프레임 |
|---|---:|---:|---:|
| b16 엔진 · batch≤16 (§2, 전일) | 2.35 | 74.8 | 13.4 ms |
| b32 엔진 · batch≤16 (대조, 당일) | 2.05 | 65.3 | 15.3 ms |
| b32 엔진 · batch≤32 (§9.2, 당일) | 1.98 | 63.5 | 15.8 ms |

같은 날 측정한 두 b32 구성(batch 16 vs 32)은 65.3 vs 63.5fps로 **대동소이**
— 32ch 지점의 §2 대비 낙폭(−13~15%)에는 배치 효과 외에 측정일 간 변동
(스트림 콘텐츠 루프 위상에 따른 트래킹 부하 차이, §6 방법론 한계)이 섞여
있다고 본다. 반면 **당일 세션 안에서의 경향은 일관적**이다: 프레임 단가가
16ch 12.6 → 20ch 13.9 → 32ch 15.8ms로 배치·채널과 함께 단조 증가하고,
어느 지점에서도 배치 확대가 단가를 낮추지 못한다. 결론(이득 없음)은
엔진(b16/b32)·배치 상한(16/32) 어느 축으로도 뒤집히지 않는다.

### 9.4 판정·병목 최종 정리

- **(a) 채널당 5fps 유지 한계: GPU 1장당 16ch** — b16/b32/워커 분할 모두
  동일. 20ch부터 3.6fps로 붕괴한다.
- **(b) 1fps 도달점: ~54ch** (b32 실측 48ch 1.16 → 64ch 0.73 선형 내삽
  ≈54ch, b16은 ≈57ch). 50ch대 중반부터는 채널당 1fps도 못 지킨다.
- **b32 엔진 운영 채택 안 함** — 기본 b16 유지(`worker --det-engine` 기본값
  불변). 엔진 파일·빌드 스크립트·인자화(`--max-batch`/`DS_ENGINE_MAX_BATCH`/
  `DS_DET_ENGINE`)는 후속 실험용으로 남긴다.
- **병목의 실체 (진단 3차 수정)**: §3 "GIL" → §7.3 "GPU 커널"을 거쳐,
  b32 실험으로 최종 정리하면 — 검출 커널은 ~4.9ms/장(선형·총 ~200fps
  여력)이고, 상한 ~78fps를 만드는 것은 **프레임당 직렬 호스트+GPU 혼합
  단가 ~12.6ms**(검출 커널 4.9 + 트래킹 CPU·ReID·전처리·동기화 ~7.7)다.
  워커 분할(§7)이 못 늘린 이유도 GPU 커널 포화가 아니라 분할된 프로세스들이
  같은 GPU 직렬 자원(커널+복사+동기화)을 시분할하기 때문으로 재해석된다.
  배치를 키우면 GPU 점유 구간이 길어져 appsink 콜백(GIL)과의 경합만 늘고
  (프레임 단가 12.6→15.8ms), 큐 체류가 길어져 드랍 리듬도 나빠진다.
- 1GPU에서 16ch를 넘기는 다음 레버 (우선순위 재갱신): ① **트래킹 CPU
  단가 절감**(프레임당 ~7ms — 연관 수식 벡터화/네이티브화, 검출 수 상한),
  ② 검출 입력 해상도 축소(896×1600 → 736×1280, 커널 4.9ms/장 절감,
  정확도 트레이드오프 실측 필요), ③ appsink 콜백 경량화(전처리·synchronize를
  추론 스레드로 이동), ④ FP8/INT8 양자화. (②~④는 미실측.)
