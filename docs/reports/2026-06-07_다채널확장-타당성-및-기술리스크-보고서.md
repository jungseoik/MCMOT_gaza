## 1. 문서 목적

고객 요구 4개 기능의 **구현 난이도·기술 리스크**를 평가하고, 최종 목표인 **150채널 동시 운영**이 현재 아키텍처/하드웨어에서 가능한지, **단일 카메라 대비 150채널의 지연·자원**을 비교 분석하여, **달성까지의 공수**를 산정한다.

## 2. 현재 시스템 기준선 (측정 기반)

### 2.1 하드웨어

| 자원 | 사양 | 비고 |
|------|------|------|
| GPU | RTX PRO 6000 Blackwell Server Edition ×2 | 각 **96GB** VRAM, compute 12.0 |
| CPU | Intel Xeon 6530P | **128 logical cores** |
| 추론 모델 | YOLOX(검출) + FastReID(재식별), 둘 다 TRT FP16 | 1세트 VRAM ~100~150MB |

### 2.2 단일 카메라 실측 성능 (646프레임, 1 GPU, 단일 스레드)

| 모드 | FPS | 1프레임 | 비고 |
|------|-----|---------|------|
| PyTorch 원본 | 0.88 | 1,140ms | — |
| TRT FP16 단독 | 0.93 | — | 병목이 모델추론이 아니라 효과 미미 |
| **TRT FP16 + GPU 최적화** | **17.6** | **57ms** | 현재 운영 기준선 |

### 2.3 1프레임(57ms) 자원별 분해 — **이것이 확장성의 핵심**

| 단계 | 시간 | 자원 | 채널 수 증가 시 |
|------|------|------|----------------|
| 전처리(letterbox resize) | ~39ms | **CPU** | 코어 분산 가능 |
| YOLOX 검출 | ~8ms | **GPU** | ❌ 배치로 효율화 안 됨 (3.A 실측) |
| ReID crop(cv2) | ~10ms | **CPU** | 객체 수 비례 |
| ReID 모델 추론 | ~7ms | **GPU** | ✅ 배치 효과 있음 (3.B 실측) |
| ECC 카메라보정 | ~8ms | **CPU** | GPU 대안 없음(고정비) |
| 추적/연관(Hungarian 등) | ~수ms | **CPU** | **군중 밀도 O(N×M)** |

**결정적 사실 3가지:**
1. **GPU 작업은 전체의 일부(실측 ~9~16ms)에 불과**하다. 단일 스트림에서는 GPU(Blackwell)가 **거의 놀고 있다**. → GPU는 여러 채널이 공유할 여력이 있다. **단, 검출은 배치로 안 빨라지므로 공유 채널 수에는 천장이 있다(3장).**
2. 나머지(전처리·ECC·crop·연관)는 **CPU 바운드**. 128코어로 **수평 분산** 여지가 크다 → CPU는 병목이 아니다.
3. 추적 연관 비용은 **화면 내 사람 수(N) × 추적 객체 수(M)에 비례**해 증가한다. 혼잡 장면(공항·대피)일수록 채널당 부하가 커진다.

> 위 분해는 최적화 보고서 기준(저밀도 클립). **본 머신 실측값은 3장** 참조(검출 ~4.6ms, ReID·전처리 포함 단일 스트림 12.5FPS).

### 2.4 구조적 제약 (확장 시 반드시 고려)

| 제약 | 현재 상태 | 영향 |
|------|-----------|------|
| 배치 추론 | **없음** (1프레임씩) | ReID엔 손해(배치 효과 못 씀). 단 **검출은 배치해도 비가속**이라(3.A) 배치만으론 천장 못 올림 |
| 동시성 | `_model_lock`으로 **직렬화**, 단일 트래커 인스턴스 공유 | 한 프로세스가 1채널만. 다채널 = 다프로세스 필요 |
| 상태 영속화 | **인메모리만** (휘발성) | 보고서·잔류인원 누적엔 DB/스토리지 필요 |
| 좌표계 | **카메라 단위 독립** | 다카메라 통합 맵(기능3)에 좌표 정합 필요 |

## 3. 실측 배치 추론 벤치마크 (2026-06-07, 본 머신)

> 고객 요청: "현재 로직을 **배치처리로 1→15채널** 돌렸을 때 지연이 실제로 얼마나 늘어나는지" 측정.
> 측정 환경: RTX PRO 6000 Blackwell **1장**(GPU1), FP16 TRT 엔진, 워밍업 후 평균. (스크립트·원자료: [`bench/`](bench/), `results.json`)

### 3.A YOLOX 검출 — 채널 배치 시 지연 (입력 896×1600)

검출 엔진을 **동적 배치로 재빌드**해 N채널 프레임을 한 번에 추론한 실측:

| 배치 채널 수 | 1회 추론 지연 | **프레임당 지연** | 직렬 대비 처리량 |
|:-----------:|:------------:|:----------------:|:---------------:|
| 1 (고정엔진) | 5.06 ms | 5.06 ms | 기준 |
| 1 (동적) | 6.19 ms | 6.19 ms | ×0.82 |
| 2 | 10.28 ms | 5.14 ms | ×0.98 |
| 4 | 17.90 ms | 4.48 ms | ×1.13 |
| 8 | 35.11 ms | 4.39 ms | ×1.15 |
| 12 | 54.89 ms | 4.57 ms | ×1.11 |
| **15** | **69.22 ms** | **4.61 ms** | **×1.10** |

> **⚠️ 핵심 발견: 검출은 배치해도 처리량이 거의 안 늘어난다.** 프레임당 지연이 5.0→4.6ms(고작 −9%)에 그친다. 입력 해상도(896×1600)가 커서 **단일 프레임만으로도 GPU 연산이 이미 포화**되기 때문이다. 즉 배치는 일을 **선형으로 쌓을 뿐** GPU 처리량을 곱해주지 못한다. → 검출 처리량 천장은 **약 200~220 fps/GPU로 고정**.

### 3.B FastReID — crop 배치 시 지연 (입력 384×128)

ReID는 (검출과 달리) 배치 효과가 뚜렷하다:

| crop 수 | 1회 추론 지연 | crop당 지연 |
|:------:|:------------:|:----------:|
| 1 | 1.13 ms | 1.130 ms |
| 8 | 1.73 ms | 0.216 ms |
| 16 | 2.49 ms | 0.155 ms |
| 32 | 3.89 ms | 0.121 ms |
| 50 | 5.62 ms | 0.113 ms |
| 64 | 7.18 ms | 0.112 ms |
| 128 | 14.6 ms | 0.114 ms |
| 256 | 30.0 ms | 0.117 ms |

> ReID는 batch≈32~50에서 포화(crop당 ~0.11ms). 사람 40명/프레임 ≈ **4.5ms/프레임**. 단, 혼잡 장면(100명)이면 ~11ms로 증가 → **밀도가 ReID 비용을 좌우**.

### 3.C CPU 전처리 (배치 불가, 프레임당 고정)

| 항목 | 실측 |
|------|------|
| letterbox resize (960×540→896×1600) | **29.35 ms/frame** |

> 전처리는 GPU 배치와 무관하게 **프레임마다 CPU에서 발생**. 다채널 시 128코어로 분산해야 하며, 분산하지 않으면 이 자체가 병목.

### 3.D 단일 스트림 전체 파이프라인 (실측, 본 머신)

| 영상 | 실측 FPS | 프레임당 | 비고 |
|------|:--------:|:--------:|------|
| sample1.mp4 (공항 혼잡, ~40~50명) | **12.51 FPS** | **79.9 ms** | GPU작업 ~10ms + 전처리 29ms + ECC/추적/연관 ~40ms |

> 최적화 보고서의 17.6 FPS는 **밀도가 낮은 646프레임 MOT20 클립** 기준. 본 측정은 **혼잡 장면**이라 연관/ReID 비용이 커져 12.5 FPS. → **밀도가 채널당 성능을 크게 좌우**함을 실증.

### 3.E ⭐ 전체 파이프라인 다채널 실측 (검출+추적+ReID, 1프로세스·1GPU)

**핵심 요청에 대한 직접 실측.** N채널을 한 라운드(채널당 1프레임)로 처리 — 검출은 진짜 배치(1 GPU 콜), 추적은 채널별 독립 인스턴스. 라운드 전체 지연과 그에 따른 fps:
(스크립트: [`bench/bench_pipeline_channels.py`](bench/bench_pipeline_channels.py), 원자료 `results_pipeline.json`. 전처리 29ms/frame은 별도·가산 항목으로 제외)

| 채널 | 라운드 지연 | 검출 | 추적 | **채널당 fps** | 총 처리량 |
|:---:|:----------:|:----:|:----:|:-------------:|:--------:|
| 1 | 35.6 ms | 7.4 | 28.1 | **28.1** | 28.1 fps |
| 2 | 72.4 ms | 12.3 | 60.0 | **13.8** | 27.6 |
| 4 | 150.5 ms | 21.6 | 128.7 | **6.65** | 26.6 |
| 6 | 227.9 ms | 31.1 | 196.6 | **4.39** | 26.3 |
| 8 | 302.3 ms | 41.0 | 261.1 | **3.31** | 26.5 |
| 10 | 379.4 ms | 50.9 | 328.2 | **2.64** | 26.4 |
| 12 | 449.6 ms | 61.8 | 387.5 | **2.22** | 26.7 |
| **15** | **563.4 ms** | 77.2 | 485.7 | **1.78** | 26.6 |

**측정이 말하는 것:**
1. **지연은 채널당 +37.6ms로 선형 증가** → `라운드 지연 ≈ 37.6 × 채널수 (ms)`. 15채널 563ms.
2. **채널당 fps = 26.6 ÷ 채널수** (15채널 = 1.78fps).
3. **총 처리량은 ~27fps로 고정** — 1프로세스에선 채널을 늘려도 총량이 안 늘고 **27fps를 채널 수로 나눌 뿐**. ("배치로 한 방에 싸게"가 성립 안 함을 실증)
4. **병목은 검출이 아니라 추적** — 15채널에서 추적 486ms(86%) vs 검출 77ms(14%). ReID·ECC·연관이 채널마다 쌓인다.

> **150채널 외삽**: 1프로세스·1GPU 그대로면 27fps÷150 = **채널당 0.18fps**(라운드 5.6초) → 불가. 추적은 CPU라 **병렬화(128코어·2GPU)** 하면 총 처리량이 아래 GPU 천장(~200fps)까지 오르지만, 그래도 **150채널 @ ~1.3fps**가 한계.

### 3.F 측정 종합 — GPU 처리량 천장 (병렬화 시 상한)

위 단일 프로세스(27fps)는 GPU·CPU가 한 스레드에서 직렬이라 GPU가 논다. **다프로세스로 병렬화하면** 총 처리량은 GPU 천장까지 오른다:

| 구성요소(프레임당) | 중밀도(~40명) | 고밀도(~100명) | 배치 가속 |
|------------------|:------------:|:-------------:|:--------:|
| 검출(GPU) | 4.6 ms | 4.6 ms | ❌ 거의 없음 |
| ReID(GPU) | 4.5 ms | 11 ms | ✅ 있음(포화 전) |
| **GPU 합계/프레임** | **~9 ms** | **~16 ms** | — |
| **GPU 천장(1장)** | **~110 fps** | **~64 fps** | — |
| **GPU 천장(2장)** | **~200~220 fps** | **~128 fps** | — |

**두 측정의 관계:** 1프로세스 = 27fps(GPU 놀고 CPU 직렬), 완전 병렬화 = GPU 천장 ~200fps(2GPU). **150채널 판단의 상한이 이 ~200fps**이며, 검출이 배치로 안 빨라지므로(3.A) 이 천장은 GPU 시간으로 고정된다. → 검출/추적 **경량화**만이 천장을 올린다.

### 3.G ⭐⭐ 병렬 다채널 실측 (멀티프로세스·2GPU, 현재 코드 그대로)

**"지금 15채널 실시간 처리량이 얼마냐"에 대한 직접 실측.** 채널마다 독립 프로세스로 전체 파이프라인을 2 GPU에 분산하고, 경합 상태에서 채널당 지속 fps를 측정:
(스크립트: [`bench/bench_multiproc.py`](bench/bench_multiproc.py), 원자료 `results_multiproc.json`. GPU0은 타 작업 ~20% 점유 중이라 약간 보수적)

| 동시 채널 | **채널당 fps** | 총 처리량 | 병렬효율 |
|:---:|:------------:|:--------:|:-------:|
| 1 | 10.85 | 10.9 fps | — |
| 4 | 9.95 | 39.8 fps | 92% |
| 8 | 8.85 | 70.8 fps | 82% |
| **15** | **7.07** | **106.1 fps** | 65% |

**측정이 말하는 것:**
1. **지금 15채널 = 채널당 ~7fps, 총 106fps** (현재 코드·무최적화·2GPU). 1프로세스 1.78fps 대비 **~4배** — 병렬화가 GPU·CPU를 겹쳐 쓰기 때문.
2. **채널당 fps는 완만히 감소**(10.85→7.07), 총 처리량은 상승하나 **65% 효율로 둔화** — 2GPU를 15프로세스가 나눠 쓰며 GPU 경합·컨텍스트 스위칭 발생. GPU 천장(~150~200fps)에 접근 중.
3. 25fps 부드러운 추론은 안 되지만 **7fps는 군중 분석에 실용적**. 표출 영상은 원본 fps로 보여주고 분석 오버레이만 7fps 갱신하면 체감 실시간.

> **150채널 외삽(실측 곡선 기반)**: 총 처리량 천장 ~150~200fps → 150채널이면 **채널당 ~1~1.3fps**. 5fps 이상은 **검출/추적 경량화 + GPU 증설** 필수. (3.F 추정을 실측이 확인)

### 3.H MPS 효과 실측 (단일 GPU, 멀티채널, 켜고/끄고 비교)

`nvidia-cuda-mps-control` 데몬으로 여러 프로세스가 GPU SM을 **동시 점유**(시간분할 대신)하게 했을 때의 처리량 변화. 동일 GPU·동일 영상(896×1600)에서 MPS off/on 비교:
(스크립트: [`bench/bench_mps.py`](bench/bench_mps.py), 원자료 `results_mps_*.json`. 데몬 셋업/함정은 [`bench/README.md`](bench/README.md))

| 채널 | MPS off 총 | MPS on 총 | 개선 | (채널당 off→on) |
|:---:|:---------:|:--------:|:----:|:---------------:|
| 1 | 12.4 | 12.2 | −2% | 12.4→12.2 |
| 4 | 34.6 | 41.3 | **+19%** | 8.65→10.32 |
| 8 | 51.2 | 65.0 | **+27%** | 6.40→8.12 |
| 12 | 63.4 | 69.5 | +10% | 5.28→5.79 |

**측정이 말하는 것:**
1. **MPS는 중간 동시성(4~8ch)에서 +19~27%** — 8ch에서 최대(51→65fps). 단일 채널엔 효과 없음(겹칠 게 없음).
2. **per-GPU 천장이 ~63→~70fps로 상승**, 하지만 **이론 연산 천장 ~100fps엔 못 미침.** 남은 격차는 GPU 스케줄링이 아니라 **프로세스별 CPU(전처리·추적)+Python 오버헤드** → MPS만으로는 못 메움.
3. 결론: **MPS는 "공짜에 가까운 +20~27% 보조 지렛대"**(코드 변경 0, 데몬만 기동). 단, 천장 자체를 크게 못 올리므로 **추적 경량화가 여전히 핵심.**

## 5. 단일 카메라 vs 150채널 비교 분석 (실측 기반)

### 5.1 처리량(throughput) — 3장 실측 천장 적용

3.F의 실측 천장(검출 비가속 확정): **중밀도 ~110 fps/GPU, 고밀도 ~64 fps/GPU.**
2 GPU 합산 천장 = **중밀도 ~200 fps / 고밀도 ~128 fps** (CPU는 128코어로 분산 가능하므로 천장은 GPU가 결정).

| 시나리오 | 필요 처리량 | 2GPU 천장(중밀도 200fps) 대비 | 판정 |
|----------|-------------|------------------------------|------|
| 150ch × 25fps | 3,750 fps | 천장의 **19배** | ❌ |
| 150ch × 10fps | 1,500 fps | 천장의 **7.5배** | ❌ |
| 150ch × 5fps | 750 fps | 천장의 **3.75배** | ❌ |
| 150ch × 1.3fps | ~200 fps | ≈ 천장 | 🟡 (fps 너무 낮음) |

**2 GPU에서 채널수 ↔ fps 트레이드오프 (실측 천장 200fps 기준):**

| 채널당 fps | 2GPU 최대 채널 수 |
|:---------:|:-----------------:|
| 1.3 | ~150ch (한계, 추적품질 저하) |
| 5 | **~40ch** |
| 10 | **~20ch** |
| 25 | ~8ch |

> 검출이 배치로 가속되지 않으므로(3.A), "현재 코드 그대로"든 "배치 구현"이든 **GPU 천장은 동일**하다. 배치는 검출 처리량을 못 올린다 — 이게 이전 추정과 가장 크게 달라진 점.

### 5.2 150채널을 위해 필요한 GPU 수 (실측 외삽)

per-GPU 천장(현재 모델, 실측): MPS off **~54fps/GPU**, **MPS on ~65~70fps/GPU**(3.H). 이론 연산 천장 ~100은 CPU·Python 오버헤드로 미달. 측정치 기준:

| 목표 | 필요 처리량 | 현재 모델(~54fps/GPU) | +MPS(~70fps/GPU) | +MPS+추적경량화·해상도↓(낙관 ~100) |
|------|-------------|:---------------------:|:----------------:|:----------------------------------:|
| 150ch @ 1.5fps | 225 fps | ~4 GPU | ~3 GPU | 2~3 GPU |
| 150ch @ 5fps | 750 fps | **~14 GPU** | **~11 GPU** | **~8 GPU** |
| 150ch @ 10fps | 1,500 fps | ~28 GPU | ~22 GPU | ~15 GPU |

> 실측 지렛대: **MPS +20~27%(3.H), 검출 해상도↓ ×1.2~1.5([해상도 보고서](2026-06-07_검출해상도-스케일링-실측-보고서.md))** — 둘 다 **완만**하다. 병목이 **추적**이라, GPU 수를 절반으로 줄이려면 **추적/ReID 경량화가 핵심**이고 MPS·해상도·INT8는 보조. "경량화로 GPU 절반"은 단일 지렛대론 과대추정.

### 5.3 지연시간(latency) 비교

| 구분 | 단일 카메라(실측) | 150채널 (2GPU·현 모델) | 150채널 (4GPU·검출경량화) |
|------|------------------|------------------------|---------------------------|
| 프레임당 GPU | ~9~16 ms | 동일(공유) → **채널당 ~1.3fps로 제한** | 채널당 5~10fps 설계 가능 |
| 전체 처리 | 79.9ms (12.5fps) | 큐 적체 시 체감 수 초+ | 목표 <1s 설계 가능 |
| VRAM | ~0.15~1GB | 150ch ≈ **~30GB (96GB×2에 충분)** | 충분 — **VRAM은 제약 아님** |
| 병목 | 전처리(CPU)+연관 | **GPU 검출 처리량(배치 비가속)** | 검출 경량화로 천장 상향 |

**핵심:** VRAM(192GB)은 문제가 아니다. 진짜 벽은 **검출 GPU 처리량이 배치로 안 늘어난다**는 실측 사실이다.

## 6. 150채널 달성 가능성 — 종합 판정 (실측 기반)

| 목표 수준 | 2 GPU(현 모델) | 4 GPU(현 모델) | 4 GPU(검출 경량화) | 결론 |
|-----------|:--------------:|:--------------:|:------------------:|------|
| 150ch @ 25fps | ❌ | ❌ | ❌ | ~13~38 GPU 필요. 비현실적 |
| 150ch @ 10fps | ❌ | 🟡(경계) | 🟢 | 4GPU+경량화 권장 |
| 150ch @ 5fps | ❌ | 🟡 | 🟢 | **현실적 1차 목표** |
| 150ch @ ~1.5fps | 🟡(품질저하) | 🟢 | 🟢 | fps 낮아 추적 품질 위험 |

**판정 (실측 근거):**
- **현재 코드/모델 그대로 2GPU: 유용한 fps(5~10) 기준 ~20~40채널이 한계.** 150채널과 큰 격차.
- **150채널을 5~10fps로 돌리려면**: (a) **검출 경량화**(해상도↓·INT8·경량 검출기)로 GPU 천장을 2~3배 끌어올리고, (b) **GPU 4장 내외**로 증설, (c) 멀티프로세스로 CPU(전처리·추적)를 128코어에 분산.
- **검출 경량화 없이 배치만으로는 불가** — 3.A 실측이 배치 비가속을 증명.
- **밀도가 결정적**: 공항/대피 같은 고밀도(100명+)에서는 천장이 절반(~128fps/2GPU)으로 떨어져 필요 GPU가 ~2배.

## 7. 필수 선행 — 지연시간/부하 테스트 계획

> 3장에서 **단일 GPU의 배치 추론 곡선**은 실측 완료. 남은 것은 **다채널 동시 end-to-end**(멀티프로세스 큐 적체·CPU 경합·실효 fps)의 실부하 측정이다.

### 7.1 테스트 매트릭스

| 변수 | 수준 |
|------|------|
| 동시 채널 수 | 1, 4, 8, 16, 32, 64, 100, 150 |
| 채널당 목표 fps | 3, 5, 10, 25 |
| 장면 밀도 | 저(~10명) / 중(~50명) / 고(~150명+) |
| GPU 수 | 1, 2, (가능 시 4) |
| 구성 | 현재 코드(멀티프로세스) / 고도화 단계별 |

### 7.2 측정 지표
- **채널당 실효 fps**(목표 대비 달성률), **end-to-end 지연**(프레임 입력→결과 출력) p50/p95/p99
- GPU 가동률·VRAM, CPU 코어 점유, 큐 적체 길이
- 채널 수 증가에 따른 **지연 곡선의 꺾이는 지점(saturation knee)** = 안전 채널 한계

### 7.3 산출물
- "GPU N장 × 밀도 × fps → 안전 채널 수" 곡선 → **150채널에 필요한 GPU 수/fps 확정**
- RTSP 송출 환경은 이미 구축됨(`~/rtsp-stream/` mediamtx). 동일 스트림을 **N개 경로로 복제 송출**해 부하 발생기로 사용 가능.

## 8. 고도화 로드맵 & 예상 공수

> 실측(3장)에 따라 우선순위를 재조정: **검출 처리량을 못 올리는 "배치 추론"은 효과가 작고, "검출 경량화"가 핵심 지렛대**다.

| 단계 | 작업 | 효과(실측 반영) | 난이도 | 공수(추정) |
|------|------|----------------|:------:|:----------:|
| 0 | **다채널 실부하 테스트 하니스**(7장) | 목표·병목·실효 fps 확정 | 🟡 | 1~2주 |
| 1 | 멀티프로세스/MPS 오케스트레이션(채널↔프로세스, GPU 분산) | CPU 128코어·2GPU 활용 극대화 | 🟡 | 2~3주 |
| 2 | **검출 경량화** ⭐(입력 해상도↓ / INT8 양자화 / 경량 검출기) | **GPU 천장 ×2~3 (유일하게 효과적)** — 정확도 검증 필수 | 🔴 | 4~8주 |
| 3 | ReID 배치 통합(다채널 crop 합쳐 추론) | ReID는 배치 효과 있음(3.B) → 소폭 이득 | 🟡 | 2~3주 |
| 4 | **GPU 전처리**(letterbox CUDA화, 보간 동일성 확보) | 채널당 -29ms CPU → 필요 코어↓ | 🔴 | 2~4주 |
| 5 | 혼잡 장면 연관 최적화(게이팅/그리디로 O(N×M)↓) | 고밀도 안정화 | 🟡 | 2~3주 |
| 6 | 영속화 계층(지표 DB) — 기능2·4 전제 | 잔류누적·보고서 | 🟡 | 1~2주 |

**스케일링 고도화 합계: 약 13~22주 (3~5.5개월), 1차 목표(150ch@5fps, 4GPU) 기준.** 단계 2(검출 경량화)가 처리량 천장을 결정하는 핵심 경로. GPU 증설은 경량화와 별개로 병행 가능.

### 기능 구현 공수(스케일링과 병행)

| 기능 | 공수 | 핵심 선행 |
|------|:----:|-----------|
| F1 지표·대시보드 | 1~2주 | (거의 완료) |
| F2 잔류인원 | 3~5주 | 게이트 카운팅 + 영속화(단계6) |
| F3 2D맵·대피경로 | 8~12주+ | 다카메라 좌표정합·경로엔진 |

## 9. 리스크 요약 & 권고

### 최상위 리스크
1. **🔴 검출 GPU 처리량이 배치로 안 늘어남 (실측 확정)** — 3.A에서 배치=비가속 증명. 150채널의 최대 기술 장벽. **검출 경량화(단계2)** 없이는 GPU 천장을 못 올림.
2. **🔴 기능3(다카메라 통합맵·대피경로)** — 신규 서브시스템 다수, 일정 불확실성 최대. 별도 트랙 권장.
3. **🟡 밀도 의존 연관비용 O(N×M)** — 공항/대피 같은 고밀도에서 ReID·연관 비용 급증 → GPU 천장 절반(실측 64fps/GPU). 채널당 안전 fps를 밀도별로 확정 필요.
4. **🟡 검출 경량화의 정확도 트레이드오프** — 해상도↓·INT8·경량모델은 처리량을 올리지만 탐지 정확도 저하 위험. 반드시 정확도 검증 동반.
5. **🟡 정확도 신뢰성** — km/h·잔류수 모두 보정/누적 의존 추정값. 고객 보고 전 **보정선 교차검증** 권장.

### 권고
- **단계적 목표**: 1차 **150ch @ 5fps**(군중 흐름분석 충분) → 검증 후 fps/채널 상향.
- **하드웨어**: VRAM은 충분(192GB). 실측 천장상 **GPU 4장 내외 증설 + 검출 경량화 병행**이 150채널 5fps의 현실 경로.
- **즉시 실행**: 7장 **다채널 실부하 테스트**부터(단일 GPU 배치곡선은 3장에서 실측 완료). 실효 fps·큐 적체를 확정한 뒤 인력/하드웨어 투자 결정.
- **기능 우선순위**: F1(완료급) → F4·F2(영속화 공유) → F3(별도 트랙·장기).
